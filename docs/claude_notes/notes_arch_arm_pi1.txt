What this is
------------
forks/rpi1 is zhiyihuang/xv6_rpi_port (2014) - the root of the whole
"ARM Raspberry Pi" lineage in this repo (forks/armv6-rpi is forked from
its tip; forks/rpi2 extends it to ARMv7). Genuinely targets real
Raspberry Pi 1 (BCM2835/ARM1176JZF-S) hardware: Alex Chadwick's "Baking
Pi" tutorial-style GPU/mailbox driver code, a real vendored libcsud.a
(Chadderz's USB driver, unlike armv6-rpi's own missing copy), a dual
GPU-framebuffer + Mini-UART console (writes every character to BOTH),
and a real, if outdated, mailbox-based framebuffer setup.

Toolchain: arm-linux-gnueabihf-gcc/qemu-system-arm, already installed - no gaps

Real hardware safety
---------------------
kernel.ld (what "make all"/kernel.img - the thing you'd write to an SD
card - actually uses) was NOT touched. All three fixes below are either:
  - universal correctness fixes (the CC/ARMGNU bug, -fcommon, and the
    -mcpu/-marm codegen fix) that make the SAME real-hardware kernel.img
    build correctly and target the real CPU more precisely than before -
    none of these change what the compiled code actually does on real
    silicon, they just make gcc generate code that actually matches the
    "-Wa,"-only flags' original intent instead of silently using the
    toolchain's own unrelated default
  - the delay()/getsystemtime() busy-wait fix (source/timer.c), which
    changes an exact-equality spin-wait to a "target reached or passed"
    spin-wait - real hardware's timer should never actually skip past
    the exact target value in practice, so this is unlikely to ever
    change behavior there, but is strictly more robust either way (see
    that fix's own writeup below)
  - kernel-qemu.ld / the "kernel-qemu.img"/"qemu" Makefile targets are
    ENTIRELY NEW, additive files/targets - kernel.ld and the "all"/
    "kernel.img" targets are completely unchanged, byte-for-byte
    identical Makefile rules to before this session

Bug 1 (real, fixed): "CC := gcc" ignored the ARMGNU cross-toolchain prefix entirely
----------------------------------------------------------------------------------------
The Makefile's own $(ARMGNU)-as/-ld/-objcopy/-objdump rules all
correctly used the ARMGNU prefix - but CC was hardcoded to plain "gcc"
(the HOST compiler), with no prefix at all. A build invoked with just
"ARMGNU=arm-linux-gnueabihf" (no separate CC=... override) would
silently try to compile ARM kernel code with the native x86_64/aarch64
host compiler - never producing valid ARM code. Fixed to
"CC := $(ARMGNU)-gcc". Purely a build-system correctness fix; the
default ARMGNU is still unset (matching upstream), so an explicit
ARMGNU=... is still required either way - this just makes that one
variable now control BOTH the assembler/linker AND the C compiler,
instead of requiring a separate, easy-to-forget CC=... override too.

Bug 2 (real, fixed): -fcommon needed for include/proc.h's "struct cpu cpus[NCPU];"
---------------------------------------------------------------------------------------
Same class of bug documented in every other fork brought up in this
repo by now (GCC 10 flipped the -fcommon default). Fixed by adding
-fcommon to CFLAGS.

Bug 3 (real, fixed, proactive): "-Wa,-march=armv6 -Wa,-mcpu=arm1176jzf-s" only restricts the assembler, not gcc's own codegen target
-------------------------------------------------------------------------------------------------------------------------------------------
Fixed proactively, before actually being hit as a build/link failure -
this is the EXACT SAME flag pattern that caused a real, reproduced
Thumb-switching-BLX crash in the sibling armv6-rpi port under QEMU (see
notes_arch_arm_pi1_bis.txt bug 4) - "-Wa," flags only restrict what the
ASSEMBLER stage accepts, not what gcc's own code generator targets,
which silently falls back to this toolchain's real default
(armv7-a+fp) without an explicit override. Replaced with real gcc-level
"-mcpu=arm1176jzf-s -marm" (CFLAGS only - ASFLAGS isn't used by this
Makefile at all, since it has no separate .S/.s-via-CC rule; the two
hand-written assembly files (entry.s/exception.s/keyboard.s) go through
$(ARMGNU)-as directly, a real, separate assembler invocation with no
codegen-target ambiguity to begin with).

Note: NO "-mfloat-abi=soft" was added here (unlike armv6-rpi's own
otherwise-identical fix) - "-mcpu=arm1176jzf-s" alone already implies
its real VFPv2 unit (confirmed via "readelf -A": Tag_FP_arch VFPv2,
Tag_ABI_VFP_args "VFP registers"), and forcing soft-float would conflict
with the vendored libcsud.a's own prebuilt hard-float ABI ("uses VFP
register arguments, build/output.elf does not" link error) - this
prebuilt library is genuine evidence the real hardware target has always
assumed hard-float/VFP, so keeping it is both correct and necessary.

Dual-target build setup: kernel-qemu.ld / "make qemu"
-------------------------------------------------------
kernel.ld links at physical 0x8000 (AT(0x8000)) - the address real
Raspberry Pi 1 firmware always loads a kernel.img at. Confirmed via the
QEMU monitor's "xp" command that QEMU's "-M raspi1ap" "-kernel" loader
(for a raw binary) places content at physical 0x10000 instead - same
finding as notes_arch_arm_pi1_bis.txt's own bug 5. Rather than changing
kernel.ld itself (which would break real hardware boot), added a
SEPARATE kernel-qemu.ld (identical SECTIONS layout, only the base
address differs: 0x80010000/AT(0x10000)) and new, purely-additive
Makefile targets: "kernel-qemu.img" (links the exact same $(OBJECTS)/
$(C_OBJS) a second time against kernel-qemu.ld) and "qemu" (boots it
under "-M raspi1ap -nographic"). "all"/"$(TARGET)"/"clean" all keep
their original behavior; "clean" was extended (additively) to also
remove the two new qemu-only output files.

Bug 4 (real, fixed): delay()'s exact-equality busy-wait can spin forever under QEMU's timer emulation
-------------------------------------------------------------------------------------------------------------
Once the above got QEMU booting cleanly through the SMC/firmware
handoff with no crash loop, "-d in_asm" showed execution stuck cycling
between delay()/getsystemtime() during uartinit()'s own GPIO pull-up/
down settle delay. source/timer.c's delay() used
"while(t != getsystemtime());" - exact equality against a computed
target tick count. Root-caused by directly recognizing the SAME pattern
already diagnosed and fixed in the user's own Plan 9 kernel for this
exact real hardware family: ~/principia/kernel/COMPILE/9/bcm/clock.c has
a "claude:"-tagged comment on this precise bug ("under emulation (QEMU)
clo can jump by more than 1 between two reads and skip tend, so != would
spin for a full 2^32 counter wrap"), fixed there with a signed
"has-target-been-reached-or-passed" comparison instead of exact match.
Applied the identical pattern here: "while((long long)(getsystemtime()
- t) < 0);". Confirmed via "-d in_asm" that boot now progresses well
past uartinit() into real, varied kernel code (cprintf/panic/console
drawing functions) after this fix - the hang is genuinely gone.

Two console paths, two different QEMU gaps (both open, NOT fixed)
---------------------------------------------------------------------
This kernel writes every console character to BOTH the Mini-UART
(uartputc) and the GPU framebuffer (gpuputc) - source/console.c's own
consolewrite()/cprintf()/etc all call both unconditionally. Neither
produces visible output under QEMU's "-M raspi1ap", for two entirely
separate reasons - confirmed this is not one bug wearing two faces:

  1. Mini-UART (AUX, what uart.c actually configures - GPIO 14/15 in
     ALT5) has NO chardev backend at all under raspi1ap: "info qtree"
     shows "dev: bcm2835-aux, id \"\" ... chardev = \"\"" - genuinely
     empty. Only the separate PL011 UART0 gets wired to "serial0"/
     stdio ("dev: pl011, id \"\" ... chardev = \"serial0\""). This looks
     like a QEMU raspi1ap board-model limitation, not something fixable
     from kernel source - nothing written to the Mini-UART's registers
     is observable via "-serial"/stdio no matter what, though the
     registers themselves are correctly mapped and writable (confirmed:
     "info mtree" shows a real "bcm2835-aux" device at the expected
     physical 0x20215000, matching this driver's own DEVSPACE-mapped
     virtual address exactly).

  2. The GPU framebuffer genuinely never displays anything: a QEMU
     "screendump" (via the monitor, works even under "-display none"
     since the framebuffer memory itself is still emulated) showed a
     completely blank, single-color (pure black) 1024x768 image, even
     after boot had clearly progressed into panic()/cprintf()/
     drawcharacter()/gpuputc() (confirmed executing via "-d in_asm").
     source/console.c's own initframebuf() uses the OLD, simple
     mailbox-channel-1 struct-based framebuffer allocation API (a
     single Msg struct written via writemailbox()/readmailbox()) - NOT
     the modern property-tag protocol (mailbox channel 8, tag-based
     requests like "Allocate Buffer" = 0x00040001). Strong evidence this
     old API is the actual gap: the user's own Plan 9 kernel
     (~/principia/kernel/COMPILE/9/bcm/vcore.c) uses the modern
     property-tag protocol for its own framebuffer setup ("TagFballoc =
     0x00040001") and DOES get a working framebuffer under QEMU's same
     "-M raspi1ap" (confirmed working by the user, both on real hardware
     and under QEMU) - strongly suggesting QEMU's own bcm2835-fb
     mailbox emulation only implements the modern protocol, not the old
     channel-1 struct API this xv6 port still uses. (Separately, Plan
     9's own screen.c has a "claude:"-tagged comment about ONE specific
     LATER mailbox call - screen blanking - tripping QEMU's MMIO
     re-entrancy guard and needing to be skipped under emulation; that
     is a different, narrower issue than the framebuffer-allocation gap
     xv6 hits here, and doesn't block Plan 9's own initial framebuffer
     setup from working.)

Given both gaps are more substantial than a build-flag/address fix -
(1) looks unfixable from kernel source at all (a QEMU board-model
limitation), and (2) would require actually rewriting the mailbox
protocol xv6 uses for framebuffer setup (a real, non-trivial code
change to the primary console path, not just a QEMU-side workaround) -
both were left open per the user's own explicit choice, rather than
attempting the mailbox rewrite this session. The clearest concrete next
step for a future session: port initframebuf() (and whatever else in
mailbox.c the old channel-1 protocol touches) to the modern property-tag
mailbox protocol, using ~/principia/kernel/COMPILE/9/bcm/vcore.c's own
TagFballoc-based implementation as a working reference for the exact
tag layout - this is very likely ALSO safe for real hardware (property
tags have been supported by real Pi firmware for a decade), not just a
QEMU-only fix, so it wouldn't need to be gated/conditional at all.

Bug 4 (real, fixed): no PL011 console output at all - Mini-UART has no QEMU chardev, confirmed via "info qtree"
------------------------------------------------------------------------------------------------------------------------
Same underlying finding as forks/arm/forks/arm-pi3's own bring-ups:
"info qtree" shows "dev: bcm2835-aux ... chardev = \"\"" (empty - no
backend at all) versus "dev: pl011 ... chardev = \"serial0\"" for THIS
board too (raspi1ap, not just raspi2b/raspi3b - confirmed directly, not
assumed). Fixed the same way: added a PL011 driver to source/uart.c
(register offsets at DEVSPACE+0x201xxx, this fork's own existing
KERNBASE-relative peripheral-mapping convention) and folded its
put/get calls directly INTO uartputc()/uartgetc()/miniuartintr()/
enableirqminiuart() rather than adding new call sites - every existing
caller (console.c, consoleintr()) automatically gets both UARTs for

Genuinely UNCONDITIONAL, no #ifdef and no runtime QEMU-detection probe
at all (unlike forks/arm-pi3's own -DRPI3_QEMU split) - two real
findings made this possible: (1) PL011 is a real, always-physically-
present peripheral on this SoC (BCM2835 includes the full IP block
regardless of board), so touching its registers is never unsafe; (2)
confirmed empirically that writing to PL011 does NOT require remuxing
GPIO 14/15 away from ALT5 (Mini-UART, this fork's own real-hardware
pin config) - QEMU's own PL011 model doesn't check GPIO alt-function

so both UARTs work simultaneously through the SAME physical pins
without any pin-muxing conflict. This is exactly the dynamic-over-
static-dispatch pattern asked for this session (see
~/principia/kernel/COMPILE/9/bcm/usbdwc.c's own emulating() for the
general technique) - it just turned out no runtime CHECK was needed at
all, because the underlying operation is unconditionally safe on both
targets.

Bug 5 (real, fixed): gpuputc() writing to an invalid framebuffer pointer, mishandled catastrophically because tvinit() hadn't run yet
-----------------------------------------------------------------------------------------------------------------------------------------------
Root cause of the ACTUAL infinite loop (not the two "no visible
output" theories from Session 1, which turned out to be secondary).
Chased via "-d in_asm"/"-d int" and the QEMU monitor's "xp"/"info
roms": consoleinit() calls initframebuf(), which reports SUCCESS
(fbinfoaddr==0, the only condition this fork's own code checks) even
though fbinfo.fbp (the framebuffer pointer the GPU is supposed to fill
in via the mailbox response) holds a value this kernel cannot draw
through under QEMU - confirmed the mailbox call itself completes (no
hang), just returns a value outside the mapped GPU window. (Session 3
found out exactly why, and it is NOT the "channel 1 isn't implemented"
guess recorded below: QEMU answers correctly, just with a physical
rather than a bus address - see "Bug 7" at the end of this file, which
also fixes it.) gpuputc()'s own
drawpixel() then writes through that bad pointer during the very first
"Hello World" print, at 0x10000ish, and the resulting Data Abort landed
in code that turned out to still be QEMU's own unrelated bootloader ROM
(physical page 0, "info roms" confirms this is where HVECTORS's own
SMALL page mapping points), not this kernel's own trap()/panic()
handler - because tvinit() (which installs the real handler via a
memmove() into HVECTORS) doesn't run until much later in main.c's
cmain(), well after the first cprintf(). One real exception, mishandled
by whatever pre-existing, unrelated code happened to be at the memory
address the (not-yet-installed) vector table pointed to, cascaded into
the observed infinite loop.

Two candidate fixes were tried; the second is what's actually in the
tree:
  - Moving tvinit()/kinit1()/pinit() earlier (before consoleinit()) so
    a real trap()/panic() would at least catch the fault gracefully:
    this DID change the crash signature (confirmed - a genuinely
    different fault pattern appeared, an Undefined Instruction loop
    with stack-pointer-looking addresses near KERNBASE-8), meaning it
    had a real effect, but it exposed a SECOND, separate, unresolved
    bug (something about tvinit()'s own per-mode-stack kalloc() calls
    or the relocated vector table's own position-dependent code) rather
    than reaching output. Reverted rather than compound two open bugs.
  - What's actually in the tree: don't let gpuputc() write through a
    bad pointer in the first place. consoleinit() now sanity-checks
    fbinfo.fbp against the real GPU memory range (GPUMEMBASE..
    GPUMEMBASE+GPUMEMSIZE, this fork's own existing constants) and sets
    a `fb_ready` flag; gpuputc() returns immediately if it's false. On
    real hardware, where the old mailbox API DOES return a real,
    in-range pointer, fb_ready is true and gpuputc()/the framebuffer
    console work exactly as before, completely unchanged - this is a
    genuine runtime validity check, not a QEMU-specific gate, and it
    directly imitates what forks/arm/forks/arm-pi3 effectively do by
    simply not depending on a framebuffer at all.

Also reordered console.c's own gpuputc()/uartputc() call pairs (every
site, consolewrite/printint/cprintf/consputc) to call uartputc() FIRST
- defense in depth, so a character reaches the wire even if something
else about gpuputc() ever misbehaves again in the future.

Bug 6 (real, fixed): PL011 RX/keyboard input wasn't wired up either
------------------------------------------------------------------------
Same fix shape as forks/arm-pi3's own bring-up: enableirqminiuart()
also enables gpuenable[1] bit 25 (PL011's real hardware IRQ, 57 = bank
1 bit 25 - trap.c's own dead enable_intrs() function already had this

concluded input wasn't working at all; switching to '\r' immediately
showed full, correct command execution. forks/arm-pi1/test-xv6.py
(new, see below) sends "\r", not "\n", for exactly this reason.

Bug 7 (real, fixed 2026-09-09): framebuffer never rendered under QEMU - the returned fbp is a PHYSICAL address there, a BUS address on real hardware
--------------------------------------------------------------------------------------------------------------------------------------------------------------
fb_ready (Bug 5) made the CRASH go away by skipping gpuputc(), but left
the framebuffer itself dead under QEMU. A later session found the real
cause, and in doing so proved the Bug 5 write-up's own explanation
WRONG in an instructive way.

That earlier write-up asserted "the old mailbox-channel-1 API this port
uses isn't implemented [under QEMU], so fbinfo.fbp stays whatever it
was set to before the call". That is simply false. Probing it directly
- a temporary patch making the VC alias a variable, looping over all
four aliases (0x40000000/0xC0000000/0x00000000/0x80000000) and
cprintf-ing the reply each time - showed QEMU answering the channel-1
request perfectly, and identically for every alias:

  EXPERIMENT alias=40000000 resp=0 fbp=1c100000 fbs=180000 pitch=800
  EXPERIMENT alias=c0000000 resp=0 fbp=1c100000 fbs=180000 pitch=800
  EXPERIMENT alias=0        resp=0 fbp=1c100000 fbs=180000 pitch=800
  EXPERIMENT alias=80000000 resp=0 fbp=1c100000 fbs=180000 pitch=800

Every field is correct for the requested 1024x768x16: fbs=0x180000 is
exactly 1024*768*2, pitch=0x800 is exactly 1024*2, and resp=0 is the
documented channel-1 success code. So the request side - struct layout,
16-byte alignment, cache flush, bus-address arithmetic, all the things
the previous session had carefully "ruled out" one by one - was never
the problem, and neither was the alias (QEMU accepts any of them).

The actual difference is the FORM of the returned pointer:

  - Real VideoCore firmware returns a VC BUS address (the 0x40000000
    cache alias for this board - matching ~/principia/kernel/COMPILE/9/
    bcm/raspi1.c's own ".busdram = 0x40000000"). That is precisely why
    this fork's mmu.c identity-maps GPUMEMBASE..GPUMEMBASE+GPUMEMSIZE
    (0x40000000..0x80000000) and why the original author could then use
    fbinfo.fbp directly as a CPU pointer with no conversion at all.
  - QEMU's bcm2835-fb model returns a plain ARM PHYSICAL address
    (0x1c100000 on -M raspi1ap: just above the 448MB it gives the ARM,
    inside the GPU's own carve-out - consistent with the "ARM memory is
    0 1c000000" line this kernel already prints at boot).

Nothing in this kernel maps 0x1c100000: mmu.c maps physical
0..RAMSIZE(0xC000000) at KERNBASE, identity-maps only the first 1MB,
maps IO at DEVSPACE, and identity-maps the GPU window at 0x40000000+.
So the QEMU-form pointer was unusable, and the fb_ready range check
(which only accepted the bus-alias form) was right to refuse it.

The fix, in consoleinit(), accepts both forms:

  if(fbinfo.fbp >= GPUMEMBASE && fbinfo.fbp < GPUMEMBASE+GPUMEMSIZE){
    fb_base = fbinfo.fbp;          /* real hw: unchanged, byte for byte */
    fb_ready = 1;
  } else if(... fbinfo.fbp < GPUMEMBASE && fbp+fbs <= GPUMEMSIZE){
    /* QEMU: map it at the same VA real firmware would have returned */
    for(pa = fbinfo.fbp & ~(MBYTE-1); pa < fbinfo.fbp+fbinfo.fbs; pa += MBYTE)
      l1[PDX(GPUMEMBASE + pa)] = pa|DOMAIN0|PDX_AP(K_RW)|SECTION;
    dsb_barrier(); flush_tlb();
    fb_base = GPUMEMBASE + fbinfo.fbp;
    fb_ready = 1;
  }

and drawpixel()/gpuputc()'s two scroll memmove()s now go through
fb_base instead of fbinfo.fbp.

Two details that matter and are easy to get wrong:

  - WHY map at GPUMEMBASE+phys rather than identity-mapping phys.
    switchuvm() in vm.c does "memmove(kpgdir, p->pgdir, PGSIZE)" - it
    copies a process's user page over the FIRST 4KB of the live 16KB L1
    table on every context switch, i.e. it rewrites every L1 entry for
    VA < 0x40000000. An identity mapping of 0x1c100000 lives at L1 index
    0x1c1 = 449, inside that clobbered range, so it would survive
    exactly until the first user process ran. GPUMEMBASE+phys =
    0x5c100000 is at index 1473, in the kernel half, which switchuvm()
    never touches. (The window this fork already identity-maps for the
    GPU is safe for the same reason.)
  - The live L1 table is the one entry.S/mmu.c built at K_PDX_BASE
    (0x4000), reachable as P2V(K_PDX_BASE) - main.c does
    "kpgdir = p2v(K_PDX_BASE)". vm.c's kvmalloc()/setupkvm_new() pair,
    which would rebuild the table from kmap[] (and would NOT include
    the GPU window), is dead code - never called from anywhere.

Real hardware is untouched by this fix: firmware there returns the
bus-address form, which takes the first branch and behaves exactly as
it did before. The second branch can only run where the first one
does not - and where it does run, it strictly replaces "refuse to
draw" with "draw correctly".

Bug 8/Session 4 (2026-09-09): USB keyboard bring-up - real progress, one open failure left
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
The framebuffer is a real output device now (Bug 7), but the QEMU
window was still output-only: input only ever came from the UART
(consoleintr(uartgetc)). This fork ships a USB keyboard path -
source/keyboard.s (Alex Chadwick's input01 sample) plus
UsbInitialise()/KeyboardUpdate()/KeyboardGetChar() declared in
include/defs.h - but nothing had ever called any of it, and the USB
stack was a prebuilt libcsud.a with no source in this tree.

Vendored csud/ (github.com/Chadderz121/csud @ e13b935, MIT, confirmed
to be that exact blob's own source - built from this tree it exports
the same 141 symbols, plus LogPrintF which this fork's own build
resolves itself via source/csud_glue.c) and built it from source
instead, using this kernel's own real ARMv6 codegen flags. Wired
UsbInitialise() into main.c (right after ideinit()) and polled it from
the existing 100Hz timer tick (timer.c's own timer3intr() - CSUD is a
polling driver with no interrupt path of its own).

Getting the HCD to actually initialize and the root hub to attach
needed four separate, real fixes:

  - HCD_DESIGNWARE_BASE (csud/include/configuration.h) and two more
    addresses in csud/source/platform/arm/broadcom2835.c
    (MicroDelay's timestamp register, PowerOnUsb's mailbox) were raw
    ARM PHYSICAL addresses (0x20980000, 0x20003004, 0x2000B880) -
    meaningless under this kernel's own memory map, which only ever
    reaches peripherals through the DEVSPACE=0xFE000000 virtual alias
    (mmu.c's own "map IO region" loop). Relocated to that alias,
    cross-checked byte-for-byte against this fork's own uart.c/
    timer.c/mailbox.h for the identical hardware. Needed on real
    hardware too - not a QEMU-only fix.
  - This kernel never zeroes .bss anywhere - a real, previously-latent,
    kernel-WIDE bug, proven by console.c's own pre-existing "panicked =
    0; // must initialize in code since the compiler does not"
    comment/workaround. CSUD's own zero-initialized globals came up as
    leftover garbage, permanently short-circuiting its own "no device
    yet, scan for one" logic. Fixed with a new bss_start linker symbol
    (kernel.ld/kernel-qemu.ld) and a bsszero() call as the literal
    first thing cmain() does - a universal correctness fix (real
    hardware's own pre-boot RAM contents are just as unpredictable,
    only less consistently reproducible than under emulation).
  - RootHubDeviceNumber (csud/source/hcd/dwc/designware20.c) is
    declared but never assigned anywhere in upstream CSUD - confirmed
    by grepping the whole vendored tree for every WRITE to it (not
    just reads): there are none. HcdSumbitControlMessage's own
    "pipe.Device == RootHubDeviceNumber" dispatch to the virtual
    root-hub handler only matched while the virtual root hub itself
    still had address 0 (true only during its own first couple of
    enumeration steps, which is why HubGetStatus - called once, early
    - succeeded). Every later poll (HubCheckForChange's own repeated
    HubPortGetStatus calls) silently fell through to a REAL bus
    transfer instead, and silently failed against no real device. A
    genuine, pre-existing upstream CSUD bug, not introduced by
    vendoring - fixed by assigning it once in usbd.c's UsbInitialise(),
    right after the root hub's real address becomes known.
  - HubAttach()'s own post-power-on port scan (csud/source/device/
    hub.c) only acts on each port's STICKY "connection changed" bit -
    correct for periodic runtime polling, wrong for a device that was
    already connected from machine start. A "-device usb-kbd" given on
    the QEMU command line is a permanent part of the machine's own
    config, not something the guest ever observes "plugging in" - so
    there is no transition to latch (confirmed directly: reading the
    raw status showed Connected=1, Changed=0, unconditionally, even on
    the very first read). Fixed by also force-attaching whenever a
    port already reads Connected with nothing attached to it yet -
    matching what a real hub driver's initial scan is supposed to do
    on any platform (Linux's own hub_port_init() behaves the same way).

Two genuine emulation-specific gaps, gated behind a new HcdEmulating()
(same technique as ~/principia/kernel/COMPILE/9/bcm/usbdwc.c's own
emulating() - a runtime VendorId read: QEMU's dwc2 reports revision
2.94a where real hardware reports 2.80a):

  - QEMU's dwc2 model doesn't populate GHWCFG2.HighSpeedPhysical, which
    without the gate made HcdInitialise() wrongly reject QEMU's own
    controller as "incompatible hardware".
  - QEMU's mailbox model never answers the legacy "channel 0"
    (power-management) handshake PowerOnUsb() waits on - a real,
    unbounded hang (confirmed via "-d int": zero further interrupt
    activity once stuck there), not a timeout. Skipped entirely under
    emulation (nothing to power-sequence in a QEMU guest).
  - Split-transaction setup is also skipped under emulation (same
    HcdEmulating() gate), matching usbdwc.c's own documented fix for
    the identical underlying QEMU dwc2 gap (no split state machine in
    the model at all).

Bug 9: three more real bugs, found by reading QEMU's own device-model source directly
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
The "Transfer was not acknowledged"/enumeration-stuck failure above was
root-caused, not left open. Fetched QEMU 8.2.2's actual
hw/usb/hcd-dwc2.c (pinned to the exact installed version - see
notes_tutorial_qemu.txt for the general technique) rather than
continuing to guess:

  - HcdChannelInterruptToError() (designware20.c) treats a transfer as
    failed unless the hardware's "Ack" interrupt bit is set. Grepping
    QEMU's ENTIRE dwc2 model for every write to HCINTMSK_ACK found
    none, anywhere in the file - on a successful transfer QEMU only
    ever raises XferCompl + ChHltd; real Broadcom hardware additionally
    raises Ack, which is what this check actually tested for. Skipped
    under HcdEmulating() - Halt, which the driver's own SETUP/DATA/
    STATUS loops already wait on before checking this, still correctly
    reflects real completion either way.
  - HcdChannelSendWait()'s own "packets == PacketCount means the
    transfer got stuck" heuristic misfires for a genuinely-completed
    0-length transfer (the STATUS stage of every control transfer).
    QEMU's own completion arithmetic (dwc2_handle_packet(): "tpcnt =
    actual/mps; pcnt -= min(tpcnt,pcnt)") computes tpcnt=0 for
    actual==0, so PacketCount is written back UNCHANGED even though the
    transfer did complete (QEMU separately flags it done via its own
    "actual == 0" check - confirmed the transfer itself succeeded via
    HcdChannelSendWaitOne's own return value). Skipped for
    bufferLength==0 under HcdEmulating() - the same class of gap as
    Principia's own usbdwc.c "0-length transfer Pktcnt not decremented"
    writeup, independently rediscovered here for a different driver.
  - HubAttach()'s own PowerSwitchingMode switch statement (hub.c) only
    handles Global(0)/Individual(1) and rejects everything else as
    "Driver incompatible" - QEMU's emulated hub reports mode 2 ("no
    power switching - always on"), a real, spec-defined value (USB 2.0
    sec 11.23.2.1), not a QEMU quirk. Added the missing case,
    unconditionally (not gated on HcdEmulating() - a real hub could
    report this too).

With those three, the emulated hub AND keyboard both fully enumerate
("Device Attached: USB 1.1 Hub" / "... HID Keyboard").

Bug 10: two more bugs found only once real keystrokes were tested (not just log lines)
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
Enumeration succeeding is not the same as input working. Verified with
real injected keystrokes via QMP's send-key against the emulated USB
HID device (see notes_tutorial_qemu.txt) rather than trusting the log:

  - A held key produced a long run of identical characters
    ("llllll..."). Confirmed via HidReadDevice's own built-in raw-report
    dump hook (csud/source/device/hid/hid.c's pre-existing, previously
    commented-out "quick hack to view 8 bytes worth of report") that
    the underlying USB HID report was completely clean - a single,
    correct press-then-release transition, not a stuck/repeating report
    at the hardware level. The bug is in CSUD's own KeyboardGetChar()/
    KeyWasDown() repeat-suppression (keyboard.s, hand-written ARM
    assembly) failing to actually suppress in practice. Rather than
    debug that state machine further, fixed at the glue layer instead:
    source/timer.c's usbkbdgetc() now refuses to emit the same
    character on two consecutive polls in a row (a genuine repeat needs
    a real "key up" - KeyboardGetChar() returning 0 - in between).
  - Enter produced no output at all. source/keyboard.s's own
    KeysNormal/KeysShift tables map the Enter key to '\n' (0x0a) - a
    reasonable, standard USB-keyboard-driver choice in isolation, but
    this kernel's own consoleintr() explicitly discards a raw '\n' and
    only treats '\r' (0x0d) as "submit line" (the same real
    serial-terminal convention already documented for the UART path
    earlier in this file - not a new rule, just a second input path
    that also needed to honor it). Translated '\n' -> '\r' in
    usbkbdgetc() specifically - not in keyboard.s (would be the wrong
    fix for any other hypothetical caller expecting standard ASCII) and
    not in consoleintr() itself (shared with the UART path, already
    correct there).
