Debugging techniques, written up as they get used
=================================================

Notes on *how* problems in this repo were tracked down, as opposed to what
they were - see docs/claude_notes/notes_arch_*.txt for the actual bugs and
findings per port. Update this file when a technique earns its place from
real use, not with a narrative of any specific investigation.

1. Triage a -Werror failure before touching any flag: false positive, or real bug?
------------------------------------------------------------------------------------
These ports were written 2006-2023 and are now compiled with GCC 12-13.
Every one of them builds with `-Wall -Werror`, so a warning GCC added
*after* a file was last touched becomes an unconditional build failure,
indistinguishable at first glance from a real bug in 20-year-old code.
Before reaching for a fix, form a concrete hypothesis about which case it
is:

- Read the GCC diagnostic itself for a warning name added recently
  relative to the code's age (`-Warray-bounds` strengthened in GCC 10,
  `-Winfinite-recursion` added in GCC 12 - both hit forks/i386's and
  forks/x86_64's Makefiles this session, see notes_arch_i386.txt).
  A warning about pointer arithmetic on a raw physical address, or about
  a recursive-descent parser/interpreter that obviously terminates via
  exec()/exit() in its base case, is a strong prior for "heuristic false
  positive" - GCC's static analysis can't see the runtime property that
  makes it safe.
- Confirm empirically before suppressing: does the code actually work
  once built anyway? For mp.c's -Warray-bounds, that meant confirming
  mpinit() actually enumerates the second CPU under `-smp 2`; for sh.c's
  -Winfinite-recursion, that meant confirming the shell runs pipelines/
  redirection/command lists correctly throughout a real usertests run.
  Never suppress a warning on the strength of "it's probably fine."
- Fix by adding the single, precisely-named `-Wno-<warning>` flag, not a
  blanket `-Wno-error` or a rewrite of the flagged code - see forks/i386/
  Makefile's and forks/x86_64/Makefile's own `-Wno-array-bounds`/
  `-Wno-infinite-recursion` additions, each with a `claude:`-tagged
  comment naming the exact GCC version and the confirming evidence. A
  real new bug in this code would still be caught by every OTHER warning
  in -Wall.
- If the failure is instead a genuine crash, wrong-answer, or an
  assertion inside a build-time host tool (not a compiler warning at
  all), that's technique 2 below, not this one.

2. Read the assertion/error message and compute the actual numbers before guessing
--------------------------------------------------------------------------------------
forks/x86_64's mkfs aborted with `tools/mkfs.c:268: iappend: Assertion
`fbn < MAXFILE' failed` while packing fs.img. Two minutes of reading turned
that into three concrete, checkable numbers instead of a vague "the build
is broken":

  MAXFILE = NDIRECT + NINDIRECT = 10 + (512/4) = 138 blocks
  138 * BSIZE(512) = 70656 bytes  <- largest file this fs can hold
  actual `usertests` binary size = 79728 bytes  <- confirmed via `ls -la .fs/`

That single comparison identified the exact fix needed (more headroom in
MAXFILE*BSIZE) and, just as importantly, which fix was safe: doubling
BSIZE (multiplying the NINDIRECT term) rather than raising NDIRECT
(which would also grow struct dinode and need re-deriving IPB/inode-block
counts) - see notes_arch_amd64_jserv.txt for the full reasoning and the
cross-check against forks/riscv64/kernel/fs.h's own BSIZE=1024 precedent.
The general lesson: an assertion failure names a file and a line for a
reason - compute the real values on both sides of the failing condition
before forming a hypothesis about the fix.

3. A hung/silent QEMU boot: use gdb-multiarch against QEMU's own -gdb stub, then correlate the PC against the kernel's own objdump+symbols
------------------------------------------------------------------------------------------------------------------------------------------------
forks/x86_64 booted (SeaBIOS, ACPI CPU enumeration, "cpuN: starting")
but then produced zero further console output, indefinitely, under both
`-smp 1` and `-smp 2`. Guessing at the cause (timer? APIC? scheduler?)
from the symptom alone would have been slow. Instead:

  qemu-system-x86_64 ... -gdb tcp::12399 &   # -S not even needed - it
                                              # was already stuck
  gdb-multiarch -batch \
    -ex "set architecture i386:x86-64" \
    -ex "target remote localhost:12399" \
    -ex "info registers rip rsp rbp" -ex "x/3i \$pc" -ex "bt"

This gives a real, if symbol-less (no `file` loaded), instruction
pointer and backtrace immediately. The next step is mechanical, not
guesswork: grep that exact address against the kernel's own
`out/kernel.asm` (every fork's Makefile already generates this via
`objdump -S kernel` as part of the normal build - see e.g. forks/x86_64/
Makefile's `$(OUT)/kernel.elf` rule) to find which function and even
which source line the address falls inside, then read the surrounding
disassembly to see the actual control flow at that point. This
immediately turned "silently hung, no idea where" into "sitting right
after a `hlt` instruction inside scheduler()'s own documented idle-wait
path (`if no runnable process, hlt() until the next interrupt`)" -
reframing the question from "where is it stuck" (answered) to "why does
this specific hlt() never get woken back up" (the real remaining
question - see notes_arch_amd64_jserv.txt for how that was run down).

`gdb-multiarch` (not the host's plain `gdb`) is required on a non-x86
host - confirmed plain `gdb`'s `set architecture i386:x86-64` fails with
"Undefined item" when gdb wasn't built with multi-arch support, while
`gdb-multiarch` (already installed on this box; `sudo apt install
gdb-multiarch` otherwise) accepts it immediately. No `TOOLPREFIX`-style
cross-gdb (e.g. `x86_64-linux-gnu-gdb`) is needed or was installed -
`gdb-multiarch` covers every target this repo's ports build for.

4. Don't trust a same-named tool's version-parsing output without checking `which -a` first
-------------------------------------------------------------------------------------------------
./configure's own qemu-version check (`sed -E`, later rewritten - see
below) failed inexplicably on this machine: `sed: Unknown flag: E`, then
a `bc` "Illegal number: stdin:1 syntax error" on what should have been a
trivial numeric comparison. `which -a sed` and `which -a bc` immediately
showed the cause: `~/goken`'s own build had prepended
`~/goken/ROOT/arch/boot-gcc/bin` onto PATH, and that directory holds
goken's own self-built, minimal `sed`/`bc` binaries (confirmed via
`file`: real aarch64 ELF binaries, not the expected GNU coreutils) which
silently do the wrong thing for `-E`/bare boolean expressions instead of
erroring loudly. `which -a <tool>` (not just `which`, which only shows
the first match) is the fast way to notice a same-named-but-different
tool earlier on PATH before spending time debugging what looks like a
logic bug in your own script. The more robust fix generalizes beyond
this one host: avoid depending on GNU-specific `sed -E`/`bc` behavior at
all when a pure POSIX-shell equivalent exists (parameter expansion +
integer `[ -ge ]` comparisons) - see ./configure's own
detect_qemu_system function and notes_arch_riscv64.txt's "PATH hazard"
section for the full before/after.

5. A captured (non-tty) log's per-line timestamps can be misleading - Python's stdout is block-buffered when piped
----------------------------------------------------------------------------------------------------------------------
Reading a `docker build` log (or any captured `make`/subprocess output),
a `test-xv6.py`-style script's `print()` calls appear to happen all at
once, at whatever moment the process actually exits or its buffer fills
- NOT incrementally as the lines were produced in real time. This showed
up concretely: a captured log had two "ALL TESTS PASSED" lines and a
wrapping "usertests: ALL TESTS PASSED" line all stamped with the exact
same cumulative timestamp, which briefly looked like it implied a
per-arch timing breakdown that later turned out to be an artifact of
buffering, not real elapsed time. Don't compute per-step durations from
timestamps inside a single buffered stream; if real timing matters,
either force line-buffering (`python3 -u`, or `print(..., flush=True)`)
or measure wall-clock time around the whole subprocess from outside
instead.

6. Verify a Docker/CI change locally, with the exact matrix arguments CI will use, before pushing
-------------------------------------------------------------------------------------------------------
When the Dockerfile grew an `ARCH` build-arg so CI could run one job per
arch in parallel, `docker build --build-arg ARCH=riscv64 .` was run
locally first, before touching docker.yml's matrix or pushing anything.
That single local run caught a real bug that would otherwise have only
surfaced as a confusing CI failure: `python3` had never actually been
installed by this Dockerfile - it only "worked" by accident, riding
along as a transitive Recommends of qemu-system-gui's GTK/desktop stack
(python3-gi, python3-dbus), which `--no-install-recommends` (added in
the same change, for an unrelated size/speed reason) then removed. A
second local run with `ARCH=i386` caught a too-tight test timeout the
same way (see notes_arch_i386.txt's TIMEOUT note) - a real, reproducible
failure on this machine with no other load, not a CI-runner-specific
flake, exactly the kind of thing worth catching before spending a CI
run's wall-clock time (and, on this project, the reviewer's patience)
on it. A third example, `ARCH=arm` (forks/armv7-rpi): the fork's own
"qemu" Makefile target ran a bare `clear` before starting QEMU, which
had worked in every interactive terminal session this port was ever
tested from - but `clear` exits non-zero with no `TERM` set, which is
exactly the environment a Docker build runs in, and a plain `@` on a
make recipe line silences echoing the command, not its exit-status
handling, so the whole recipe aborted before QEMU ever started. A
fourth, `ARCH=arm64` (forks/arm64): `qemu-system-aarch64` refused to
boot at all - "failed to find romfile efi-virtio.rom" - because
`ipxe-qemu` (which ships that ROM, needed for the `virtio-blk-device`
this fork's own Makefile passes, even though no firmware/EFI code ever
actually runs) is only a Recommends of `qemu-system-arm`, stripped by
the same `--no-install-recommends` this Dockerfile uses for image-size
reasons - identical shape to the very first python3 example, just a
different package pulled in by a different Recommends chain. A fifth
and sixth, both `ARCH=mips`: `libc6-dev-mipsel-cross` (cross-compiled
libc headers, only a Recommends of `gcc-mipsel-linux-gnu`) and, once
past that, TWO more missing option ROMs at once (`efi-pcnet.rom` for
QEMU malta's emulated NIC, `vgabios-cirrus.bin` for its emulated VGA
card, from `ipxe-qemu` and `seabios` respectively, both Recommends of
`qemu-system-mips`) - this board model wires up a whole legacy PC-
compatible peripheral set regardless of whether the kernel's own
drivers ever touch most of it, so QEMU refuses to boot at all without
ROMs for hardware this specific kernel never even talks to. The general
pattern across all six: a real terminal's environment (TERM set,
Recommends-pulled packages present, a fast unloaded machine) quietly
supplies things a Docker/CI environment does not, and the gap only
shows up once something actually runs without that scaffolding - which
is precisely why running the container locally, not just reading the
Dockerfile, is the useful step. Worth checking, specifically, whenever
`--no-install-recommends` (or an equivalent minimal-install flag) is in
play: grep `apt-cache depends <package>` for `Recommends:` entries
before assuming the Depends line alone tells you what a package
actually needs at runtime - and expect to need more than one pass: each
of these six was only found because fixing the previous one let the
build get further and hit the next.

7. When a fork's Makefile has an unusual pattern, check whether its siblings share it
------------------------------------------------------------------------------------------
forks/riscv64, forks/i386, and forks/x86_64 all descend from the same MIT
lineage (see the root README's fork-point table) and, unsurprisingly,
share near-identical `TOOLPREFIX`/`QEMU` auto-detect blocks and the same
`sh.c`/`usertests.c` heritage. A gap or bug found in one - forks/i386's
missing `i686-linux-gnu-` candidate in its own TOOLPREFIX probe, or the
`-Winfinite-recursion` false positive in its `sh.c` - was worth checking
in its siblings immediately rather than waiting to rediscover it
independently during that arch's own bring-up: forks/x86_64 turned out
to share the exact same sh.c-derived bug (fixed the same way, see
notes_arch_amd64_jserv.txt), while forks/riscv64's own kernel/fs.h had already
independently solved the same class of problem forks/x86_64 hit
(MAXFILE headroom) by using a bigger BSIZE - a precedent worth searching
for and citing rather than re-deriving the fix from first principles.

8. gdb-multiarch against QEMU's -gdb stub: don't trust an argument display at a breakpoint on a function's opening brace
--------------------------------------------------------------------------------------------------------------------------------
See docs/claude_notes/notes_tutorial_gdb_multiarch.txt for the full
worked tutorial (real command sequences, real output) this technique is
drawn from - this entry is just the one-paragraph version for a fast
re-read. Setting `break <function>` with no explicit line stops at that
function's opening `{`, before its prologue has necessarily spilled
register arguments to the stack slots the debug info assumes for them.
This session hit a real disagreement: GDB's own frame-printed argument
(`chan=0x...`) did not match a direct `print/x $rdi` read at the exact
same stop, and the register read was the correct one (confirmed against
an independently-known-good address moments later). When an argument
value looks implausible right at a function's entry breakpoint, read the
raw SysV argument register directly (`$rdi`/`$rsi`/`$rdx`/`$rcx`/`$r8`/
`$r9` for the first six integer/pointer args) rather than trusting the
pretty-printed frame arguments.

9. Check state AFTER the code that's supposed to change it has actually run, not just near it
----------------------------------------------------------------------------------------------------
A related gdb-multiarch gotcha from the same session (see
notes_tutorial_gdb_multiarch.txt's own case study 5): breaking on
`wakeup()` and reading a process's state at that same stop - i.e. at
`wakeup()`'s own opening brace, before its body has executed - makes it
look like the call had no effect, since the state genuinely hasn't
changed *yet*. This isn't evidence a fix failed; it's evidence of
checking at the wrong instant. Use `finish` (run until the current
function returns) or move the breakpoint to a point past the relevant
mutation before concluding anything from the state you read.

10. `pkill -f`/`pgrep -f` can match this very tool call's own wrapper shell - use the bare name instead
------------------------------------------------------------------------------------------------------------
`pkill -f <pattern>` matches a process's *entire command line*, not just
the target binary. In this harness, every shell command runs inside a
wrapper (`bash -c "... eval '<your whole multi-line script>' ..."`) whose
own argv contains the literal text of the script being run. If that
script's own text contains the same `<pattern>` you're killing (which it
almost always does - you just typed the target's name in the `pkill`
line itself, in the same script), `pkill -f` matches and kills that
wrapper process, silently aborting the entire tool call with no output
at all: no error message, no partial stdout, just an opaque "Exit code
1" (or 137) and every subsequent `;`-separated command in the same call
lost. This cost a long stretch of apparently-inexplicable silent
failures during rv32 bring-up (`pkill -9 -f qemu-system-riscv32 ...`
immediately followed by nothing, even a plain `echo` after it). Fix:
avoid `-f` when the plain process name is enough (`pkill -9
<15-char-or-shorter-name>`), or when the name is truncated/too long for
non-`-f` matching (as `qemu-system-riscv32` is, at 20 characters), filter
`ps -eo pid,comm` yourself instead: `ps -eo pid,comm | awk
'$2 ~ /qemu-system-r/{print $1}' | xargs -r kill -9` - `comm` is the
kernel's own short process name for the *target*, and never contains
your wrapper shell's own command-line text.

11. QEMU's own `-d int,guest_errors -D <file>` beats guessing from gdb's CSR reads when a trap is looping
------------------------------------------------------------------------------------------------------------
When a kernel is stuck retaking the same trap forever (a boot hang that
never advances), attaching gdb-multiarch and reading `$mepc`/`$mcause`/
`$priv` convention registers is one option, but those reads go through
the target's remote-protocol register map, and for less-common
architectures/register sets that map can be incomplete or stale in ways
that are hard to distinguish from a real, reproducible finding (this
happened during rv32 bring-up: gdb's `$mepc` looked consistent across
independent samples, which read as "real" until QEMU's own trace flatly
confirmed it). QEMU itself will log every trap it takes, authoritatively,
with `-d int,guest_errors -D /path/to/file`: each line names the real
`cause`, whether it's `async` (interrupt) or synchronous (exception),
the real `epc`, and `tval`. Grepping that log's *first* occurrence (not
just the repeating tail) confirmed a genuine, 100%-reproducible
"fault_fetch" exception on every single execution of a specific `mret`,
which is what led to the missing-PMP-setup fix (see
notes_arch_riscv32.txt). Reach for this whenever a trap is looping and the
question is "what does the hardware actually think is happening", not
"what does my mental model predict" - it also gives an instant node
count (`wc -l` on the trace) that quantifies just how tight the loop is.

12. A struct copied from a 64-bit sibling port needs its on-disk/on-wire layout re-verified, not just its field types
--------------------------------------------------------------------------------------------------------------------------
Changing `uint64` fields to `uint32` in a struct ported from a 64-bit
sibling fixes the obvious problem (field width) but not necessarily a
more subtle one: some ELF64 structures have a genuinely *different field
order* from their ELF32 counterparts, not just different field widths.
`Elf64_Phdr` is `type, flags, offset, vaddr, paddr, filesz, memsz,
align`; `Elf32_Phdr` is `type, offset, vaddr, paddr, filesz, memsz,
flags, align` - `flags` moves from second to second-to-last. rv32's
`kernel/elf.h` had dropped `flags` entirely (with a comment claiming it
"not in 32 bit ELF!" - wrong; it's in ELF32 too, just relocated), making
`sizeof(struct proghdr)` 4 bytes short of the real on-disk stride. The
first program header read fine anyway (its own fields all landed right,
since the missing field is at the very end); every subsequent one, in a
loop that advances the file offset by `sizeof(ph)` per iteration, read
completely scrambled. The tell: instrumenting each phdr-processing step
with a `printf` showed the very first LOAD segment's iteration produce
no output at all (silently misclassified as a non-LOAD type from
garbled field values) while the second produced a `filesz` that plainly
contradicted `readelf -l`'s own report for that same binary. When a
struct is ported from a 64-bit sibling, cross-check its *field order*
against the real on-disk/on-wire format for the 32-bit case specifically
(a working 32-bit sibling fork's own copy of the same struct, if one
exists in the repo, settles it fastest - forks/i386's `elf.h` had the
correct ELF32 layout all along).

13. A linker script gap on one sibling fork can be invisible until a later pipeline stage
------------------------------------------------------------------------------------------------
forks/riscv64 (rv64) links user programs with a dedicated `user/user.ld`
that explicitly page-aligns `.data` after `.text`
(`. = ALIGN(0x1000);`); forks/riscv32 instead used a bare `-N -e main
-Ttext 0`, which packs sections with no such alignment. Both link
*successfully* - the gap only became visible three steps later, at
runtime, when this kernel's own `exec()` rejected the resulting
non-page-aligned second `PT_LOAD` segment (`ph.vaddr % PGSIZE != 0`).
Nothing in the build itself (compiler, assembler, linker, even `readelf`
run without comparison) flags this as wrong - `-N` binaries with
back-to-back unaligned segments are perfectly valid ELF, just not valid
input to *this specific* `exec()`'s stricter check. When a fork is
missing a convention a sibling has (a linker script, a CSR setup step,
an extra build flag), check whether the missing piece is load-bearing by
looking at what *consumes* its output downstream, not just whether the
producing step itself succeeds.

14. When a diagnostic printf's own output looks impossible, suspect the print, and verify with gdb before chasing it
--------------------------------------------------------------------------------------------------------------------------
During arm64's bring-up, `usertrap()`'s own "unexpected ec" print
always showed `0x0`, which looked like it might mean "this was really a
misrouted interrupt, not a real synchronous exception" (interrupts don't
populate ESR_EL1 the same way). The real explanation was mundane: the
function reads ESR_EL1 into a local `ec` a few lines earlier, then
immediately writes 0 back into the register (`w_esr_el1(0)`) - so the
diagnostic printf's own *second* read of the same register, later, could
only ever print 0, regardless of what the real value had been. This was
a real bug (in the print, not the crash), and it would have sent the
investigation in a wrong direction (chasing an interrupt-routing theory)
if trusted at face value. Caught by printing the *local variable*
(captured before the clear) instead of re-reading the register - still
0, which is what finally confirmed the exception class itself really was
the anomaly, not the print. Separately on the same investigation: a
custom `printf("...%x...", some_uint32_t)` call produced values that
didn't match a same-moment `gdb` read of the identical C variable at a
`nop` placed right after the call - not a variadic width bug here (this
kernel's own `%x` and the caller's `uint32_t` argument agreed at 32
bits), but enough of a discrepancy on the first pass to burn real time
second-guessing the print instead of the underlying data. General rule:
when a print's output contradicts everything else you know to be true,
verify the *same value* via `gdb print` (of the actual variable, or of a
`copyin`-style probe result stored somewhere gdb can read it directly)
before spending more time reasoning about what the printed number could
mean - a homegrown kernel `printf`/`vprintf` is exactly the kind of code
most likely to have its own quiet bugs, especially in a 15-20-year-old
freestanding codebase never exercised against every format specifier
combination.

15. A crash at the same call site across two unrelated forks is a hypothesis, not yet a conclusion - but worth writing down either way
------------------------------------------------------------------------------------------------------------------------------------------------
riscv32's still-open "bug 4" and arm64's still-open "bug 1" (see both
forks' own notes_arch_*.txt) both crash a freshly-exec'd `sh` shortly
after its first prompt, inside or immediately around the very first
`memset()` call in `getcmd()` - two ports from different original
authors, different years, different ISAs, with no shared code for this
specific bug to live in (each has its own independently-written
kernel/exec.c, trap handling, etc.). This might be pure coincidence
(getcmd() is genuinely the first non-trivial thing any shell does after
its prompt, so it's an unsurprising place for ANY bug to first surface,
unrelated to what the bug actually is in each case) - but it's the kind
of pattern that's cheap to write down and expensive to silently miss.
When a second unrelated port hits a symptom that rhymes with an already-
documented open bug on a sibling, note the resemblance explicitly in
that port's own notes_arch_*.txt (even before knowing whether it's the
same root cause) - if a THIRD port in the same lineage repeats it, that
upgrades the pattern from "interesting coincidence" to "go looking for a
shared root cause in the common ancestor code" rather than re-diagnosing
each one from scratch.

16. QEMU's own `info mtree` monitor command is authoritative for "what's really at this address" - but you still have to read its output carefully, line by line, not skim it
--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
When a kernel hangs polling a device that should respond, or writes to
something that seems to have no effect, the fastest way to settle "is
this address even right" is to ask QEMU directly rather than cross-
checking against documentation, source comments, or the port's own
(possibly stale) assumptions. Start QEMU halted with an extra monitor
endpoint - `-S -monitor unix:/path/to/sock,server,nowait` (a Unix
socket is easier to script against than the interactive `-monitor
stdio` this repo's forks' own Makefiles use) - then, from a second
shell, `echo "info mtree" | nc -U /path/to/sock` (`nc`, not `socat`,
if the latter isn't installed - both work). This prints the *actual*,
live physical memory map: every device's real base address and size,
organized by which internal bus/address-space it lives in, straight
from QEMU's own device model. This is the same class of technique as
item 11's `-d int,guest_errors` trace (ask the emulator directly
instead of reasoning from source), applied to address-space layout
instead of trap/exception history - reach for `info mtree` specifically
when the question is "where does this address actually land", and item
11's trace when the question is "what trap did the CPU actually take".

During mips bring-up this immediately showed `0x14000000` (what the
kernel's own `io_port_base` assumed was the legacy PCI/ISA I/O window)
actually belongs to the GT64120 system controller's PCI config-space
registers, an unrelated device - real progress, `info mtree` did its
job. But the FIX drawn from that same output was itself wrong, and
stayed wrong across an entire subsequent bring-up session: the real
line was

  0000000010000000-0000000017ffffff (prio 0, i/o): alias pci0-mem0 @pci0-mem ...
  0000000018000000-00000000181fffff (prio 0, i/o): alias pci0-io @io ...

and the fix taken at the time was `0x10000000` (`pci0-mem0` - PCI
*memory* space) instead of the actually-correct `0x18000000`
(`pci0-io` - PCI *I/O* space, two lines down, a different address
space entirely despite the very similar-looking label). Writing/
reading through the wrong-but-real window doesn't fault or show up in
`-d guest_errors` (it's backed memory, just the wrong kind), so the
original symptom (an `ideinit()` busy-wait hang) genuinely went away -
enough surface-level improvement to make the fix look validated - while
the real bug (a UART that produced zero console output) persisted for
an entire separate investigation, root-caused only when a *later*
session re-ran `info mtree` and read the two adjacent alias lines
properly, then cross-checked with a direct register readback (`xp` on
the live UART's IIR at the candidate address, see item 18 below) rather
than trusting the mtree line alone a second time. The tool was right
both times; only the reading of it was careless the first time. Worth
remembering: `info mtree`'s output rewards a careful line-by-line read,
not a skim for the first plausible-looking alias - two adjacent regions
with near-identical labels (`pci0-mem0` vs `pci0-io`) are exactly the
shape of mistake that's easy to make once and then re-derive fixes on
top of for a long time before anyone re-checks the original evidence.

17. When "no console output" survives every kernel-code check, rule out the *host-side capture path* by reading a raw pty directly, not `-nographic`'s stdio multiplexing
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
A kernel that provably reaches `outb(port, c)` with the right port and
the right byte (confirmed via gdb, single-stepped past the actual store
instruction) but still produces zero visible characters has two very
different possible explanations left: the emulated device isn't
actually the one the byte lands on (a guest/device-model bug), or
something about how the *host* is capturing QEMU's output is eating it
(a test-harness bug). `-nographic`/`-serial stdio` funnels output
through QEMU's own terminal-raw-mode handling, which behaves
differently depending on whether the process's stdio is a real
interactive tty versus a pipe/redirect (exactly the situation a Bash
tool's backgrounded, piped invocations are in) - so "nothing arrived on
stdio" is genuinely ambiguous between the two explanations as long as
stdio is the only thing being read.

Settle it by bypassing stdio entirely: `-display none -chardev
pty,id=cm -serial chardev:cm` makes QEMU allocate a real host pty and
print its path (`char device redirected to /dev/pts/N`) at startup;
`cat /dev/pts/N` (or write to it, for input) talks to the guest UART
through an ordinary tty device node, independent of whatever redirected
QEMU's own stdout/stdin. If bytes still never show up here, the guest-
side/device-model explanation is confirmed and stdio-capture concerns
can be dropped entirely - during mips bring-up this is exactly what
happened (still zero bytes on a raw pty), which redirected the ongoing
"bug 5" investigation away from a suspected QEMU-invocation artifact
and back toward the emulated hardware/kernel-code path itself. Also
worth cross-checking with `info chardev` in this situation: it lists
every chardev QEMU actually instantiated and each one's real backend
(`filename=stdio`, `filename=null`, `filename=vc`, ...) - a `vc`
(virtual-console) backend needs a graphical `-display` to ever be
visible, so a device wired to one will look identical to "getting no
output" under `-nographic` even if the guest is writing to it
correctly.

18. When a repeating exception loop's "what got read/written" is ambiguous from a trace alone, decode the raw bytes at the fault address via the QEMU monitor's `xp`
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
`-d int,guest_errors` gives the fault type and address (DFAR/IFAR) but
not what's actually *there* - during armv6-rpi bring-up, a repeating
Data Abort at a suspicious-looking address (`0x800103cc`, matching the
kernel's own KERNBASE offset) turned out to be readable directly: `echo
"xp/8xw 0x103c0" | nc -U /path/to/monitor.sock` (a plain TCP/unix
monitor, no `-S` needed if the loop is steady-state - any snapshot mid-
loop shows the same state) dumped the raw words at that physical
address, and decoding them by hand as little-endian bytes spelled out an
exact string literal from the kernel's own source
(`"..............\nBoot starting...\n"`, from a `_puts()` call) - proving
in one step that the fault was a compiler-generated absolute-address
load for that literal, not a hardware/MMIO issue. The same technique
resolves "is this virtual address actually mapped" questions directly:
compute the PDX/PTX table index by hand from the fault address and the
port's own `mmu.h`-style shift/mask macros, then `xp` the physical
address of that specific page-table slot - a zero (or unexpected) value
there is direct proof of a missing/wrong mapping, no guessing from
symptoms required. This is the same "ask the emulator directly" family
as items 11/16, applied to arbitrary physical memory content instead of
trap history or the address-space layout.

19. A second, unrelated OS/kernel targeting the exact same real hardware is a strong cross-check for "is this sequence of boot steps actually correct"
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
When a from-scratch ARM/MMU boot sequence (disable MMU, zero page
tables, build mappings, enable MMU, switch to the high/KZERO address
space, only then call into C) is suspected of doing something in the
wrong order, a same-repo reference in another architecture's own port
doesn't help - but a genuinely independent, already-hardware-verified
kernel targeting the SAME physical board is excellent ground truth, if
one happens to be available (in this case `~/principia/kernel/COMPILE/
9/bcm/startv6.s`, a Plan 9 port for the same arm1176jzf-s/BCM2835
hardware this session's xv6 port targets, tested on both QEMU and real
Raspberry Pi 1 hardware). Comparing xv6-armv6-rpi's own boot sequence
against it immediately confirmed a real bug by omission: the working
Plan 9 version does no printing of any kind before its own MMU-enable-
and-KZERO-switch step; the xv6 port had one stray early debug print left
active (with every LATER debug print in the same function already
commented out by a previous maintainer - itself a clue the author had
already run into some version of this same problem and partially, not
fully, worked around it). Worth remembering as a search strategy: when
debugging a from-scratch boot sequence for real, well-documented
hardware, check whether the user (or the wider ecosystem) has any other
kernel already working on that exact board - the actual instruction
ORDER of a working reference is often more reliable evidence than
reasoning about ARM/MMU semantics from the architecture manual alone.

20. A breakpoint that should fire but never does is itself the finding - it means the assumed code path is wrong, not that the breakpoint is broken
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
forks/riscv32's bug 4 (see notes_arch_riscv32.txt) looked, from the crash
alone, like register corruption: a shell's memset() call received
completely wrong arguments, and every register-preservation path that
could plausibly explain it (the trapframe struct's field layout, the
trampoline.S save/restore offsets, the callee-saved-register discipline
of the intervening fprintf()/vprintf() calls) had already been checked
by hand, field by field, and matched. Rather than keep re-deriving the
call chain from static disassembly, a gdb-multiarch session was
attached to QEMU's own gdbstub (`qemu-system-riscv32 ... -S -gdb
tcp::1234`, then `target remote localhost:1234` with `set architecture
riscv:rv32`) and a hardware breakpoint (`hbreak`, not `break` - avoids
ever writing to guest memory, so there's no risk of corrupting a
not-yet-mapped or read-only page, a real hazard software breakpoints
have in a system with per-process page tables) was set at the user
virtual address of the ONE call site that could reach the crashing
function.

It never fired - not once in a run where the console was visibly
printing the exact prompt that call site's callee produces. The
instinct at that point should be to suspect the breakpoint mechanism
itself (wrong address, wrong architecture setting, gdbstub flakiness) -
worth ruling out ONCE, cheaply, by setting a second hbreak at a kernel
address known to execute constantly (any frequently-hit printf call
site) and confirming it fires immediately. Once that sanity check
passes, a breakpoint that still never fires at an address the source
code says must be reached is strong, direct evidence that execution
never reaches that address at all - i.e., that the real code path
differs from what the disassembly of the file you're reading implies
about what actually runs. Here that pointed straight at `readelf -h`/
`nm` on the actual built binary, which showed the ELF's own entry point
was a completely different, unexpected function - a two-command
diagnosis that a register-corruption theory would never have reached,
however carefully pursued.

21. A gdbstub connection negotiated for the wrong architecture doesn't just fail to break - it can corrupt the guest and mislead you into thinking the code is looping
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
forks/arm-pi3's bring-up (notes_arch_arm_pi3.txt) needed to debug a
32-bit ARM kernel running under `qemu-system-aarch64`, whose gdbstub
negotiates its INITIAL register-set width (AArch64's 268-byte one, on
this mixed-mode CPU) at connect time, before the guest has even
executed its first instruction - regardless of what state the guest
CPU is ACTUALLY in or later transitions to. Forcing `set architecture
arm` before connecting caused an outright `Remote 'g' packet reply is
too long` failure. Connecting with the (wrong, but negotiated) default
AArch64 architecture and setting a software breakpoint at a real
32-bit-code address produced something worse than a clean failure: the
SAME "SIGTRAP at a fixed, unrelated address" on every subsequent
`continue`, which briefly looked like a genuine infinite loop in the
kernel itself. It wasn't - gdb had inserted its breakpoint's opcode
bytes using the wrong instruction width/encoding for the actual
(AArch32) code at that address, corrupting the instruction stream it
was trying to observe. The tell was polling the SAME state through a
channel gdb wasn't involved in at all - the QEMU monitor's own `info
registers` (real hardware state, no software-breakpoint insertion) -
and seeing PC genuinely change between polls, proving the "loop" was a
debugging-mechanism artifact, not a real hang. General lesson: on a
mixed-mode/mixed-architecture target, cross-check ANY gdb-reported
"stuck" or "looping" state against a gdbstub-independent view (the
monitor's own register/memory reads, or `-d int`/`-d in_asm` logging)
before trusting it - and prefer QEMU's OWN monitor over software
breakpoints entirely when the guest's current execution state/width is
uncertain or actively transitioning (here: mid EL3/EL2/EL1 drop).

22. Which privilege/exception level code is ACTUALLY running at must be read from the CPU directly - never assumed from what a "typical" boot chain does
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
Also from forks/arm-pi3 (notes_arch_arm_pi3.txt's own long EL0-EL3
writeup has the full story). An AArch64 firmware stub was written
assuming it ran at EL3 - the CPU's true hardware reset state, and where
architecture-manual descriptions of "how a boot chain works" typically
start - and its very first system-register write (to an EL3-only
register) faulted immediately. The board model being emulated
(QEMU's "-M raspi3b") had already run its OWN internal firmware ROM
before ever handing control to the code under test, and that ROM had
already dropped the CPU from EL3 to EL2 as part of its own job - so the
stub's real starting level was EL2, not EL3, and every register it
should have touched was one level down from what was written. This was
only knowable by reading the CPU's actual current state directly - here
via gdb-multiarch's own CPSR/PSTATE mode-field decode (M[4] for
AArch32-vs-AArch64, M[3:2] for the EL when in AArch64) at the exact
instruction where the code was about to run - not by re-reading the
architecture manual harder or assuming the "textbook" boot sequence
applies. General lesson: for ANY code that configures privilege-level
transitions (EL3/EL2/EL1, Secure/Non-Secure, supervisor/hypervisor on
other architectures), confirm the actual starting state via a debugger
before writing a single level-specific register - a board/platform
model is free to have already done part of a real firmware's job before
your own code gets control, and there is no way to know how much of
that job remains from source code alone.

23. A privilege-transition register can be "in effect" even when the level it configures is never actually entered
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
A second ARM EL subtlety from the same forks/arm-pi3 stub (see
notes_arch_arm_pi3.txt): even after correctly targeting an eret FROM
EL2 straight TO EL1 (skipping EL2 execution entirely, a normal and
architecturally-legal transition), the target level's actual execution
state (AArch32 vs AArch64) was governed by a register belonging to the
level being SKIPPED (HCR_EL2.RW) - left at its unconfigured reset
value, the eret kept landing back in EL2 AArch64 instead of the
intended EL1 AArch32, even though every register belonging to the
transition's own source and destination levels was set correctly. This
is not intuitive from "eret transitions from level A to level B,
therefore configure A's and B's own registers" - a level's control
registers can constrain behavior even when that level's own code never
runs. General lesson, useful beyond ARM: when a privilege/mode
transition skips over an intermediate level, don't assume that level's
own configuration registers are irrelevant just because its code path
is never entered - check the architecture manual specifically for
"registers that remain in effect regardless of whether this level's
software executes," not just "registers this level's software would
set for itself."

24. A raw "-kernel"/"-device loader" image's actual load address is a fact to look up per machine model, not a value to copy from a sibling port
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
Three different QEMU Raspberry Pi board models were involved across
this repo's various ARM32 bring-ups (`-M raspi1ap`/`raspi2b`/
`raspi3b`), and each one places a raw binary passed via `-kernel` (or
`-device loader,...,force-raw=on`) at a DIFFERENT physical address -
0x10000 for raspi2b (forks/arm-pi1/forks/arm-pi2/forks/arm's own prior
findings), 0x80000 for raspi3b (forks/arm-pi3, this session) - despite
all three being "the same family" of board and superficially similar
machine definitions. Guessing or reusing a sibling port's own value
without checking cost real time in this session (a first attempt
assumed raspi3b would also use 0x10000; it doesn't). The QEMU monitor's
`info roms` command is authoritative and cheap to check directly:
launch with `-monitor telnet:127.0.0.1:PORT,server,nowait`, connect
with `nc`, and read the `addr=`/`name=` line for the loaded image -
takes seconds and removes the guesswork entirely, including for
multi-file boots (both the firmware stub and the real kernel showed up
as separate named entries in this session's own arm-pi3 investigation,
confirming both landed where intended).

25. A page table built to cover N megabytes of RAM may not IDENTITY-map all N of them - re-verify a load-address choice against the actual mapping-construction code, not just against "is it below the RAM size"
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
forks/arm-pi3's entry.S (notes_arch_arm_pi3.txt bug 7) builds two
DIFFERENT kinds of page-table entries for physical memory: a real
identity (physical=physical) mapping, but only for the FIRST 1MB
section, and a KERNBASE-relative VIRTUAL-only mapping for every other
section across the full configured RAM size. A load address comfortably
inside the total RAM size (a naive "PHYSOFFSET=2MB, RAM is 256MB, so
2MB is nowhere near the edge" check) still crashed, because the
CODE THAT RUNS BEFORE THE MMU IS FULLY TRANSITIONED - the small
pre-to-post-MMU handoff sequence every one of these ARM32 ports has -
needs to keep executing via its PHYSICAL address specifically through
that transition, and only the first-megabyte identity mapping ever
covers that. The fix wasn't "pick any address below the RAM size" but
"read the actual page-table-construction loop, find exactly which
addresses get a real identity mapping (as opposed to only a virtual
one), and pick a load address inside THAT specific, usually much
smaller window." General lesson: when relinking a kernel at a new
physical load address for QEMU (or any second boot target), don't just
check the new address against the total RAM/PHYSIZE the kernel is
configured for - read the actual bootstrap page-table code and
determine which SPECIFIC sub-range it treats specially (usually a much
smaller "just enough to get the MMU-transition code running" window
than the full RAM size), and place the load address inside that.

26. "Boots cleanly, no crash-loop noise" in a prior notes file is a claim to re-verify, not inherit - especially when the only evidence was the absence of visible output
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
forks/arm-pi1's own notes_arch_arm_pi1.txt (Session 1) recorded "boots
cleanly through the full firmware handoff... with zero crash-loop
noise" for a build that, on Session 2's re-verification of the EXACT
same command against the SAME unmodified source (confirmed via `git
stash` - proving this wasn't drift from an intervening code change),
actually hit a 100%-reproducible infinite Prefetch Abort loop (1.26
million identical faults in a 10-second `-d int` capture). The likely
explanation: with `-nographic` and no working console output either
way, "still running with no error" and "silently looping" produce
IDENTICAL terminal output - there was nothing to distinguish them
short of actually checking forward progress. General lesson: a past
finding of "boots clean" that rests on absence of visible failure
(rather than positive evidence of forward progress - a later print
statement, an exit code, a monitor-visible PC advancing) is not
trustworthy on its own; before building further work on top of it,
either reproduce it fresh with a positive-progress check (`-d int`
over a multi-second window, or polling PC via the QEMU monitor at two
different times and confirming it actually moved) or treat it as
unverified.

27. When a test string doesn't appear, check what the KERNEL actually expects as input before concluding the feature is broken
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
Several early interactive tests of forks/arm-pi1's newly-added PL011
input path sent a raw `\n` (0x0a) as "Enter" and saw individual
characters echo correctly but no command ever execute - looking exactly
like a half-broken input path (RX working, line-processing not).
Reading console.c's own `consoleintr()` found the real answer in one
line: `if(c == 0xa) break;` - the kernel explicitly DISCARDS a raw
line-feed and only treats `\r` (0x0d) as Enter, a real, intentional
serial-terminal convention (physical terminals send `\r`), not a bug
in the new code at all. Switching every test to send `\r` immediately
showed full, correct command execution. General lesson: when a
scripted/interactive test sends a byte sequence and gets a partial or
absent response, check the kernel's own input-handling code for what
byte it actually expects before spending time debugging the feature
under test - `grep` the console/tty input path for the literal
`==`/`case` comparisons against control characters (0x0a/0x0d/0x08/
0x7f/...) rather than assuming standard `\n`-terminated line semantics
apply.

28. When a deep, correct-in-principle fix (reordering boot sequence) exposes a second unrelated bug, prefer reverting to a narrower fix that imitates what already-working sibling ports do
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
forks/arm-pi1's real root cause (Bug 5 in notes_arch_arm_pi1.txt) was
that a fault-prone framebuffer write happened before the real
exception-vector table was installed, so the resulting fault got
mishandled catastrophically instead of hitting a normal panic(). The
architecturally "correct" fix - move `tvinit()`/`kinit1()`/`pinit()`
earlier, before the first framebuffer write - DID change the crash
signature (proof it was on the right track), but exposed a second,
separate, unrelated bug (a stack-pointer/vector-table-relocation issue)
that would have needed its own investigation to resolve. Per the user's
own steer ("can't we just imitate what the other working forks did?"),
this was reverted (`git checkout -- source/main.c`) in favor of a
narrower fix matching the pattern every other working sibling port in
this repo already uses: don't write through a pointer that hasn't been
validated (a `fb_ready`-style runtime bounds check gating the risky
call), rather than reordering boot sequence to make a rare fault path
survivable. General lesson: when the "root cause" fix requires
restructuring boot/init ordering and that restructuring surfaces a NEW
bug, it's often better to step back and ask whether a working sibling
port already solves the same class of problem more narrowly (skip the
risky operation when its precondition isn't met) rather than compounding
two open bugs at once chasing full architectural correctness.

29. Debugging GRAPHICS / framebuffer problems under QEMU: how to actually see, capture and diff the emulated screen
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
Every port in this repo is normally driven with `-nographic`, which is
exactly wrong for a display bug: it gives no screen at all, so "nothing
appears" is indistinguishable from "the driver never ran". The full
toolkit that actually worked on forks/arm-pi1's framebuffer console
(notes_arch_arm_pi1.txt bugs 5 and 7):

  a) Run WITH a display, but keep a usable console. Dropping
     `-nographic` gets a real GTK window; the trap is that the serial
     console then moves into that window (a "serial0" tab) and the
     terminal goes quiet, so the shell looks broken. `-serial mon:stdio`
     is the fix: it multiplexes BOTH the guest serial console and the
     QEMU monitor onto the terminal (Ctrl-A C to switch), while the
     window keeps showing the framebuffer. Plain `-monitor stdio` gives
     you the monitor but NO interactive guest console - a genuinely
     confusing state worth recognising immediately. In this repo, see
     forks/arm-pi1/Makefile's own "qemu-graphics" target.

  b) A headless machine may still have a usable X display. This
     sandbox exports a live `DISPLAY=:1`, so a GTK window works even
     with no visible desktop - always check `echo $DISPLAY` before
     assuming graphics are impossible and settling for indirect
     evidence.

  c) Capture the screen programmatically with the monitor's
     `screendump <file>.ppm`. This is the authoritative answer to "what
     would a user actually see", and unlike reading framebuffer memory
     by hand it needs no knowledge of pixel format, stride or base
     address. For scripted use, put the monitor on a socket
     (`-monitor unix:/tmp/mon.sock,server,nowait`) and drive it from a
     few lines of Python rather than typing at it.

  d) PARSE the PPM instead of eyeballing it. P6 PPM is trivial to read
     (ASCII header: magic, width, height, maxval, then raw RGB), and
     three cheap measurements answer almost every question:
       - count of non-black pixels: 0 means nothing was drawn at all;
       - number of distinct colours: 2 (background + one ink colour) is
         the signature of a working text console, many colours suggests
         garbage/uninitialised memory being displayed;
       - a coarse ASCII-art downsample (one character per 8x16 cell,
         "#" if any pixel in the cell is non-background) prints the
         actual screen layout into the terminal, which is enough to
         recognise rendered text and where it stopped.
     On arm-pi1 this turned "is it working?" into "1024x768, 2 distinct
     colours, 3293 non-black pixels forming glyph shapes in the
     top-left" - conclusive, and reproducible in CI-style scripting.

  e) DIFF two screendumps to test interactivity. Capture, send a
     command over the serial console, capture again, compare the
     non-black pixel counts and the ASCII downsample: 3293 -> 3938 with
     two new rows of text proved that characters typed at the serial
     port were also being rendered onto the framebuffer, which no
     amount of staring at a single still frame would have shown.

  f) Watch QEMU's own stderr - device-model warnings are real clues.
     arm-pi1's boot emits "Blocked re-entrant IO on MemoryRegion:
     bcm2835-fb at addr: 0x0" from QEMU's re-entrancy guard. Note also
     the anti-lesson: that warning was suggestive but ultimately NOT
     the cause of the bug (see item 30), so treat such messages as
     leads to check, not as diagnoses.

30. When a device "isn't implemented" in the emulator, probe what it ACTUALLY returns before believing it
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
forks/arm-pi1's framebuffer was written off across two sessions with a
confident-sounding diagnosis - "QEMU doesn't implement the old
mailbox-channel-1 API this port uses, so fbinfo.fbp is never filled
in" - reached by careful comparison against a known-good reference
(Plan 9's vcore.c) which ruled out, one at a time, the struct layout,
the 16-byte alignment, the cache flush, and the VC bus-address
constant. Every one of those comparisons was correct. The conclusion
was still wrong.

What settled it was ten minutes of direct measurement instead of
inference: a temporary patch turning the hardcoded bus-address alias
into a variable, looping over all four candidates, and cprintf-ing the
raw reply fields after each call. QEMU answered every single one
correctly and identically (fbp=0x1c100000, fbs=0x180000, pitch=0x800 -
each value independently checkable against the requested 1024x768x16
geometry). The device was fully implemented; it simply returned the
framebuffer pointer as a plain ARM PHYSICAL address where real firmware
returns a VC BUS address, and the kernel only had a mapping for the
latter.

Generalisable lessons:
  - "Feature X is unimplemented in the emulator" is a hypothesis, and
    usually a lazy one. It is also nearly free to falsify: print the
    actual returned values from inside the guest.
  - Ruling out every difference between your code and a working
    reference does not validate your conclusion about a third party's
    behaviour - it only narrows where YOUR bug is not. The reference
    comparison here was sound and still pointed nowhere near the bug,
    because the bug was in what came BACK, not in what was sent.
  - Sweep a parameter rather than reasoning about which value is
    "correct" when the sweep is cheap. Testing all four bus aliases at
    once cost one boot and immediately proved the alias was irrelevant,
    a question the previous session had spent real effort reasoning
    about from documentation.
  - Prefer printing raw values over inferring them from a downstream
    symptom. The whole two-session detour existed because the only
    evidence anyone had was "the screen is black".

31. A returned address may be in a DIFFERENT address space than the one you can dereference - check the form, not just the value
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
The arm-pi1 framebuffer bug in its final form: firmware hands back a
pointer, and the kernel dereferences it directly. That works only
because the pointer happens to arrive in an address space the kernel
has mapped. Real VideoCore firmware returns a VC bus address
(0x40000000-aliased), which this port identity-maps on purpose; QEMU
returns the raw ARM physical address, which nothing maps.

When consuming an address produced by another agent (firmware, a GPU,
a DMA engine, another CPU in a different mode), ask explicitly: whose
address space is this in, and do I have a mapping for that form? The
robust fix accepts every form it might arrive in and normalises:
here, mask off the alias bits to recover the physical address, then
map it at the virtual address the other form would have implied.

Two supporting checks that were essential to getting the fix right,
both generalisable:
  - Before adding a mapping at runtime, find out which page-table
    entries actually survive. This kernel's switchuvm() memmoves a
    process's page over the first 4KB of the live L1 table on every
    context switch, silently destroying any kernel mapping for
    VA < 0x40000000 - so the new mapping had to go in the upper half.
    Grep for whoever writes to the page-table root before assuming a
    mapping you install will persist.
  - Confirm which page-table root is actually LIVE. This tree contains
    a plausible-looking kvmalloc()/setupkvm_new() pair that rebuilds
    the table from a kmap[] array; it is dead code, never called, and
    the live table is the one built in early boot at a fixed physical
    address. Editing the wrong one would have produced a fix that
    changed nothing, with no error to explain why.

32. grep can silently return nothing on a file with one non-UTF-8 byte - check the file's actual encoding before trusting "no matches"
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
While chasing the arm-pi1 USB root-hub bug (item 33 below), `grep -n
"ProcessRootHub"` against csud/source/hcd/dwc/roothub.c returned
NOTHING, even though `nm` on the compiled object proved the function
was defined right there in that file. The file contained a single
non-UTF-8 byte (an "®" in a comment, left over from the original
Windows-authored source - `file` reported "ISO-8859 text" against
every OTHER vendored file's plain "ASCII text"/"UTF-8 text"). In a
UTF-8 locale, GNU grep's own "binary file matches" heuristic can
silently treat a file with an invalid UTF-8 sequence as binary and
stop reporting ordinary line matches at all, with NO error or warning
printed - the search just quietly comes back empty, indistinguishable
from "genuinely not present". `grep -a` (force text mode) or `file
<path>` (to notice the encoding is anomalous in the first place) are
the fix. General lesson: a `grep`/`ripgrep` "no matches" result on a
file you have independent reason to believe contains the string
(a linker/nm symbol table, a compiler error citing a line number) is
itself a clue, not a dead end - check the file's actual byte encoding
before concluding the string truly isn't there.

33. When a "no matching log line" investigation goes silent, trace the SPECIFIC early-return path, not just "does the function get called"
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
forks/arm-pi1's USB keyboard bring-up hit a long silent stretch: a
polling function ran every tick (confirmed directly - a debug counter
printed on schedule), yet produced zero corresponding log output from
deep inside the call chain it was supposed to drive. The instinct is
to ask "is the function even being called?" - but the more useful
question, once that is confirmed via a direct one-off instrumentation
call (see below), is "which SPECIFIC return path is it taking, silently?"
Reading the actual code found the answer: multiple guard clauses in
this call chain return early with NO log call on certain error codes
(`if (result != ErrorDisconnected) LOGF(...)`, `if ((result =
UsbControlMessage(...)) != OK) return result;` with no message at
all) - by design, not by omission, because a caller further up the
stack is expected to log the FINAL outcome. Staring at "why is nothing
printed" for a chain with several such gates is unproductive; instead,
temporarily instrument the SPECIFIC intermediate values a silent
function is branching on (here: the raw hardware Connected/Changed
status bits, added as a one-line LOGF inside the otherwise-silent
function itself) rather than continuing to add prints only at entry/exit
points further up the call stack, which just re-confirms "it's being
called" without ever revealing WHY it does nothing.

34. Reading data returned by another agent (firmware, an emulated register, a bus transaction) needs "is this genuinely the value I think it is" verified directly, not inferred
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
Two distinct bugs in the same arm-pi1 USB investigation had the exact
same shape: code compared a live value against a sentinel/expected
value, the comparison silently failed, and the actual live value was
never printed anywhere to check. (a) `RootHubDeviceNumber` (expected to
equal the root hub's own USB address) was simply never assigned -
grepping for every WRITE to the variable (not every read/use) found
the gap immediately, a five-second check that would have taken far
longer to find by tracing call chains forward. (b) A hardware port's
"connection changed" bit was assumed to be set once, on principle,
after a controller reset - reading the ACTUAL bit values
(Connected=1, Changed=0) immediately falsified that assumption rather
than yet another round of re-reading the driver's own source trying to
reason out what "should" happen. General lesson, generalizing item 30
from a QEMU-specific case to comparisons in general: when a bug looks
like "condition X should be true and evidently isn't", print the raw
value on both sides of the comparison before hypothesizing further -
it is usually cheaper than the next three hypotheses combined, and
often reveals the bug is somewhere else entirely (as in (a), where the
"missing edge" theory chased for a while turned out to be a red
herring once the real gap - a variable that starts at 0 and is
compared against, but never assigned - was found by grepping writes).

35. When guest-visible behavior contradicts a driver written for real hardware, fetch the emulator's own device-model source and read the exact arithmetic
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
arm-pi1's USB keyboard bring-up hit two separate cases where a driver
(CSUD) that plausibly worked on real hardware behaved incorrectly under
QEMU, in ways no amount of re-reading the driver's OWN source settled:
a transfer that should have succeeded reported "not acknowledged", and
a 0-length transfer that DID complete was nonetheless treated as
"stuck". Rather than keep guessing at QEMU's dwc2 model's behavior,
fetching its actual source settled both in minutes:

  curl -fsSL "https://raw.githubusercontent.com/qemu/qemu/v8.2.2/hw/usb/hcd-dwc2.c" -o /tmp/hcd-dwc2.c

(pin the tag to the EXACT installed version - `qemu-system-arm
--version` - not `master`, since behavior can differ across versions
and you want to read the code that's actually running). Grepping the
~1500-line result for every write to a specific interrupt bit
(`HCINTMSK_ACK`) found none anywhere in the file - the emulated device
genuinely never raises it, on any transfer, ever; and reading the exact
packet-completion arithmetic (`tpcnt = actual/mps; pcnt -=
min(tpcnt,pcnt)`) showed precisely why a 0-length transfer's packet
count is never decremented (tpcnt is always 0 for actual==0). Both
findings are things you could exhaustively test-and-guess your way to
eventually, but reading ~40KB of the actual deciding code settled them
with certainty in about the same time as one more guess-and-recheck
cycle would have taken. General lesson: "the emulator probably doesn't
implement X" is a hypothesis, not a diagnosis - for any actively
developed open-source emulator (QEMU included), it is nearly free to
fetch the exact device model and check directly, and doing so beats
several more rounds of print-and-guess against what is, from the
guest's side, an opaque black box. See notes_tutorial_qemu.txt for the
fuller writeup and more examples (info qtree/usb, screendump, QMP key
injection, --trace, and the process-management gotchas from this same
session).

36. Debug hooks worth keeping: prefer restoring an EXISTING toggle over deleting temporary instrumentation outright
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
Several of this session's own temporary print statements, added and
then removed while chasing the USB keyboard bugs (item 33/34's own
"KeyboardPoll result" and raw-HID-report dumps), turned out to
duplicate a toggle the ORIGINAL author had already anticipated and left
in place, commented out: csud/source/device/hid/hid.c's own
"// Uncomment this for a quick hack to view 8 bytes worth of report"
block. Recognizing and reusing an existing commented-out hook (restore
it to its original commented state when done, rather than deleting it
or leaving an ad hoc duplicate print nearby) keeps the source tidier
and preserves the SAME hook for the next session that needs it. More
generally: before adding a brand-new temporary LOGF/printf for a
one-off investigation, grep the surrounding function for a
"// uncomment" / "#if 0" / "#ifdef DEBUG"-style comment first - library
and driver code from a real upstream project (CSUD included) often
already has one. Conversely, when a temporary print turns out to answer
a question worth re-asking later (not just this one bug), consider
leaving it as a genuine toggle - a compile-time `#ifdef`/named define,
or a runtime flag checked cheaply - rather than deleting it outright,
so the NEXT investigation doesn't have to re-add it from scratch. Judge
this per-hook: a print that answered a one-off "is X true right now"
question is fine to delete; one that answers a recurring "what is the
current state of Y" question (raw HID reports, raw port-status bits)
is worth keeping behind a toggle.

37. Killing a `subprocess.Popen(["make", ...])` needs the whole process group, not just the top-level PID
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
Writing scripts/test_qemu_graphics.py (a regression test that launches
"make run-<arch>-qemu-graphics" and kills it after screendumping the
result) hit a real, reproducible leak: `proc.terminate()` on the
`Popen` handle left the actual `qemu-system-*` process running,
confirmed directly via `pgrep` after what looked like a clean test
exit. Cause: `make run-<arch>-qemu-graphics` itself invokes a SECOND,
nested `make -C forks/<name>` to run the real per-fork target, which
then execs `qemu-system-*` - `SIGTERM` sent to the outer `make`'s own
PID does not automatically propagate to that grandchild process; `make`
has no special-cased "forward signals to my own children" behavior.
General fix, useful for launching ANY multi-level process tree you'll
need to kill later (not just `make` specifically): pass
`start_new_session=True` to `Popen` (puts the whole tree in its own
process group), then kill the GROUP on cleanup -
`os.killpg(os.getpgid(proc.pid), signal.SIGTERM)`, with a `SIGKILL`
fallback if it doesn't exit within a few seconds - rather than
`proc.terminate()`/`proc.kill()` on the top-level handle alone. Worth
checking for this class of leak (`pgrep` for the expected process name
right after your own script's cleanup runs) any time a test/automation
script launches something through an intermediate wrapper process
(`make`, a shell script, a launcher binary) rather than the target
binary directly.

38. When a crash is non-deterministic and multi-core, read the boot ORDER of the transcript before analysing the crash itself
---------------------------------------------------------------------------------------------------------------------------
forks/arm-pi3's long-standing "non-deterministic SMP crash" (see
notes_arch_arm_pi3.txt's own Bug 14) took three sessions. Sessions 1 and
2 both started from the crash and worked backwards: session 1 landed on
"a page-table race inside balloc()'s memmove()", session 2 on "a core
takes a spurious return to EL2 and executes QEMU's raspi_smpboot ROM at
physical 0x300". Both observations were real and accurately captured
(with `-d int` tracing, gdb-multiarch, HCR_EL2/VBAR_EL2 reads - none of
that work was sloppy). Both were four steps downstream of the cause.

The cause was visible in the first three lines of EVERY transcript both
sessions collected, including the passing ones:

    CPU 1: Booted            <- aux_main()'s first cprintf (secondary)
    Hello World from xv6     <- cmain()'s first cprintf (primary)

A secondary core printing before the primary has initialised the console
means the secondaries were never gated at all. From there the bug is a
five-minute read of entry.S (a bare `wfene` with no loop and no
predicate). Session 3 found it by asking "in what order did these lines
get printed, and is that order possible if the handshake works?" before
looking at a single register.

The general point: on a multi-core bring-up, the console transcript is
itself a partial-order trace of who ran what, when. Interleaved or
out-of-order log lines are primary evidence about synchronisation, not
cosmetic noise to be explained away after the "real" bug is found -
especially since a broken lock and a broken gate both show up there
first. Check that the ORDER is possible before you invest in
instruction-level tracing of the failure. Corollary: garbled/interleaved
output from a kernel that has a console lock is never benign - either
the lock is broken or the code is running before the lock exists.

A second, narrower lesson from the same bug: a bare `wfe`/`sev` pair is
never a synchronisation primitive on ARM. WFE returns immediately if the
Event Register is already set (any earlier SEV from any core sets it -
here, a firmware stub's own release SEV), and is architecturally allowed
to return spuriously regardless. Any WFE must sit inside a loop that
re-tests a real memory flag; grep an unfamiliar ARM port's entry code
for `wfe` with no surrounding loop as a matter of course.

39. A pipe-driven test harness tests a different input encoding than a human types - line endings especially
------------------------------------------------------------------------------------------------------------
forks/arm-pi3 passed 20/20 scripted boots and a full usertests run, then
the user tried `make run-arm-pi3` by hand and the Return key did nothing
at all (notes_arch_arm_pi3.txt's own Bug 16). consoleintr() honoured only
LF (0x0a) and discarded CR (0x0d) outright; the harness drives QEMU's
console through a pipe and sent "usertests\n", which was exactly the one
ending that worked.

The general point: scripts/qemu_console.py talks to the guest over a
pipe, not a terminal. A real terminal's Return key sends CR; a pipe sends
whatever the script writes. Any guest-side line-ending, echo, or raw-mode
assumption is therefore untested by the harness by construction - as is
anything else where "a pipe" and "a tty" differ.

Two practical habits:
  - when a port's test-xv6.py picks a line ending, prefer the one a real
    terminal produces ("\r") over the one that merely happens to work, so
    the human-facing path is the tested path. The sibling arm-pi1/
    arm-pi1-bis/arm-pi2 harnesses all send "\r" for exactly this reason -
    arm-pi3 was the odd one out, and that is where the bug hid.
  - after any bring-up milestone declared on scripted evidence alone,
    actually run the interactive target once by hand before calling it
    done. "usertests passes" and "a human can use the shell" are
    different claims.

Related: consoleintr()-style input handling is worth grepping across
sibling forks when one is fixed - arm-pi1 and arm-pi2 hold the exact
mirror image of arm-pi3's bug (they drop LF and honour only CR), which
is almost certainly where the inverted version came from.

40. Before debugging why a scheduler-dependent test hangs, COUNT THE INTERRUPTS
------------------------------------------------------------------------------
Three ports in this repo independently skipped `usertests`' `preempt()`
with some version of the same note: "real memory pressure / multi-process
timing under emulation, not chased". That diagnosis was wrong every
time, and in two ports the real cause has now been found - both were a
timer interrupt that never reached the scheduler.

The tell is the same in every case: `preempt()` forks CPU-bound children
that spin in `for(;;)` and then `kill()`s them. Nothing in that test
makes a syscall from the spinning children, so nothing re-enters the
kernel voluntarily. It is therefore a *direct test of preemption* and of
almost nothing else. A kernel with no working timer tick still boots,
still runs a shell, and still passes nearly all of `usertests`, because
everything else yields through syscalls - so the bug hides until this
one test. `kill()` makes it worse in a way that looks unrelated: it only
sets `p->killed`, and the victim exits on its *next* trap into the
kernel, which for a spinning process is only ever a timer interrupt. So
the parent's `wait()` blocks forever too.

The measurement is one command and takes a minute, and it partitions the
problem before a line of scheduler code is read:

    qemu-system-<arch> ... -d int -D /tmp/int.log
    grep -c "Taking exception 5 \[IRQ\]" /tmp/int.log      # ARM

**But `-d int` is NOT a portable interrupt counter, and on MIPS it will
lie to you.** QEMU's MIPS target logs syscall/TLB exceptions through
`mips_cpu_do_interrupt` but does not log external interrupt delivery the
same way, so a `forks/mips` run that was in fact taking ~23 timer
interrupts per second produced a log containing only `syscall` and
`TLB store` lines - i.e. a convincing, and completely wrong, "zero
interrupts" reading. See item 42; this was the exact trap it describes.

The portable counter is one level down, at the interrupt controller,
because servicing an interrupt always ends in an ack/EOI write:

    qemu-system-<arch> ... -trace memory_region_ops_write -D /tmp/mr.log
    grep -oE "name '[^']*'" /tmp/mr.log | sort | uniq -c | sort -rn

then look at the controller's own region. On `forks/mips` (i8259 via
Malta's PIIX4) that immediately showed the truth:

    347  0x20 <- 0x0a   (OCW3: read IRR)
    346  0x20 <- 0x0c   (OCW3: poll)
    346  0x20 <- 0x60   (OCW2: specific EOI, IRQ 0)

346 timer EOIs in 15s of idle - the tick was working all along. That
same trace is also how to check the timer was PROGRAMMED at all (look
for writes to the `pit` region), and it needs no per-target knowledge of
how the emulator names exceptions. Prefer it over `-d int` unless you
have already confirmed `-d int` reports interrupts on that target.

and, on SMP, count PER CPU - a tick that reaches one core and not the
others looks identical from the console:

    grep -o "Taking exception 5 \[IRQ\] on CPU [0-9]" /tmp/int.log \
      | sort | uniq -c

What that has actually found here:

 - `forks/arm64-pi4`: 108 / 0 / 0 / 0 IRQs across CPUs 0-3. The virtual
   timer PPI was enabled on CPU0 only, because GICv2 banks ISENABLER0/
   ICPENDR0/IPRIORITYR per CPU interface for INTIDs 0-31 and
   `gic_setup_ppi()` was called from the CPU0-only init function. After
   the fix: 382 / 351 / 351 / 350.
 - `forks/arm`: **1** IRQ against 7214 SVCs across a whole boot plus 150s
   of `usertests`. The kernel was driving the SP804 "ARM timer", which
   QEMU registers as a `create_unimp()` stub that never interrupts, so
   the port had no preemption at all and was running entirely on
   cooperative scheduling.

Both numbers are unambiguous in a way that reading scheduler code is
not, and both took far less time than the sessions that had previously
looked at these hangs and given up.

Corollaries worth stating separately:

 - **A sibling port that PASSES the same test is the fastest fix.**
   `forks/arm-pi2` runs `preempt()` fine on the identical board, because
   it ticks off the BCM2835 System Timer instead of the SP804. That made
   the `forks/arm` fix a transcription rather than a design problem. So:
   before designing a fix, grep the sibling forks for one that already
   passes, and diff the relevant driver.
 - **"No interrupts at all" and "interrupts on some cores" are different
   bugs with an identical console symptom.** Only the per-CPU count
   tells them apart.
 - Fixing the timer can *unmask* a second bug rather than finishing the
   job - see item 41.

41. A fix that enables a previously-dead code path is expected to surface a second bug; budget for it
-----------------------------------------------------------------------------------------------------
Twice in one session, fixing a timer immediately produced a *new* failure
that had been unreachable before, and in both cases the second bug was
older than the first:

 - `forks/arm64-pi4`: enabling the timer on cores 1-3 turned a
   `preempt()` hang into a total loss of forward progress. `scheduler()`
   had always flushed the incoming process's *entire* address space
   (`dc cvau`/`ic ivau` per page, O(`p->sz`)) on every context switch
   while holding `p->lock` - survivable only while secondary cores
   almost never rescheduled.
 - `forks/arm`: enabling the System Timer produced a flood of
   "unhandled interrupt: 0". `pic_dispatch()` tested the whole BCM2835
   BASIC pending word as "the ARM timer fired", but bits 8/9 of that
   register mean "GPU pending register 1/2 is non-empty" - so every
   GPU-routed interrupt was also dispatched as the timer. Harmless only
   while nothing else was ever pending.

The pattern: code that was never exercised was never wrong in a way
anyone could observe. When a fix turns a dormant path live, re-run the
FULL suite rather than just the one test that was failing, and read the
new failure as a genuine finding rather than as a regression from the
fix. Neither of these was caused by the timer change; both were revealed
by it.

42. Validate a measurement tool on a signal you know is present, before trusting a zero from it
------------------------------------------------------------------------------------------------
While chasing `forks/mips`' own `preempt()` skip, a
`-trace "pit_ioport*"` run produced an empty log, which reads as a
strong result: "the kernel's `outb()` writes never reach QEMU's PIT at
all". It was wrong. Re-running with a *control* event known to be
firing - `-trace "serial_ioport*"`, on a port whose console output is
visibly working - produced an empty log too, proving the filter itself
was matching nothing and the first "zero" carried no information.

A zero from an instrument you have not calibrated is not evidence. Any
time a measurement returns "this never happens", spend the extra minute
to make the same instrument report something you already know does
happen. Cheap controls for the tools used in this repo:

 - `-trace <glob>`: also trace a device you can see working (the UART,
   on any port that prints).
 - `-d int`: check the log is non-empty at all; a syscall-heavy guest
   should show a steady stream of them. Note that non-empty is NOT
   enough to trust it as an *interrupt* counter - on MIPS it logs
   syscalls and TLB faults while silently omitting external interrupts
   (see item 40).
 - a device trace (`-trace "pit_ioport*"`): confirm the event name
   actually exists in the emulator's own `trace-events` first. Two
   separate "zero accesses" readings in this repo came from event names
   that were never registered - `serial_ioport_*` does not exist (the
   16550's events are `serial_read`/`serial_write`), and
   `pit_ioport_write` never fired even though
   `memory_region_ops_write` showed the PIT being programmed three
   times. `memory_region_ops_read`/`_write` is the low-level fallback
   that cannot miss.
 - a `cprintf()` you just added: confirm an unconditional one at the
   same point appears, before concluding the conditional never fires.

43. A condition ported from another architecture can be silently always-false; grep for constants that no longer mean anything
------------------------------------------------------------------------------------------------------------------------------
`forks/mips` had this in `trap.c`, and it is the whole reason the kernel
never preempted anything:

    if(proc && proc->state == RUNNING && tf->cause == T_IRQ0+IRQ_TIMER)
      yield();

That line is correct, verbatim, in x86 xv6 - `tf->trapno` really does
hold `T_IRQ0 + <irq>` there. On MIPS `tf->cause` is the CP0 **Cause**
register: a 5-bit exception code at bits 6:2 sharing the register with
the IP pending bits, BD and CE. For a hardware interrupt the code is 0
and the register reads something like `0x00008000` - never the constant
32 this compares against. So the branch was dead, and no process ever
gave up the CPU on a clock tick.

What makes this class nasty is that everything around it was already
ported correctly. Fifteen lines above, the same function decodes the
same register properly (`tf->cause & CAUSE_EXC`, then `picgetirq()` to
get the IRQ number) and services the timer, increments `ticks` and EOIs
it. Only the *last* use of `tf->cause` kept the x86 meaning. A reviewer
reading top-to-bottom sees correct MIPS code and stops looking.

The failure is also maximally quiet. A kernel with no preemption boots,
runs a shell, and passes nearly all of `usertests`, because everything
else yields through syscalls. It shows up in exactly one test -
`preempt()` - which had duly been commented out in three ports as "real
memory pressure / multi-process timing under emulation".

How to find this class deliberately:

 - **Grep the ported tree for the old architecture's constants and field
   names.** `T_IRQ0`, `trapno`, `tf->cs & 3`, `DPL_USER`, `%eip` in a
   MIPS/ARM/RISC-V port are all suspects. A constant that survives a port
   unchanged is either genuinely portable or a bug; there is rarely a
   middle case.
 - **Suspect any comparison of a hardware register against a small
   integer.** Registers like Cause, ESR, SPSR or CPSR are bitfields;
   `reg == <constant>` is almost always wrong where `reg & MASK` is meant.
   `forks/arm` had the mirror-image bug in the same session -
   `if(vic_base[VIC_IRQPENDING_ARM])` treated a whole pending word as one
   flag, when bits 8/9 of it mean "some *other* bank is pending".
 - **When one use of a field is decoded and a later use is not, the later
   one is the bug.** Decoding it twice, inconsistently, in one function is
   the signature.

The fix here is the shape worth copying: decide the condition *where the
information exists*. `picgetirq()` already returns the IRQ number in the
dispatch switch, so set an `istimer` flag there and test that flag at the
bottom - which is exactly what `forks/arm`'s own `device/gic.c`
`pic_dispatch()` does. Don't re-derive a decoded value from a raw
register a second time.

Result: `preempt()` uncommented, and `forks/mips` reports ALL TESTS
PASSED. Two ports in one session had `preempt()` skipped as a timing
artifact and neither was - `forks/arm` had no timer interrupt at all
(item 40), `forks/mips` had the interrupt but no yield.

44. When a build redoes work, ask what the build is TRACKING, not what it is doing
----------------------------------------------------------------------------------
`make build-all` followed by `make test-all` recompiled most of the tree
a second time. The visible cause was a `make clean` in eight ports' own
test-xv6.py; the useful question was why anyone had written it. Answer:
those Makefiles never read the header dependencies they were generating,
so an incremental build was silently wrong, and cleaning was the only
way to trust the result. Fixing the workaround without fixing the
tracking would have traded visible waste for invisible staleness.

Two habits from this, both cheap:

- Run the build twice and diff. A correct build is idempotent: the
  second run must do nothing. Two consecutive `make build-all` runs
  recompiling two ports completely was the tell that found the
  order-only-prerequisite and phony-prerequisite bugs, and it needs no
  hypothesis to try.
- Verify dependency tracking by touching a header and checking a .o
  mtime, never by counting compiler lines in the log. forks/arm and
  forks/arm-pi1-bis print "  CC  build/proc.o" via a `quiet-command`
  macro and never name the compiler, so a grep for "gcc" returns zero
  and a broken build looks like a clean one - the same
  validate-your-measurement-tool point as item 42.

The full write-up, including why a `make depend` target is the wrong
fix and what Linux does instead, is in
docs/claude_notes/notes_build_system.txt.


45. An orphaned QEMU eats a core for hours and silently invalidates every
    timing-sensitive result you take afterwards.

Half a day of chasing a "regression" in forks/arm-pi1 was spent on a
machine that had three qemu processes pegged at 100% CPU, left over from
test runs killed with Ctrl-C, `timeout`, or `pkill make`. The oldest had
been running for 17,775 seconds - nearly five hours:

    pid=808985 age=17775s cpu=100% qemu-system-i386
    pid=884973 age=9914s  cpu=100% qemu-system-mipsel
    pid=960489 age=3676s  cpu=100% qemu-system-mipsel

Killing the make wrapper does not kill the emulator it spawned. Every
`make test-<arch>` run after that was competing for three fewer cores, and
since the harness fails on a 600-second wall-clock timeout, tests started
"failing" that were merely slow. Worse, they failed inconsistently, which
looks exactly like a real intermittent bug.

`make kill-all` exists for this and the top-level Makefile has had it since
the build-and-test phase. The habit that actually matters:

- Before trusting ANY timing-sensitive result, run
  `ps -eo pid,etimes,pcpu,args | grep [q]emu-system`. An emulator older
  than the run you just started is a leftover.
- Run `make kill-all` after any interrupted test, not just when something
  looks wrong.

Same class as item 42: validate the measuring environment before believing
the measurement.


46. A green CI check is weak evidence, and a red one is not automatically a
    regression - read WHICH failure it is.

Every port's harness gives up after 600 seconds with

    ERROR: usertests did not report ALL TESTS PASSED within 600s

On a shared GitHub runner, whose throughput varies several-fold between
runs, that is a coin flip for the slower TCG-emulated ports. This shows up
as jobs failing and passing across commits that cannot possibly have
affected them, and as differing sets of failing jobs on consecutive
commits - which makes `git bisect` against CI results actively misleading.

So classify the failure before reasoning about it:

- a 600s timeout is evidence about SPEED (or about the runner), not
  necessarily about correctness;
- a panic, a trap, or "unknown sys call" is a real defect and will
  reproduce locally on an unloaded machine.

Bisect locally, on a quiet machine, using the port's own `make
test-<arch>`. `make test-all` is the cheap first signal - about a minute
for all fourteen - but it only proves each kernel boots to a shell, so it
cannot see a usertests regression at all.


47. You cannot reproduce a port's test by piping commands into
    `qemu -nographic`.

The obvious shortcut

    ( sleep 30; echo usertests ) | qemu-system-arm -nographic -kernel ...

does not work: the guest echoes the characters and then sits there. The
shell never sees a completed line, so nothing runs, and it looks like the
shell has hung - a completely fabricated symptom that sent this
investigation down a blind alley for several rounds.

Use the port's own test-xv6.py (or `make test-<arch>`), which drives the
console the way the guest expects. If raw output is wanted, redirect the
whole make invocation to a file - piping it to `tail` loses everything when
`timeout` kills the pipeline.


48. Do not conclude "C is slower than assembly here" without reading the
    assembly.

While hunting a suspected performance regression in the shared
lib_core/libc/ulib/ulib.c, forks/mips looked like it had lost a fast
`memset`: its old one called `stosb()`, the shared one is a byte loop. On
i386, `stosb` really is `rep stosb` inline assembly. But forks/mips defines
its own `stosb` in kernel/mips.h, and it is:

    static inline void
    stosb(void *addr, int data, int cnt)
    {
      int i;
      for (i = 0; i < cnt; i++)
        *(((char *) addr) + i) = (char) data;
    }

A plain C byte loop with an x86 name, inherited from the port's x86
ancestry. Replacing it changed nothing, and the "C versus assembly"
explanation was wrong - it just sounded plausible because the name came
from x86. Grep for the definition, in that port, before building a theory
on what an identifier is called.
