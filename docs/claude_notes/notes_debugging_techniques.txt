Debugging techniques, written up as they get used
=================================================

Notes on *how* problems in this repo were tracked down, as opposed to what
they were - see docs/claude_notes/notes_arch_*.txt for the actual bugs and
findings per port. Update this file when a technique earns its place from
real use, not with a narrative of any specific investigation.

1. Triage a -Werror failure before touching any flag: false positive, or real bug?
------------------------------------------------------------------------------------
These ports were written 2006-2023 and are now compiled with GCC 12-13.
Every one of them builds with `-Wall -Werror`, so a warning GCC added
*after* a file was last touched becomes an unconditional build failure,
indistinguishable at first glance from a real bug in 20-year-old code.
Before reaching for a fix, form a concrete hypothesis about which case it
is:

- Read the GCC diagnostic itself for a warning name added recently
  relative to the code's age (`-Warray-bounds` strengthened in GCC 10,
  `-Winfinite-recursion` added in GCC 12 - both hit forks/i386's and
  forks/x86_64's Makefiles this session, see notes_arch_i386.txt).
  A warning about pointer arithmetic on a raw physical address, or about
  a recursive-descent parser/interpreter that obviously terminates via
  exec()/exit() in its base case, is a strong prior for "heuristic false
  positive" - GCC's static analysis can't see the runtime property that
  makes it safe.
- Confirm empirically before suppressing: does the code actually work
  once built anyway? For mp.c's -Warray-bounds, that meant confirming
  mpinit() actually enumerates the second CPU under `-smp 2`; for sh.c's
  -Winfinite-recursion, that meant confirming the shell runs pipelines/
  redirection/command lists correctly throughout a real usertests run.
  Never suppress a warning on the strength of "it's probably fine."
- Fix by adding the single, precisely-named `-Wno-<warning>` flag, not a
  blanket `-Wno-error` or a rewrite of the flagged code - see forks/i386/
  Makefile's and forks/x86_64/Makefile's own `-Wno-array-bounds`/
  `-Wno-infinite-recursion` additions, each with a `claude:`-tagged
  comment naming the exact GCC version and the confirming evidence. A
  real new bug in this code would still be caught by every OTHER warning
  in -Wall.
- If the failure is instead a genuine crash, wrong-answer, or an
  assertion inside a build-time host tool (not a compiler warning at
  all), that's technique 2 below, not this one.

2. Read the assertion/error message and compute the actual numbers before guessing
--------------------------------------------------------------------------------------
forks/x86_64's mkfs aborted with `tools/mkfs.c:268: iappend: Assertion
`fbn < MAXFILE' failed` while packing fs.img. Two minutes of reading turned
that into three concrete, checkable numbers instead of a vague "the build
is broken":

  MAXFILE = NDIRECT + NINDIRECT = 10 + (512/4) = 138 blocks
  138 * BSIZE(512) = 70656 bytes  <- largest file this fs can hold
  actual `usertests` binary size = 79728 bytes  <- confirmed via `ls -la .fs/`

That single comparison identified the exact fix needed (more headroom in
MAXFILE*BSIZE) and, just as importantly, which fix was safe: doubling
BSIZE (multiplying the NINDIRECT term) rather than raising NDIRECT
(which would also grow struct dinode and need re-deriving IPB/inode-block
counts) - see notes_arch_x86_64.txt for the full reasoning and the
cross-check against forks/riscv64/kernel/fs.h's own BSIZE=1024 precedent.
The general lesson: an assertion failure names a file and a line for a
reason - compute the real values on both sides of the failing condition
before forming a hypothesis about the fix.

3. A hung/silent QEMU boot: use gdb-multiarch against QEMU's own -gdb stub, then correlate the PC against the kernel's own objdump+symbols
------------------------------------------------------------------------------------------------------------------------------------------------
forks/x86_64 booted (SeaBIOS, ACPI CPU enumeration, "cpuN: starting")
but then produced zero further console output, indefinitely, under both
`-smp 1` and `-smp 2`. Guessing at the cause (timer? APIC? scheduler?)
from the symptom alone would have been slow. Instead:

  qemu-system-x86_64 ... -gdb tcp::12399 &   # -S not even needed - it
                                              # was already stuck
  gdb-multiarch -batch \
    -ex "set architecture i386:x86-64" \
    -ex "target remote localhost:12399" \
    -ex "info registers rip rsp rbp" -ex "x/3i \$pc" -ex "bt"

This gives a real, if symbol-less (no `file` loaded), instruction
pointer and backtrace immediately. The next step is mechanical, not
guesswork: grep that exact address against the kernel's own
`out/kernel.asm` (every fork's Makefile already generates this via
`objdump -S kernel` as part of the normal build - see e.g. forks/x86_64/
Makefile's `$(OUT)/kernel.elf` rule) to find which function and even
which source line the address falls inside, then read the surrounding
disassembly to see the actual control flow at that point. This
immediately turned "silently hung, no idea where" into "sitting right
after a `hlt` instruction inside scheduler()'s own documented idle-wait
path (`if no runnable process, hlt() until the next interrupt`)" -
reframing the question from "where is it stuck" (answered) to "why does
this specific hlt() never get woken back up" (the real remaining
question - see notes_arch_x86_64.txt for how that was run down).

`gdb-multiarch` (not the host's plain `gdb`) is required on a non-x86
host - confirmed plain `gdb`'s `set architecture i386:x86-64` fails with
"Undefined item" when gdb wasn't built with multi-arch support, while
`gdb-multiarch` (already installed on this box; `sudo apt install
gdb-multiarch` otherwise) accepts it immediately. No `TOOLPREFIX`-style
cross-gdb (e.g. `x86_64-linux-gnu-gdb`) is needed or was installed -
`gdb-multiarch` covers every target this repo's ports build for.

4. Don't trust a same-named tool's version-parsing output without checking `which -a` first
-------------------------------------------------------------------------------------------------
./configure's own qemu-version check (`sed -E`, later rewritten - see
below) failed inexplicably on this machine: `sed: Unknown flag: E`, then
a `bc` "Illegal number: stdin:1 syntax error" on what should have been a
trivial numeric comparison. `which -a sed` and `which -a bc` immediately
showed the cause: `~/goken`'s own build had prepended
`~/goken/ROOT/arch/boot-gcc/bin` onto PATH, and that directory holds
goken's own self-built, minimal `sed`/`bc` binaries (confirmed via
`file`: real aarch64 ELF binaries, not the expected GNU coreutils) which
silently do the wrong thing for `-E`/bare boolean expressions instead of
erroring loudly. `which -a <tool>` (not just `which`, which only shows
the first match) is the fast way to notice a same-named-but-different
tool earlier on PATH before spending time debugging what looks like a
logic bug in your own script. The more robust fix generalizes beyond
this one host: avoid depending on GNU-specific `sed -E`/`bc` behavior at
all when a pure POSIX-shell equivalent exists (parameter expansion +
integer `[ -ge ]` comparisons) - see ./configure's own
detect_qemu_system function and notes_arch_riscv64.txt's "PATH hazard"
section for the full before/after.

5. A captured (non-tty) log's per-line timestamps can be misleading - Python's stdout is block-buffered when piped
----------------------------------------------------------------------------------------------------------------------
Reading a `docker build` log (or any captured `make`/subprocess output),
a `test-xv6.py`-style script's `print()` calls appear to happen all at
once, at whatever moment the process actually exits or its buffer fills
- NOT incrementally as the lines were produced in real time. This showed
up concretely: a captured log had two "ALL TESTS PASSED" lines and a
wrapping "usertests: ALL TESTS PASSED" line all stamped with the exact
same cumulative timestamp, which briefly looked like it implied a
per-arch timing breakdown that later turned out to be an artifact of
buffering, not real elapsed time. Don't compute per-step durations from
timestamps inside a single buffered stream; if real timing matters,
either force line-buffering (`python3 -u`, or `print(..., flush=True)`)
or measure wall-clock time around the whole subprocess from outside
instead.

6. Verify a Docker/CI change locally, with the exact matrix arguments CI will use, before pushing
-------------------------------------------------------------------------------------------------------
When the Dockerfile grew an `ARCH` build-arg so CI could run one job per
arch in parallel, `docker build --build-arg ARCH=riscv64 .` was run
locally first, before touching docker.yml's matrix or pushing anything.
That single local run caught a real bug that would otherwise have only
surfaced as a confusing CI failure: `python3` had never actually been
installed by this Dockerfile - it only "worked" by accident, riding
along as a transitive Recommends of qemu-system-gui's GTK/desktop stack
(python3-gi, python3-dbus), which `--no-install-recommends` (added in
the same change, for an unrelated size/speed reason) then removed. A
second local run with `ARCH=i386` caught a too-tight test timeout the
same way (see notes_arch_i386.txt's TIMEOUT note) - a real, reproducible
failure on this machine with no other load, not a CI-runner-specific
flake, exactly the kind of thing worth catching before spending a CI
run's wall-clock time (and, on this project, the reviewer's patience)
on it. A third example, `ARCH=arm` (forks/armv7-rpi): the fork's own
"qemu" Makefile target ran a bare `clear` before starting QEMU, which
had worked in every interactive terminal session this port was ever
tested from - but `clear` exits non-zero with no `TERM` set, which is
exactly the environment a Docker build runs in, and a plain `@` on a
make recipe line silences echoing the command, not its exit-status
handling, so the whole recipe aborted before QEMU ever started. A
fourth, `ARCH=arm64` (forks/aarch64): `qemu-system-aarch64` refused to
boot at all - "failed to find romfile efi-virtio.rom" - because
`ipxe-qemu` (which ships that ROM, needed for the `virtio-blk-device`
this fork's own Makefile passes, even though no firmware/EFI code ever
actually runs) is only a Recommends of `qemu-system-arm`, stripped by
the same `--no-install-recommends` this Dockerfile uses for image-size
reasons - identical shape to the very first python3 example, just a
different package pulled in by a different Recommends chain. A fifth
and sixth, both `ARCH=mips`: `libc6-dev-mipsel-cross` (cross-compiled
libc headers, only a Recommends of `gcc-mipsel-linux-gnu`) and, once
past that, TWO more missing option ROMs at once (`efi-pcnet.rom` for
QEMU malta's emulated NIC, `vgabios-cirrus.bin` for its emulated VGA
card, from `ipxe-qemu` and `seabios` respectively, both Recommends of
`qemu-system-mips`) - this board model wires up a whole legacy PC-
compatible peripheral set regardless of whether the kernel's own
drivers ever touch most of it, so QEMU refuses to boot at all without
ROMs for hardware this specific kernel never even talks to. The general
pattern across all six: a real terminal's environment (TERM set,
Recommends-pulled packages present, a fast unloaded machine) quietly
supplies things a Docker/CI environment does not, and the gap only
shows up once something actually runs without that scaffolding - which
is precisely why running the container locally, not just reading the
Dockerfile, is the useful step. Worth checking, specifically, whenever
`--no-install-recommends` (or an equivalent minimal-install flag) is in
play: grep `apt-cache depends <package>` for `Recommends:` entries
before assuming the Depends line alone tells you what a package
actually needs at runtime - and expect to need more than one pass: each
of these six was only found because fixing the previous one let the
build get further and hit the next.

7. When a fork's Makefile has an unusual pattern, check whether its siblings share it
------------------------------------------------------------------------------------------
forks/riscv64, forks/i386, and forks/x86_64 all descend from the same MIT
lineage (see the root README's fork-point table) and, unsurprisingly,
share near-identical `TOOLPREFIX`/`QEMU` auto-detect blocks and the same
`sh.c`/`usertests.c` heritage. A gap or bug found in one - forks/i386's
missing `i686-linux-gnu-` candidate in its own TOOLPREFIX probe, or the
`-Winfinite-recursion` false positive in its `sh.c` - was worth checking
in its siblings immediately rather than waiting to rediscover it
independently during that arch's own bring-up: forks/x86_64 turned out
to share the exact same sh.c-derived bug (fixed the same way, see
notes_arch_x86_64.txt), while forks/riscv64's own kernel/fs.h had already
independently solved the same class of problem forks/x86_64 hit
(MAXFILE headroom) by using a bigger BSIZE - a precedent worth searching
for and citing rather than re-deriving the fix from first principles.

8. gdb-multiarch against QEMU's -gdb stub: don't trust an argument display at a breakpoint on a function's opening brace
--------------------------------------------------------------------------------------------------------------------------------
See docs/claude_notes/notes_tutorial_gdb_multiarch.txt for the full
worked tutorial (real command sequences, real output) this technique is
drawn from - this entry is just the one-paragraph version for a fast
re-read. Setting `break <function>` with no explicit line stops at that
function's opening `{`, before its prologue has necessarily spilled
register arguments to the stack slots the debug info assumes for them.
This session hit a real disagreement: GDB's own frame-printed argument
(`chan=0x...`) did not match a direct `print/x $rdi` read at the exact
same stop, and the register read was the correct one (confirmed against
an independently-known-good address moments later). When an argument
value looks implausible right at a function's entry breakpoint, read the
raw SysV argument register directly (`$rdi`/`$rsi`/`$rdx`/`$rcx`/`$r8`/
`$r9` for the first six integer/pointer args) rather than trusting the
pretty-printed frame arguments.

9. Check state AFTER the code that's supposed to change it has actually run, not just near it
----------------------------------------------------------------------------------------------------
A related gdb-multiarch gotcha from the same session (see
notes_tutorial_gdb_multiarch.txt's own case study 5): breaking on
`wakeup()` and reading a process's state at that same stop - i.e. at
`wakeup()`'s own opening brace, before its body has executed - makes it
look like the call had no effect, since the state genuinely hasn't
changed *yet*. This isn't evidence a fix failed; it's evidence of
checking at the wrong instant. Use `finish` (run until the current
function returns) or move the breakpoint to a point past the relevant
mutation before concluding anything from the state you read.

10. `pkill -f`/`pgrep -f` can match this very tool call's own wrapper shell - use the bare name instead
------------------------------------------------------------------------------------------------------------
`pkill -f <pattern>` matches a process's *entire command line*, not just
the target binary. In this harness, every shell command runs inside a
wrapper (`bash -c "... eval '<your whole multi-line script>' ..."`) whose
own argv contains the literal text of the script being run. If that
script's own text contains the same `<pattern>` you're killing (which it
almost always does - you just typed the target's name in the `pkill`
line itself, in the same script), `pkill -f` matches and kills that
wrapper process, silently aborting the entire tool call with no output
at all: no error message, no partial stdout, just an opaque "Exit code
1" (or 137) and every subsequent `;`-separated command in the same call
lost. This cost a long stretch of apparently-inexplicable silent
failures during rv32 bring-up (`pkill -9 -f qemu-system-riscv32 ...`
immediately followed by nothing, even a plain `echo` after it). Fix:
avoid `-f` when the plain process name is enough (`pkill -9
<15-char-or-shorter-name>`), or when the name is truncated/too long for
non-`-f` matching (as `qemu-system-riscv32` is, at 20 characters), filter
`ps -eo pid,comm` yourself instead: `ps -eo pid,comm | awk
'$2 ~ /qemu-system-r/{print $1}' | xargs -r kill -9` - `comm` is the
kernel's own short process name for the *target*, and never contains
your wrapper shell's own command-line text.

11. QEMU's own `-d int,guest_errors -D <file>` beats guessing from gdb's CSR reads when a trap is looping
------------------------------------------------------------------------------------------------------------
When a kernel is stuck retaking the same trap forever (a boot hang that
never advances), attaching gdb-multiarch and reading `$mepc`/`$mcause`/
`$priv` convention registers is one option, but those reads go through
the target's remote-protocol register map, and for less-common
architectures/register sets that map can be incomplete or stale in ways
that are hard to distinguish from a real, reproducible finding (this
happened during rv32 bring-up: gdb's `$mepc` looked consistent across
independent samples, which read as "real" until QEMU's own trace flatly
confirmed it). QEMU itself will log every trap it takes, authoritatively,
with `-d int,guest_errors -D /path/to/file`: each line names the real
`cause`, whether it's `async` (interrupt) or synchronous (exception),
the real `epc`, and `tval`. Grepping that log's *first* occurrence (not
just the repeating tail) confirmed a genuine, 100%-reproducible
"fault_fetch" exception on every single execution of a specific `mret`,
which is what led to the missing-PMP-setup fix (see
notes_arch_riscv32.txt). Reach for this whenever a trap is looping and the
question is "what does the hardware actually think is happening", not
"what does my mental model predict" - it also gives an instant node
count (`wc -l` on the trace) that quantifies just how tight the loop is.

12. A struct copied from a 64-bit sibling port needs its on-disk/on-wire layout re-verified, not just its field types
--------------------------------------------------------------------------------------------------------------------------
Changing `uint64` fields to `uint32` in a struct ported from a 64-bit
sibling fixes the obvious problem (field width) but not necessarily a
more subtle one: some ELF64 structures have a genuinely *different field
order* from their ELF32 counterparts, not just different field widths.
`Elf64_Phdr` is `type, flags, offset, vaddr, paddr, filesz, memsz,
align`; `Elf32_Phdr` is `type, offset, vaddr, paddr, filesz, memsz,
flags, align` - `flags` moves from second to second-to-last. rv32's
`kernel/elf.h` had dropped `flags` entirely (with a comment claiming it
"not in 32 bit ELF!" - wrong; it's in ELF32 too, just relocated), making
`sizeof(struct proghdr)` 4 bytes short of the real on-disk stride. The
first program header read fine anyway (its own fields all landed right,
since the missing field is at the very end); every subsequent one, in a
loop that advances the file offset by `sizeof(ph)` per iteration, read
completely scrambled. The tell: instrumenting each phdr-processing step
with a `printf` showed the very first LOAD segment's iteration produce
no output at all (silently misclassified as a non-LOAD type from
garbled field values) while the second produced a `filesz` that plainly
contradicted `readelf -l`'s own report for that same binary. When a
struct is ported from a 64-bit sibling, cross-check its *field order*
against the real on-disk/on-wire format for the 32-bit case specifically
(a working 32-bit sibling fork's own copy of the same struct, if one
exists in the repo, settles it fastest - forks/i386's `elf.h` had the
correct ELF32 layout all along).

13. A linker script gap on one sibling fork can be invisible until a later pipeline stage
------------------------------------------------------------------------------------------------
forks/riscv64 (rv64) links user programs with a dedicated `user/user.ld`
that explicitly page-aligns `.data` after `.text`
(`. = ALIGN(0x1000);`); forks/rv32 instead used a bare `-N -e main
-Ttext 0`, which packs sections with no such alignment. Both link
*successfully* - the gap only became visible three steps later, at
runtime, when this kernel's own `exec()` rejected the resulting
non-page-aligned second `PT_LOAD` segment (`ph.vaddr % PGSIZE != 0`).
Nothing in the build itself (compiler, assembler, linker, even `readelf`
run without comparison) flags this as wrong - `-N` binaries with
back-to-back unaligned segments are perfectly valid ELF, just not valid
input to *this specific* `exec()`'s stricter check. When a fork is
missing a convention a sibling has (a linker script, a CSR setup step,
an extra build flag), check whether the missing piece is load-bearing by
looking at what *consumes* its output downstream, not just whether the
producing step itself succeeds.

14. When a diagnostic printf's own output looks impossible, suspect the print, and verify with gdb before chasing it
--------------------------------------------------------------------------------------------------------------------------
During arm64's bring-up, `usertrap()`'s own "unexpected ec" print
always showed `0x0`, which looked like it might mean "this was really a
misrouted interrupt, not a real synchronous exception" (interrupts don't
populate ESR_EL1 the same way). The real explanation was mundane: the
function reads ESR_EL1 into a local `ec` a few lines earlier, then
immediately writes 0 back into the register (`w_esr_el1(0)`) - so the
diagnostic printf's own *second* read of the same register, later, could
only ever print 0, regardless of what the real value had been. This was
a real bug (in the print, not the crash), and it would have sent the
investigation in a wrong direction (chasing an interrupt-routing theory)
if trusted at face value. Caught by printing the *local variable*
(captured before the clear) instead of re-reading the register - still
0, which is what finally confirmed the exception class itself really was
the anomaly, not the print. Separately on the same investigation: a
custom `printf("...%x...", some_uint32_t)` call produced values that
didn't match a same-moment `gdb` read of the identical C variable at a
`nop` placed right after the call - not a variadic width bug here (this
kernel's own `%x` and the caller's `uint32_t` argument agreed at 32
bits), but enough of a discrepancy on the first pass to burn real time
second-guessing the print instead of the underlying data. General rule:
when a print's output contradicts everything else you know to be true,
verify the *same value* via `gdb print` (of the actual variable, or of a
`copyin`-style probe result stored somewhere gdb can read it directly)
before spending more time reasoning about what the printed number could
mean - a homegrown kernel `printf`/`vprintf` is exactly the kind of code
most likely to have its own quiet bugs, especially in a 15-20-year-old
freestanding codebase never exercised against every format specifier
combination.

15. A crash at the same call site across two unrelated forks is a hypothesis, not yet a conclusion - but worth writing down either way
------------------------------------------------------------------------------------------------------------------------------------------------
riscv32's still-open "bug 4" and arm64's still-open "bug 1" (see both
forks' own notes_arch_*.txt) both crash a freshly-exec'd `sh` shortly
after its first prompt, inside or immediately around the very first
`memset()` call in `getcmd()` - two ports from different original
authors, different years, different ISAs, with no shared code for this
specific bug to live in (each has its own independently-written
kernel/exec.c, trap handling, etc.). This might be pure coincidence
(getcmd() is genuinely the first non-trivial thing any shell does after
its prompt, so it's an unsurprising place for ANY bug to first surface,
unrelated to what the bug actually is in each case) - but it's the kind
of pattern that's cheap to write down and expensive to silently miss.
When a second unrelated port hits a symptom that rhymes with an already-
documented open bug on a sibling, note the resemblance explicitly in
that port's own notes_arch_*.txt (even before knowing whether it's the
same root cause) - if a THIRD port in the same lineage repeats it, that
upgrades the pattern from "interesting coincidence" to "go looking for a
shared root cause in the common ancestor code" rather than re-diagnosing
each one from scratch.

16. QEMU's own `info mtree` monitor command is authoritative for "what's really at this address" - but you still have to read its output carefully, line by line, not skim it
--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
When a kernel hangs polling a device that should respond, or writes to
something that seems to have no effect, the fastest way to settle "is
this address even right" is to ask QEMU directly rather than cross-
checking against documentation, source comments, or the port's own
(possibly stale) assumptions. Start QEMU halted with an extra monitor
endpoint - `-S -monitor unix:/path/to/sock,server,nowait` (a Unix
socket is easier to script against than the interactive `-monitor
stdio` this repo's forks' own Makefiles use) - then, from a second
shell, `echo "info mtree" | nc -U /path/to/sock` (`nc`, not `socat`,
if the latter isn't installed - both work). This prints the *actual*,
live physical memory map: every device's real base address and size,
organized by which internal bus/address-space it lives in, straight
from QEMU's own device model. This is the same class of technique as
item 11's `-d int,guest_errors` trace (ask the emulator directly
instead of reasoning from source), applied to address-space layout
instead of trap/exception history - reach for `info mtree` specifically
when the question is "where does this address actually land", and item
11's trace when the question is "what trap did the CPU actually take".

During mips bring-up this immediately showed `0x14000000` (what the
kernel's own `io_port_base` assumed was the legacy PCI/ISA I/O window)
actually belongs to the GT64120 system controller's PCI config-space
registers, an unrelated device - real progress, `info mtree` did its
job. But the FIX drawn from that same output was itself wrong, and
stayed wrong across an entire subsequent bring-up session: the real
line was

  0000000010000000-0000000017ffffff (prio 0, i/o): alias pci0-mem0 @pci0-mem ...
  0000000018000000-00000000181fffff (prio 0, i/o): alias pci0-io @io ...

and the fix taken at the time was `0x10000000` (`pci0-mem0` - PCI
*memory* space) instead of the actually-correct `0x18000000`
(`pci0-io` - PCI *I/O* space, two lines down, a different address
space entirely despite the very similar-looking label). Writing/
reading through the wrong-but-real window doesn't fault or show up in
`-d guest_errors` (it's backed memory, just the wrong kind), so the
original symptom (an `ideinit()` busy-wait hang) genuinely went away -
enough surface-level improvement to make the fix look validated - while
the real bug (a UART that produced zero console output) persisted for
an entire separate investigation, root-caused only when a *later*
session re-ran `info mtree` and read the two adjacent alias lines
properly, then cross-checked with a direct register readback (`xp` on
the live UART's IIR at the candidate address, see item 18 below) rather
than trusting the mtree line alone a second time. The tool was right
both times; only the reading of it was careless the first time. Worth
remembering: `info mtree`'s output rewards a careful line-by-line read,
not a skim for the first plausible-looking alias - two adjacent regions
with near-identical labels (`pci0-mem0` vs `pci0-io`) are exactly the
shape of mistake that's easy to make once and then re-derive fixes on
top of for a long time before anyone re-checks the original evidence.

17. When "no console output" survives every kernel-code check, rule out the *host-side capture path* by reading a raw pty directly, not `-nographic`'s stdio multiplexing
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
A kernel that provably reaches `outb(port, c)` with the right port and
the right byte (confirmed via gdb, single-stepped past the actual store
instruction) but still produces zero visible characters has two very
different possible explanations left: the emulated device isn't
actually the one the byte lands on (a guest/device-model bug), or
something about how the *host* is capturing QEMU's output is eating it
(a test-harness bug). `-nographic`/`-serial stdio` funnels output
through QEMU's own terminal-raw-mode handling, which behaves
differently depending on whether the process's stdio is a real
interactive tty versus a pipe/redirect (exactly the situation a Bash
tool's backgrounded, piped invocations are in) - so "nothing arrived on
stdio" is genuinely ambiguous between the two explanations as long as
stdio is the only thing being read.

Settle it by bypassing stdio entirely: `-display none -chardev
pty,id=cm -serial chardev:cm` makes QEMU allocate a real host pty and
print its path (`char device redirected to /dev/pts/N`) at startup;
`cat /dev/pts/N` (or write to it, for input) talks to the guest UART
through an ordinary tty device node, independent of whatever redirected
QEMU's own stdout/stdin. If bytes still never show up here, the guest-
side/device-model explanation is confirmed and stdio-capture concerns
can be dropped entirely - during mips bring-up this is exactly what
happened (still zero bytes on a raw pty), which redirected the ongoing
"bug 5" investigation away from a suspected QEMU-invocation artifact
and back toward the emulated hardware/kernel-code path itself. Also
worth cross-checking with `info chardev` in this situation: it lists
every chardev QEMU actually instantiated and each one's real backend
(`filename=stdio`, `filename=null`, `filename=vc`, ...) - a `vc`
(virtual-console) backend needs a graphical `-display` to ever be
visible, so a device wired to one will look identical to "getting no
output" under `-nographic` even if the guest is writing to it
correctly.

18. When a repeating exception loop's "what got read/written" is ambiguous from a trace alone, decode the raw bytes at the fault address via the QEMU monitor's `xp`
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
`-d int,guest_errors` gives the fault type and address (DFAR/IFAR) but
not what's actually *there* - during armv6-rpi bring-up, a repeating
Data Abort at a suspicious-looking address (`0x800103cc`, matching the
kernel's own KERNBASE offset) turned out to be readable directly: `echo
"xp/8xw 0x103c0" | nc -U /path/to/monitor.sock` (a plain TCP/unix
monitor, no `-S` needed if the loop is steady-state - any snapshot mid-
loop shows the same state) dumped the raw words at that physical
address, and decoding them by hand as little-endian bytes spelled out an
exact string literal from the kernel's own source
(`"..............\nBoot starting...\n"`, from a `_puts()` call) - proving
in one step that the fault was a compiler-generated absolute-address
load for that literal, not a hardware/MMIO issue. The same technique
resolves "is this virtual address actually mapped" questions directly:
compute the PDX/PTX table index by hand from the fault address and the
port's own `mmu.h`-style shift/mask macros, then `xp` the physical
address of that specific page-table slot - a zero (or unexpected) value
there is direct proof of a missing/wrong mapping, no guessing from
symptoms required. This is the same "ask the emulator directly" family
as items 11/16, applied to arbitrary physical memory content instead of
trap history or the address-space layout.

19. A second, unrelated OS/kernel targeting the exact same real hardware is a strong cross-check for "is this sequence of boot steps actually correct"
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
When a from-scratch ARM/MMU boot sequence (disable MMU, zero page
tables, build mappings, enable MMU, switch to the high/KZERO address
space, only then call into C) is suspected of doing something in the
wrong order, a same-repo reference in another architecture's own port
doesn't help - but a genuinely independent, already-hardware-verified
kernel targeting the SAME physical board is excellent ground truth, if
one happens to be available (in this case `~/principia/kernel/COMPILE/
9/bcm/startv6.s`, a Plan 9 port for the same arm1176jzf-s/BCM2835
hardware this session's xv6 port targets, tested on both QEMU and real
Raspberry Pi 1 hardware). Comparing xv6-armv6-rpi's own boot sequence
against it immediately confirmed a real bug by omission: the working
Plan 9 version does no printing of any kind before its own MMU-enable-
and-KZERO-switch step; the xv6 port had one stray early debug print left
active (with every LATER debug print in the same function already
commented out by a previous maintainer - itself a clue the author had
already run into some version of this same problem and partially, not
fully, worked around it). Worth remembering as a search strategy: when
debugging a from-scratch boot sequence for real, well-documented
hardware, check whether the user (or the wider ecosystem) has any other
kernel already working on that exact board - the actual instruction
ORDER of a working reference is often more reliable evidence than
reasoning about ARM/MMU semantics from the architecture manual alone.

20. A breakpoint that should fire but never does is itself the finding - it means the assumed code path is wrong, not that the breakpoint is broken
------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
forks/rv32's bug 4 (see notes_arch_riscv32.txt) looked, from the crash
alone, like register corruption: a shell's memset() call received
completely wrong arguments, and every register-preservation path that
could plausibly explain it (the trapframe struct's field layout, the
trampoline.S save/restore offsets, the callee-saved-register discipline
of the intervening fprintf()/vprintf() calls) had already been checked
by hand, field by field, and matched. Rather than keep re-deriving the
call chain from static disassembly, a gdb-multiarch session was
attached to QEMU's own gdbstub (`qemu-system-riscv32 ... -S -gdb
tcp::1234`, then `target remote localhost:1234` with `set architecture
riscv:rv32`) and a hardware breakpoint (`hbreak`, not `break` - avoids
ever writing to guest memory, so there's no risk of corrupting a
not-yet-mapped or read-only page, a real hazard software breakpoints
have in a system with per-process page tables) was set at the user
virtual address of the ONE call site that could reach the crashing
function.

It never fired - not once in a run where the console was visibly
printing the exact prompt that call site's callee produces. The
instinct at that point should be to suspect the breakpoint mechanism
itself (wrong address, wrong architecture setting, gdbstub flakiness) -
worth ruling out ONCE, cheaply, by setting a second hbreak at a kernel
address known to execute constantly (any frequently-hit printf call
site) and confirming it fires immediately. Once that sanity check
passes, a breakpoint that still never fires at an address the source
code says must be reached is strong, direct evidence that execution
never reaches that address at all - i.e., that the real code path
differs from what the disassembly of the file you're reading implies
about what actually runs. Here that pointed straight at `readelf -h`/
`nm` on the actual built binary, which showed the ELF's own entry point
was a completely different, unexpected function - a two-command
diagnosis that a register-corruption theory would never have reached,
however carefully pursued.
