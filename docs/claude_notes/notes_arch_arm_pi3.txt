What this is, and the naming correction
----------------------------------------
forks/arm-pi3 is patha454/xv6_pi_mp (Harley Paterson, University of
Otago SRG, 2019) - a *verified* real git fork partway down
forks/arm-pi2's own history (see docs/provenance.md). Real Raspberry Pi
3 hardware, with genuine multiprocessing support (the "MP" in pi_mp) -
this is the whole point of the port, unlike the other ARM32 forks here.

Its own upstream README says "AArch64 MP" and the root README's port
table originally described it that way too - but its Makefile only
ever builds 32-bit ARM code (arm-none-eabi- toolchain, -mcpu=cortex-a7/
cortex-a9, -mfloat-abi=hard). This was caught mid-session: an initial
rename to forks/arm64-pi3 (grouping it with the genuinely-AArch64
forks/arm64-pi4) was corrected the same day to forks/arm-pi3 once the
Makefile evidence was actually checked, not just the upstream
description. "AArch64 MP" describes running on the Pi 3's ARMv8 chip in
its AArch32 compatibility mode, with real multiprocessing added on top
- not a 64-bit kernel. See CLAUDE.md's own naming-convention section
and docs/provenance.md for the corrected mapping.

Build system: same "hw=" parameterized Makefile as forks/arm-pi2
--------------------------------------------------------------------
Same fvp/rpi1/rpi2 "hw=" selector, same PHYSTART/PHYSIZE/KERNBASE/
MMIO_PA/MMIO_VA/PERIPHBASE --defsym parameterization as forks/arm-pi2
(both zhiyihuang/xv6_rpi_port descendants) - hw=rpi2 (MMIO_PA=
0x3F000000, real Pi 2/3 BCM2836/2837 peripheral base) is what this
bring-up used throughout, matching the real Pi 3 hardware this fork
targets. Also carries real USB support (uspi_*.c, a full DesignWare
Hi-Speed USB Host controller driver, Chadderz/Rene Stange's USPI
library) that forks/arm-pi1/forks/arm-pi2 don't have at all.

Bug 1 (real, fixed): -fcommon needed for include/proc.h's "struct cpu cpus[NCPU];"
------------------------------------------------------------------------------------
Same class of bug documented in every other fork brought up in this
repo by now (GCC 10 flipped the -fcommon default). Fixed by adding
-fcommon to CFLAGS (all three hw= branches, for consistency).

Bug 2 (real, fixed): missing -marm let the linker emit a Thumb-switching call, sending execution off into uninitialized memory
------------------------------------------------------------------------------------------------------------------------------------
The same class of bug as the sibling forks/arm-pi1-bis fork's own Bug 4
(notes_arch_arm_pi1_bis.txt) - without an explicit ARM/Thumb choice in
CFLAGS, gcc's default codegen mode left room for the linker to emit a
Thumb-switching "blx" for some call (into memmove-family code, as far
as this session dug - not root-caused to the exact call site, just the
mechanism). Confirmed via the QEMU monitor's "info registers": PSR
showed Thumb mode active ("T" flag set) with an odd (bit0-set) LR value
- the unmistakable interworking-switch signature - and PC then visibly
wandering through unrelated, uninitialized memory over successive
polls, instead of executing real code. Fixed the same way as the
sibling fork: added "-marm" to CFLAGS (all three hw= branches) to force
plain ARM code generation outright, removing the state-switch question
entirely. Verified this doesn't affect the real-hardware build in any
way that could matter (same fix category as forks/arm-pi1's own Bug 3
- a universal correctness fix, not a QEMU-only workaround) - a clean
"make hw=rpi2" (the real-hardware "all"/kernel7.bin target) was run
after every change in this session specifically to confirm this.

Bug 3 (real, fixed): delay()'s exact-equality busy-wait
----------------------------------------------------------
Identical to forks/arm-pi1's own Bug 4 and forks/arm-pi2's own Bug 1 -
source/timer.c's delay() used "while(t != getsystemtime());", which can
spin forever if QEMU's emulated timer counter advances by more than 1
between two reads and skips the exact target value. Same fix: a signed
"target reached or passed" comparison
("while((long long)(getsystemtime() - t) < 0);") instead of exact
match - strictly safer on real hardware too, not a QEMU-only patch.
Found via the QEMU monitor: PC parked at a fixed address inside
getsystemtime() (called from delay()) across repeated polls, once the
Thumb bug above was fixed and PC finally became reproducible instead of
wandering.

Bug 4 (real, fixed): VFP/NEON access never enabled - gcc's own -O2 codegen emitted a trapped instruction
-------------------------------------------------------------------------------------------------------------
A genuinely new bug class for this repo (none of the other ARM32 forks
hit it). Once the Thumb bug was fixed, boot progressed further and then
took an "Undefined Instruction" exception (confirmed via "-d int": ESR
0x1fe00000, EC field = 0x7 - "trapped access to SIMD/FP functionality")
- something in this kernel's own C code triggered a VFP or NEON
instruction (almost certainly gcc's own -O2 auto-vectorizing a
struct-copy or similar, not anything the C source intentionally does
with floating point - this kernel is a freestanding OS with no
legitimate use for float/double), and with no coprocessor access
enabled at all (grepped the whole tree - no CPACR/VFP/FPEXC setup
anywhere), the very first such instruction trapped. Real Cortex-A7/A53
silicon would hit the exact same trap - this isn't a QEMU-only gap.
Fixed by adding a standard VFP/NEON enable sequence to entry.S's
boot_reset (CPACR cp10/cp11 = full access, then FPEXC.EN) - added
early, right after the "Update ARM vector address" block, on every
core's own boot path (before the primary/secondary split), so all 4
cores get it.

Bug 5 (real, fixed): Monitor mode setup crashes under QEMU's Non-Secure boot - and is genuinely dead code either way
--------------------------------------------------------------------------------------------------------------------------
trap.c's tvinit() calls set_mode_sp(ptr+4096, 0xD6) to set up a stack
for Monitor mode, among five other exception modes. Monitor mode only
exists in Secure state - a direct CPSR mode-switch into it from
Non-Secure state is architecturally undefined and traps ("unexpected
trap 1" data abort on every core, confirmed via the kernel's own trap
handler output, right at this call). QEMU's raspi3b board-setup ROM
(see Bug 8/armstub64.S below) drops the CPU to Non-Secure before this
kernel ever gets control, so this call was guaranteed to fault under
QEMU. But it's genuinely dead code independent of that: grepped the
whole tree for "smc"/monitor-mode usage - nothing else in this kernel
ever executes an "smc" instruction or enters Monitor mode at all. This
was precautionary SP setup for a mode never actually used, so it was
commented out (not gated behind a runtime Secure/Non-Secure check,
which would only ever have protected dead code) rather than worked
around.

Bug 6 (real, fixed): secondary cores never actually reached this kernel's own entry point at all
-------------------------------------------------------------------------------------------------------
The deepest and most interesting bug this session found. Confirmed via
the QEMU monitor's "info roms": only CPU0 is jumped to "-kernel"'s own
load address directly - cores 1-3 start executing QEMU's own
"raspi_smpboot" ROM instead (a small stub at physical 0x300, matching
what real Pi firmware's own secondary-core release mechanism looks
like), which polls the REAL hardware spintable release-address slots
(physical 0xe0/0xe8/0xf0 for cores 1-3 respectively - core 0 has none
of its own) - the same protocol real Raspberry Pi firmware uses on
actual silicon. Nothing was writing to those slots, so cores 1-3 waited
forever, and this kernel's own multiprocessing support (startothers()/
wait_on_cores() in main.c) never saw them start. Fixed in armstub64.S
(see Bug 8 below) - the stub writes its own base address into all
three slots before doing its own EL2->AArch32-EL1 drop, releasing the
cores into the SAME stub, so each independently repeats that drop and
lands at this kernel's own entry point alongside CPU0 - where
entry.S's existing MPIDR-based primary/secondary gating (the
"cmp r0,#0; wfene; bne mp_continue" near its own top) takes over
exactly as it would following real firmware's own release. Confirmed
working: "CPU 1: Booted" / "CPU 2: Booted" / "CPU 3: Booted" and all
the way through "CPU N: Handing off to scheduler" for all three,
matching CPU0's own boot trace.

Bugs 7-8 (real, fixed): QEMU's raspi3b needs a real firmware step this kernel never had to supply before
-------------------------------------------------------------------------------------------------------------
Two related, non-obvious findings, both new to this repo (the other
ARM32 forks target raspi2b, a pure-AArch32 CPU with none of this):

Bug 7 - wrong QEMU machine, wrong load address, twice: qemu-system-
aarch64's "-M raspi3b" places a raw "-kernel"/"-device loader" image at
physical 0x80000 (confirmed via the monitor's "info roms" - different
from raspi2b's own 0x10000, which the sibling forks/arm-pi1/forks/
arm-pi2 already established). A naive PHYSOFFSET=0x200000 choice built
and looked like it should work, but crashed with a Prefetch Abort
(IFSR 0x5, translation fault) deep inside entry.S's own mp_continue -
root cause: this fork's page-table setup (entry.S's mmu_phase1/
map_kernel_pages) only ever builds an IDENTITY (physical=physical)
mapping for the FIRST 1MB of physical memory (the block handling
PHYSTART's own section, done once before the main loop) - every other
1MB section only gets its KERNBASE-relative VIRTUAL mapping, not an
identity one. The real-hardware default PHYSOFFSET (0x8000) happens to
sit inside that first-MB window, so this was never an issue before;
0x200000 (2MB) sits well outside it, so the pre-MMU/post-MMU-transition
code physically living there (the .init section, and specifically the
"mov pc, r1" jump to _pagingstart mid-transition) had no valid physical
mapping to keep executing from once the MMU turned on. Fixed by picking
QEMU_ARM_ENTRY=0x90000 instead - clear of the armstub's own tiny
footprint at 0x80000, but still comfortably under 0x100000, so the
(very small, ~1KB) .init section stays inside the identity-mapped
window while the REST of the ~600KB kernel physically extends well
past it - which is fine, since everything past .init is only ever
fetched via its virtual (KERNBASE-relative) alias once the MMU is on,
and that side of the mapping the loop DOES build correctly across the
full 256MB PHYSIZE regardless of where PHYSOFFSET sits.

Bug 8 - the real missing piece: an EL3/EL2/AArch32 firmware stub this
kernel needs but never had to write. Even at the right load address,
"-M raspi3b" hung silently (no exceptions logged at all via "-d int" -
genuinely stuck, not crashing). Root cause: the Cortex-A53 QEMU
emulates for raspi3b always resets in AArch64 (confirmed via
gdb-multiarch - the initial gdbstub connection negotiates a 268-byte
AArch64 register set, not AArch32's 168-byte one) - real hardware's GPU
firmware drops the CPU from AArch64 down to AArch32 before jumping to a
32-bit kernel7.img, but QEMU's raw "-kernel"/"-device loader" loaders
skip that whole firmware stage and just jump straight into the loaded
image in whatever state the CPU already has. Tried working around this
with a "-cpu cortex-a53,aarch64=off" property - QEMU refuses outright
("'aarch64' feature cannot be disabled unless KVM is enabled and 32-bit
EL1 is supported"), and KVM itself separately refuses raspi3b ("Cannot
enable KVM when guest CPU has EL3 enabled") - not fixable from the
command line at all on this TCG-only setup. Fixed by writing
armstub64.S - a small (~40 instruction) AArch64 firmware stub,
this repo's own equivalent of real Pi 4/3 firmware's "armstub8-32.bin"
- built with the aarch64-linux-gnu- toolchain (reusing whatever
TOOLPREFIX_ARM64 already found - see configure's own arm-pi3 section),
loaded via "-kernel" (so it's what every core's own reset vector
lands on first), and doing the actual EL-level drop.

Getting that drop right took real trial and error, and is worth a
longer note since the EL0-3/Secure model is genuinely subtle (see the
next section).

The EL0-EL3 / Secure-Non-Secure model, and what actually tripped this session up
------------------------------------------------------------------------------------
ARMv8-A's privilege model has FOUR exception levels (EL0 user, EL1
kernel, EL2 hypervisor, EL3 "secure monitor" - the highest, most
trusted level, roughly where real firmware and TrustZone live) and,
orthogonally, a Secure/Non-Secure split that exists at every level
below EL3 (EL3 is always Secure). A boot chain typically starts at EL3
and drops through EL2 to EL1 before handing off to an OS kernel -
"dropping" here means: EL3 code writes SCR_EL3 (deciding Non-Secure
world and the execution state - AArch64 vs AArch32 - lower levels will
use), sets up SPSR_EL3/ELR_EL3 to describe the exact target level/mode/
address, and executes "eret", which atomically switches to that lower
level and jumps to ELR_EL3 - all in one instruction, with no way to
inspect or single-step through the transition itself.

Two things made this genuinely hard to get right here, both confirmed
empirically rather than assumed from the architecture manual alone:

1. This session's FIRST armstub attempt assumed it was running at EL3
(the CPU's true hardware reset state) and wrote SCR_EL3/SPSR_EL3/
ELR_EL3 directly - and got an immediate fault. Root cause, found via
gdb-multiarch stepping the real reset sequence (not the stub - the
board's OWN pre-kernel ROM, "board-setup" at physical 0x400-0x44c, per
"info roms"): QEMU's raspi3b board-setup ROM ALREADY does the EL3->EL2
half of this drop itself before ever jumping to "-kernel" - it issues
its own "smc 0" call as part of that (visible in that ROM's own
disassembly), matching what real ARM Trusted Firmware does before
handing off to a next-stage bootloader. So this stub's own entry point
is EL2, not EL3 - writing "scr_el3" from EL2 is an EL3-only register
access from a lower level, itself undefined and trapped (landing back
at EL2's OWN synchronous-exception vector, VBAR_EL2+0x200 - confirmed
via gdb reading CPSR's mode field directly, not inferred). Fixed by
rewriting the stub to use SPSR_EL2/ELR_EL2 and "eret" from EL2 instead
of EL3 - matching the level the CPU is ACTUALLY at, not the level the
architecture manual's "typical" boot chain describes starting from.
Lesson: don't assume which EL you start at from documentation about
"how real firmware boots" - a board model can (and this one does)
already have done part of that job before your own code gets control;
confirm the actual starting EL via a debugger (gdb-multiarch's own
initial connection register-set width, or by reading CPSR/PSTATE's
mode field directly) before writing any level-specific system register.

2. Even after fixing that, "eret"-ing from EL2 straight to AArch32 EL1
(SCR_EL3.RW=0-equivalent reasoning applied one level down) STILL landed
back in EL2 AArch64, not EL1 AArch32 - a second, genuinely
counter-intuitive architecture subtlety: when EL2 is implemented (true
on every real ARMv8-A core, and on this CPU model), EL1's ACTUAL
execution state (AArch32 vs AArch64) is governed by HCR_EL2.RW, not by
whatever SCR_EL3.RW said - and this is true even when eret-ing directly
from EL3 (or, here, EL2) straight to EL1, skipping EL2 execution
entirely. HCR_EL2 is "in effect" architecturally the moment EL2 exists
in the implementation, regardless of whether any EL2 code actually
ever runs. Left at its own reset value (unknown/unspecified in general
- happened to still read back as "AArch64" here), the eret kept landing
back in EL2. Fixed by explicitly zeroing HCR_EL2 (RW=0, meaning AArch32
for EL1) before the SPSR_EL2/ELR_EL2/eret sequence. Lesson: when
dropping to EL1 and EL2 is implemented, HCR_EL2.RW needs to be set
explicitly regardless of whether you're eret-ing FROM EL2 or skipping
past it FROM EL3 - it is not enough to only configure the level you are
eret-ing FROM.

Both of these were root-caused the same way: read gdb-multiarch's own
CPSR mode-field decode directly (M[4] for AArch32 vs AArch64, M[3:2]
for the EL when in AArch64, M[3:0] for the specific AArch32 mode when
M[4]=1) rather than guessing from where execution SHOULD be based on
the code just written - the actual state after an eret is exactly what
CPSR/PSTATE's mode bits say it is, nothing more, nothing less.

Bug 12 (real, fixed): the trapframe only ever captured IFAR, never DFAR - every Data Abort's own diagnostic address was meaningless
----------------------------------------------------------------------------------------------------------------------------------------
Found while re-investigating the open SMP crash below: exception.S's
own "_switchtosvc" (the shared handler for undefined-instruction/
prefetch-abort/data-abort/IRQ) unconditionally read IFAR (Instruction
Fault Address Register, coprocessor 15 c6,c0,2) into the trapframe's
own "ifar" field, regardless of trap type - for a genuine Data Abort
(trapno 4), the address that actually faulted lives in DFAR (c6,c0,0)
instead, a COMPLETELY DIFFERENT register. Every "unexpected trap 4 ...
ifar 0x0" diagnostic this fork (and, by inheritance, forks/arm-pi2
before its own independent fix - though that fork's own version of
this bug was never chased since its crash resolved for other reasons)
ever printed for a data abort was therefore showing a meaningless
value (usually 0), not the real fault address.

Fixed with a 3-instruction conditional in exception.S (cmp r0,#0x04;
mrceq ... c6,c0,0 ; mrcne ... c6,c0,2) - reads DFAR specifically when
trapno==T_DABT, IFAR otherwise - same stack slot either way, so no
other offset in struct trapframe or exception.S changes. Renamed the
field itself from "ifar" to "far" (arm.h) and updated trap.c's three
active print statements to match - a real, general diagnostic
improvement independent of what turns out to be causing the open crash
below.

Bug 13 (real, fixed): missing -fno-pic -fno-pie - the identical toolchain-default bug forks/arm-pi2 hit this same session
---------------------------------------------------------------------------------------------------------------------------------
This fork's own Makefile (all three hw= blocks) never had "-fno-pic
-fno-pie" either - confirmed via the identical diagnostic already used
on forks/arm-pi2 (see that fork's own notes' "Bug 7"): "objdump -d" on
a compiled acquire() showed the same GOT-indirect global-variable
access pattern ("ldr r5,[pc,#N]; add r5,pc,r5; ldr r3,[pc,#M];
ldr r5,[r5,r3]"), and this fork ALSO produces a real "cpu0: panic:
release" crash under sustained SMP load (usertests) - spinlock.c's own
release() detecting !holding(lk), exactly the symptom a broken
GOT-indirect "cpus[]" access would cause. Same fix, same reasoning:
"-fno-pic -fno-pie" restores direct "movw/movt" absolute addressing.
This fork's own rpi1 hw= block even had the SAME tell-tale commented-out
alternate CFLAGS line with "-fno-pic" already in it that forks/arm-pi2's
own rpi1 block had - both forks share the same zhiyihuang-lineage
Makefile ancestry, so this was very likely the SAME author's own fix,
lost from the ACTIVE CFLAGS line in both forks the same way.

Verified: the real-hardware kernel7.bin build stays clean with this
change (checked before and after, matching this repo's own convention
for every fork). Does NOT, on its own, fix the open SMP crash below -
see that section for why this was tested and ruled out as sufficient.

Bug 14 (real, fixed): THE open SMP race - the secondary-core boot handshake never actually blocked
--------------------------------------------------------------------------------------------------------
This is the bug two previous sessions were chasing. It is not subtle
once seen, and the reason it took three sessions is worth recording:
both earlier sessions started from the CRASH (a core executing garbage,
a core apparently back at EL2, a memmove() faulting) and tried to
explain the mechanism, rather than starting from the BOOT ORDER printed
in every single transcript.

The tell was in plain sight in every failing log, including session 1's:

    CPU 1: Booted
    <blank>
    Hello World from xv6
    CPU 2: Booted

"CPU 1: Booted" is aux_main()'s own first cprintf. "Hello World from
xv6" is cmain()'s own first cprintf, immediately after consoleinit().
A secondary core printing BEFORE CPU0 has initialised the console means
the secondary cores were never gated at all - they were running
concurrently with CPU0's entire single-threaded init sequence. (The
visibly interleaved, mid-string output in some transcripts - "CPU 1:" /
"Hello World from xv6" / " Booted" - is the same fact stated twice: no
console lock existed yet, because cons.locking is 0 until consoleinit()
sets it.)

There were TWO independent gates, and both were bare WFEs:

  1. entry.S, just before mmu_phase1:

         cmp r0, #0
         wfene
         bne mp_continue

     intended to hold cores 1-3 while CPU0 builds the master
     translation table at K_PDX_BASE.

  2. main.c's aux_main(), via wait_for_event() (exception.S: a bare
     "wfe; bx lr"), intended to hold them while CPU0 finishes
     mmuinit1().

Neither works, for two independent architectural reasons:

  - WFE returns IMMEDIATELY if the calling PE's Event Register is
    already set, and armstub64.S executes "sev" on every core as it
    passes through (and again per-core as each secondary reaches the
    stub - see that file's own comment). By the time any secondary
    executes either WFE, its Event Register is essentially always
    already set, so the instruction is a no-op.
  - WFE is architecturally permitted to return spuriously at ANY time.
    Even a perfectly ordered SEV cannot make a bare WFE into a gate;
    the ARM ARM's own WFE description says the wait must always be
    inside a loop that re-tests a real condition. This code had no
    loop and no condition.

So cores 1-3 fell straight through both gates and, concurrently with
CPU0's own cmain():

  - enabled their MMUs against K_PDX_BASE while CPU0 was still ZEROING
    and filling that very page directory (entry.S's own
    "pagetable_invalidate" loop). This is the actual mechanism behind
    session 2's most confusing observation: a core "returning to EL2"
    and executing QEMU's raspi_smpboot ROM at physical 0x300. It never
    returned to EL2 voluntarily - it translated through a half-built
    page directory, fetched garbage, and the resulting cascade of
    faults through an unpopulated vector table is what the "-d int"
    trace captured. Chasing that trace (spintable re-release, HCR_EL2
    routing, WFI/WFE trapping) was chasing a symptom four steps
    downstream of the cause.
  - called cprintf() before consoleinit() had initialised cons.lock,
    and before gpuinit() had set up the framebuffer gpuputc() writes
    into (source of the "Blocked re-entrant IO on MemoryRegion:
    bcm2835-fb" QEMU warning that also shows up in the sibling ports'
    notes).
  - wrote cpus[] (aux_mmu_init()'s own "curr_cpu->kpgdir = ...") before
    machinit()'s own memset(cpus, 0, ...) erased it again.
  - ran aux_mmu_init() - which memmove()s the whole master page
    directory into the core's own sptable[] copy - before mmuinit1()
    had added the high-RAM mappings and dropped the identity map. That
    is session 1's own "page-table race inside memmove()" observation,
    now explained: the memmove wasn't racing, its SOURCE simply wasn't
    finished yet.

Fix, in three parts:

  (a) entry.S: replaced the "wfene; bne mp_continue" with a real
      release-flag spin on a new "mp_release" word (declared next to
      cpu_sig, in .text, for the same reason cpu_sig lives there: it
      is read with the MMU OFF, at a physical address derived by
      subtracting VA_OFFSET). CPU0 stores 1 there, with a DSB in
      front, at the very end of mmu_phase1. Both sides run with MMU
      and caches disabled at that point, so no cache maintenance is
      needed. WFE is kept inside the loop purely as a spin hint.

  (b) main.c: replaced the SEV/WFE handshake with an explicit
      monotonic "mp_stage" counter plus an mp_wait_stage() spin.
      Stage MP_CPU0_READY is published by startothers(); stage
      MP_INIT_DONE by cmain() right before it hands off to the
      scheduler. signal_event() calls are kept, but purely as wake-up
      hints - the flag is what is actually tested. mp_stage is
      explicitly initialised to 0 so that this Makefile's own
      -fno-zero-initialized-in-bss keeps it in .data, which IS part of
      the loaded raw image (see Bug 15).

  (c) the second gate moved LATER than the original code intended, and
      this part matters independently: aux_main() now waits for ALL of
      cmain()'s init, not just mmuinit1(). tvinit() - the first thing
      a secondary runs - calls kalloc() four times, and kmem.use_lock
      is deliberately 0 from kinit1() until kinit2() returns (standard
      xv6: the free list is lock-free during single-threaded boot).
      Releasing the secondaries after mmuinit1() but before kinit2()
      therefore let up to four cores hammer an unlocked free list. That
      really happened and was visible after fix (a)+(b) alone: 4 of 20
      boots still failed, with

          unexpected trap 4 from cpu 1 addr 80094a98 spsr 1d3 ... far 0
          Data Fault Status Register: 0x805

      on several cores at once. 0x80094a98 is inside memset()'s own
      "str r2,[r3],#4" store loop and DFSR 0x805 decodes as a WRITE
      (bit 11) section translation fault (FS=0b00101) at FAR 0 - i.e.
      kalloc() returned 0 from a corrupted free list and tvinit()'s own
      "memset(ptr, 0, PGSIZE)" dutifully wrote to address 0.

Measured effect, all on the same host, same QEMU, 12s boot budget per
attempt:

    before any fix                    1/6  and 1/6 reached a shell
    after (a) alone                   1/6                (no real change)
    after (a)+(b)                     6/6, then 16/20
    after (a)+(b)+(c)                 20/20, twice over

Real-hardware safety: nothing here is QEMU-specific. A bare WFE is
just as unreliable on real Broadcom silicon - more so, since real Pi
firmware also SEVs to release the spintable - and the kalloc() window
is pure software. Every change is additive (a flag plus a spin loop);
no code real hardware needs was removed, and no #ifdef was introduced.

Bug 15 (real, fixed): .bss was never zeroed - the same bug all three sibling ARM Pi ports had
-----------------------------------------------------------------------------------------------
Found by inspection while fixing Bug 14, not by a failure: "objdump -h"
shows .bss as ALLOC-only (NOBITS, 0x11f90 bytes at 0x80124000), so
objcopy's raw kernel7-qemu.bin does not contain it, and nothing in
kernel.ld, entry.S or main.c ever zeroed it. Every uninitialized global
- cpus[], sptable[], kmem, the buffer cache - started out holding
whatever the previous occupant of that RAM left behind. Note that this
fork's own CFLAGS carry -fno-zero-initialized-in-bss, which only moves
EXPLICITLY zero-initialised globals to .data; it does nothing for the
uninitialized ones, which are exactly the ones at risk.

Invisible under QEMU (its RAM comes up zeroed at reset), which is why
this port got as far as it did without it, but real Pi 3 hardware makes
no such promise. Identical bug and identical fix to forks/arm-pi1's own
Bug 5, forks/arm-pi1-bis's equivalent, and forks/arm-pi2's own Bug 5:
a "PROVIDE(bss_start = .);" in kernel.ld right before ".bss :", plus a
bsszero() in source/main.c called as cmain()'s literal first statement.

One arm-pi3-specific ordering check that the sibling ports did not have
to make: by the time cmain() runs, the secondary cores have already
been released past entry.S's own mp_release gate (Bug 14a) and are
spinning inside mp_wait_stage(MP_CPU0_READY). bsszero() only touches
.bss, and mp_stage lives in .data, so zeroing cannot erase the flag
those cores are waiting on. Recorded here because a future change that
moves mp_stage into .bss would silently reintroduce a hang.

Bug 16 (real, fixed): the Return key did nothing interactively - consoleintr() discarded CR and honoured only LF
--------------------------------------------------------------------------------------------------------------------------
Reported by the user immediately after Bug 14/15 landed: "make
run-arm-pi3" gave a shell prompt, but typing "ls" and pressing RETURN
produced nothing at all.

source/console.c's own consoleintr() had:

    if(c == 0xd) break;              /* CR dropped on the floor */
    c = (c == 0xa) ? '\n' : c;       /* only LF counts as Enter */

A real terminal attached to QEMU's -nographic serial console sends CR
(0x0d) for Return, never LF - so every Return was silently discarded.
The sibling forks/arm-pi1 and forks/arm-pi2 carry the exact mirror image
of this bug in the same function ("if(c == 0xa) break; c = (c == 0xd) ?
'\n' : c;"), which is presumably where this fork's inverted version came
from - someone flipped it rather than making it accept both.

Worth recording WHY the automated tests never caught it, because the
lesson generalises: test-xv6.py drives the console through a pipe and
sent "usertests\n". A pipe is not a terminal, and '\n' was exactly the
one ending this code did honour - so the scripted path passed 20/20
while the human path was completely broken. A harness that feeds input
through a pipe silently tests a different input encoding than the one a
user types.

Fix: accept CR, LF and CRLF alike, translating any of them to '\n', with
a "lastcr" static that swallows the LF of a CRLF pair so one keypress
never becomes two newlines (lastcr is only touched with input.lock held,
for the whole of consoleintr()). Verified all three endings produce
exactly one command and one prompt. Nothing real-hardware-specific was
removed: a USB keyboard's Enter arrives as CR too, and that path is now
honoured where before only a pipe's LF was.

forks/arm-pi3/test-xv6.py now sends "usertests\r" rather than
"usertests\n" - both work after this fix, but "\r" is the ending a real
Return key produces, so it keeps the human-facing path under test.

Added 2026-09-09, at the user's suggestion, once this port had a shell:
it was a good candidate for the "-qemu-graphics" treatment
forks/arm-pi1/arm-pi1-bis already had, because unlike them it ships a
FULL USB stack of its own (uspi - Rene Stange's USPi library, vendored

Bug 17 (real, fixed): uspi rejected QEMU's dwc2 controller outright
  DWHCIDeviceInitialize() tested the DWHCI core VendorId (GSNPSID) for
  exact equality with 0x4F54280A - Synopsys revision 2.80a, what real
  BCM283x silicon reports. QEMU's dwc2 model reports 2.94a
  (0x4F54294A), so the very first thing the USB stack did was log
  "Unknown vendor 0x4F54294A" and give up ("Cannot initialize USB host
  controller interface" in every boot transcript in this file, including
  the ones from sessions 1-3 - it had been there all along).

  Fixed by accepting either ID, and by adding DWHCIDeviceEmulating() - a
  cached read of that same register, TRUE only for the QEMU value. This
  is exactly the technique csud's own HcdEmulating() uses for
  forks/arm-pi1/arm-pi1-bis, and ~/principia's bcm/usbdwc.c emulating()
  uses independently for a different kernel: a genuine hardware
  capability read, so ONE binary is correct on both targets and no
  #ifdef is involved (CLAUDE.md's "prefer runtime detection" rule).
  Note this is the same register the earlier "deliberately deferred"
  note at the end of this file discusses for UART selection - the
  objection there was that uartinit() runs far too early to trust it;
  inside the USB driver, which has just read it, that objection does not
  apply.

  The first use of DWHCIDeviceEmulating() is in
  DWHCITransferStageData's own constructor: split transactions are now
  skipped under emulation. Real hardware needs them for every
  full/low-speed device (all of them sit behind the board's built-in
  LAN9514 hub); QEMU's dwc2 model has no split state machine at all, so
  enabling splits there only makes transfers time out. Same finding, and
  same one-line shape, as csud's own "&& !HcdEmulating()".

Bug 18 (real, fixed): SetPowerStateOn() hung forever on the legacy mailbox power channel
  With Bug 17 fixed, boot stopped dead at "usb: Powering DeviceId: 3".
  source/usb.c's SetPowerStateOn() uses the LEGACY channel-0 mailbox
  power interface (write 0x80 to MAIL1, spin until MAIL0 replies), not
  the property-tag interface on channel 8 that this kernel's own
  mailboxinit()/getpmsize() use successfully. QEMU's raspi3b does not
  model channel 0: instrumenting both loops showed the FULL wait passes
  on spin 0, then the EMPTY wait spins 20,000,000 times with MAIL0
  STATUS stuck at 0x40000000 (EMPTY) and never changing.

  Fixed with an early return when DWHCIDeviceEmulating() - QEMU's dwc2
  is always powered, there is nothing to sequence. Deliberately an added
  early return rather than an edit to the handshake below it, so a real
  Pi 3 still performs the exact same firmware conversation it always
  did, byte for byte.

Bug 19 (real, fixed): an exact-equality busy-wait on the wrapping USB frame counter
  Next stop: USB enumeration reached the second control transfer and
  hung. The culprit was DWHCIFrameSchedulerNoSplitWaitForFrame():

      m_nNextFrame = (FRM_NUM(read) + 1) & 0x3FFF;
      while ((FRM_NUM(read) & 0x3FFF) != m_nNextFrame) ;

  which assumes the host frame counter is OBSERVED at every value it
  passes through. True for a CPU polling real silicon; false under QEMU,
  where the counter is advanced by a timer while TCG runs the spin loop
  in blocks, so the single value being waited for can be stepped
  straight over. Instrumentation caught both halves of this: one wait
  that did match took 3,409,702 spins, and a later one never matched at
  all (a miss costs a full 14-bit wraparound - 0x4000 frames, ~16s - and
  can then miss again).

  This is the same bug class as forks/arm-pi2's own Bug 1 and
  forks/arm-pi1's own Bug 4, both exact-equality busy-waits on
  free-running counters, and it got the same fix: wait for "has reached
  or passed", computed as a wraparound-safe modular difference
  (still-behind lands in the upper half of the 14-bit space, at-or-past
  in the lower half). Correct on real hardware too, and strictly better
  there - it exits at exactly the same frame when that frame is
  observed, and no longer stalls 16 seconds when a slow poll misses it.

  Only the NoSplit scheduler's non-periodic branch was touched (a plain
  pacing delay to the next frame boundary). The equivalent loop in
  uspi_dwhciframeschedper.c is deliberately LEFT ALONE: it runs only on
  the split path, i.e. only on real hardware, and there landing on one
  specific microframe is a real scheduling requirement rather than
  pacing.

Bug 20 (real, fixed): the hub protocol byte was hardcoded to "multiple TTs" in three places
  With Bug 19 fixed, enumeration completed and found a device on the
  root port - "ven409-55aa, dev9-0-0, int9-0-0", QEMU's own USB hub,
  which raspi3b puts between the dwc2 root port and anything attached
  with "-device usb-kbd". uspi rejected it three times over, each
  rejection hidden behind the previous one:

    1. uspi_usbdevicefactory.c matched the string "dev9-0-2" only, so no
       driver was constructed at all ("Device is not supported").
    2. USBStandardHubConfigure() tested bDeviceProtocol != 2
       ("Unsupported hub (proto 0)").
    3. the same function's interface-descriptor loop tested
       bInterfaceProtocol != 2 and "continue"d past the hub's only
       interface, falling out with pInterfaceDesc == 0 ("Invalid
       configuration descriptor (offset 0x9)").

  All three are the same assumption: that a hub is always a HIGH-SPEED
  hub with MULTIPLE transaction translators, which is what a real Pi's
  LAN9514 reports. USB 2.0 spec 11.23.1 defines three protocol values
  for class 9 / subclass 0 - 0 = full/low-speed hub (no TT), 1 =
  high-speed with a single TT, 2 = high-speed with multiple TTs - and
  nothing in TUSBStandardHub consults the TT at all (split setup lives
  in the DWHCI layer and keys off device SPEED, not this byte). All
  three tests now accept 0/1/2. Purely additive: the real LAN9514 still
  matches on exactly the terms it did before, and non-hubs and
  multi-configuration devices are still rejected.

Result: "usb: keyboard OK", and a keystroke typed into the GTK window
runs a real shell command, with the output appearing on BOTH the
emulated framebuffer and the serial console. Verified end to end by
scripts/test_qemu_graphics.py (which arm-pi3 is now a member of):
1280x1024 screen, 16313 non-black pixels at the prompt, 21408 after
typing "ls", and the command's own output on the serial log.

Window sizing (reported by the user, fixed in the Makefile only)

  Worth knowing for the sibling graphics ports: forks/arm-pi1 and
  forks/arm-pi1-bis ask for 1024x768, so they generally fit and have not

Real-hardware safety, all four: every change is additive or strictly

CLOSED (was: "Open gap") - the session-1/2 investigation, kept as a record of what the evidence looked like before Bug 14
------------------------------------------------------------------------------------------------------------------------------
NOTE (session 3, 2026-09-09): everything below is superseded by Bug 14
above, which root-caused and fixed this. It is kept verbatim rather than
deleted because it is a genuinely useful worked example of a wrong
diagnosis: two sessions of careful, correct-in-itself instruction-level
tracing that never questioned the boot ORDER visible in the very first
line of every transcript. The "core returns to EL2 and lands at
raspi_smpboot's 0x300" finding below is real and was accurately
observed - it is simply four steps downstream of the actual cause (a
core translating through a page directory CPU0 was still zeroing).
The concrete "next lead" it proposes (capture the FIRST fault at
VBAR_EL2+0x600) would have worked, but was never needed. See
notes_debugging_techniques.txt for the general lesson.

Session 1 (2026-09-08) documented this as a page-table race specifically
inside balloc()/bfree()'s own memmove(), well after "userinit: OK".
Session 2 (2026-09-09) found the SAME underlying non-determinism
manifests in at least two other ways too, INCLUDING one that happens
much EARLIER (before "userinit: OK", sometimes even before "kinit1: OK"
- the very first thing CPU0 prints after "Hello World from xv6"):

- Garbled, interleaved "cpu0: panic: release" output (multiple cores
  printing through the SAME cprintf() call concurrently, itself a
  strong signal something is corrupting shared kernel state, not just
  one memory access) - this specific SYMPTOM turned out to be Bug 13
  above (the missing -fno-pic), and no longer reproduces the same way.
- A hang with NO panic message at all: console output simply stops
  (most often right after some core's own "CPU N: Handing off to
  scheduler." line, before CPU0 has even reached "kinit1: Ok") and
  every core stays silently parked forever. "-d int" tracing (a real,
  reproduced hang, captured from the very first traced instruction -
  see "Methodology" below) caught the actual mechanism: a core (CPU3 in
  the captured run) takes "Taking exception 1 [Undefined Instruction]"
  "from EL2 to EL2" with "ELR 0x300" - physical address 0x300, QEMU's
  OWN "raspi_smpboot" ROM location (see Bug 6 above) - "to EL2 PC 0x200"
  (ESR 0x0/0x2000000: EC=0 "Unknown reason", IL=1). This happened
  immediately after that SAME core finished tvinit()'s own
  set_mode_sp()-based mode-switch sequence (5 real, successfully-traced
  AArch32 mode switches: svc<->fiq/irq/und/abt/sys, matching tvinit()'s
  own 5 set_mode_sp() calls one-for-one) - meaning the core had
  genuinely, correctly been running AArch32 EL1 kernel code for a real
  stretch, then somehow ended up back at EL2 AArch64, executing
  whatever raw bytes physical address 0x300 happens to hold as if they
  were instructions (raspi_smpboot's own real ROM code, most likely -
  not designed to be re-entered this way), which almost immediately hit
  a genuinely undefined encoding and re-trapped to EL2's own vector
  (VBAR_EL2=0, confirmed via gdb - so "PC 0x200" is literally
  VBAR_EL2+0x200, the "current EL, SPx, synchronous" vector slot),
  where it then sat forever (nothing ever populated real handler code
  there either, so the SAME re-trap just repeats).

  A concrete, testable hypothesis for HOW a core gets back to EL2 at
  all: armstub64.S's own spintable-release block (writing 0xe0/0xe8/
  0xf0 and "sev") runs unconditionally on EVERY core, not just CPU0 -
  so cores 1-3 EACH redundantly re-write those same three slots and
  re-broadcast "sev" once THEY reach the stub too, well after CPU0's
  own original release already worked. If QEMU's own raspi_smpboot ROM
  logic re-wakes on ANY "sev" (not just a targeted one), a later core's
  own redundant broadcast could spuriously pull an ALREADY-DEPARTED
  core back toward that ROM's own address range. This was implemented
  (gate the whole block behind a "mrs x0,mpidr_el1; and x0,x0,#3;
  cbnz x0,1f" check, CPU0 only) and tested across 6 repeated full
  reboot+usertests cycles - the hang/crash rate was UNCHANGED (still
  ~60-70% of runs), so this is NOT the (or at least not the whole)
  mechanism - reverted, with the hypothesis and the negative result
  recorded in armstub64.S's own comment for the next session.

  What's still unexplained: WHY a core that has demonstrably been
  running real AArch32 EL1 code (5 successful mode switches deep into
  tvinit()) would return to EL2 at all, given nothing in AArch32 EL1
  can voluntarily re-enter a higher EL without executing something
  trap-worthy (SMC/HVC/an EL2-trapped system-register or WFE/WFI
  access, per HCR_EL2's own routing bits - confirmed HCR_EL2=0 on the
  affected core via gdb, ruling out WFE/WFI-trapping specifically).
  Candidates for a future session, roughly in order of how much new
  evidence would be needed: (1) capture the FIRST exception in the
  chain, not the cascaded one this session caught - set a breakpoint at
  VBAR_EL2+0x600 (physical 0x600, the "lower EL, AArch32, synchronous"
  vector - the correct offset for a trap that originates FROM AArch32
  EL1, not from EL2 itself) on a "-S"-paused boot, BEFORE continuing,
  to read ESR_EL2/FAR_EL2/ELR_EL2 (and, critically, the ORIGINAL
  AArch32 PC/registers, all still on the SVC stack at that point)
  before anything cascades - this session's own attempts at this
  either missed the window (the race can trigger within ~2 seconds of
  boot, faster than a fresh gdb attach) or hit the SAME address-
  resolution confusion documented in notes_tutorial_gdb_multiarch.txt's
  own "mixed 32/64-bit target" gotchas; (2) once a clean FIRST-fault
  ESR_EL2 is in hand, its EC field will name the actual trap class
  directly (HVC=0x16, WFI/WFT=0x1, Data/Prefetch Abort from a lower
  EL=0x24/0x20, ...), turning this from "which of several plausible
  mechanisms" into a single concrete lead; (3) the ORIGINAL
  balloc()/bfree()/memmove() manifestation from session 1 may or may not
  be the SAME root cause as this earlier one - once the early hang is
  understood, re-check whether it still reproduces on its own.

Methodology note for a future session on this specific bug
------------------------------------------------------------------
This fork's crash is worse to chase than forks/arm-pi2's own bugs this
same session for two compounding reasons, both worth knowing going in:
(1) it is genuinely non-deterministic (roughly 60-70% of boots hang or
crash somewhere, the rest reach a real shell - always reboot-and-retry
rather than trusting a single clean or single failed run), and (2) the
CPU is a REAL Cortex-A53 (AArch64-native) running AArch32 code via
architectural compatibility mode, not a pure AArch32 core like
forks/arm-pi1/arm-pi2/arm's own QEMU targets - gdb-multiarch's own
"file" command, if pointed at the 32-bit kernel ELF BEFORE the first
"target remote", forces an ARMv7-only target description that then
outright REJECTS the remote's real (268-byte, AArch64) register-set
report ("Remote 'g' packet reply is too long") - connect WITHOUT a
preloaded file first (raw addresses/nm-derived symbols work fine, same
as notes_tutorial_gdb_multiarch.txt's own "no file at all" case
studies), and only worry about ARM-vs-AArch64 symbol resolution once
you already know which state a given core is actually in.

Dynamic QEMU-vs-real-hardware detection: considered, deliberately deferred
-------------------------------------------------------------------------------
The user asked whether the -DRPI3_QEMU compile-time split (used to
select PL011 vs Mini-UART in source/uart.c - see the Makefile/uart.c's
own comments) could instead be a runtime check, so the SAME binary
works on both targets - matching ~/principia/kernel/COMPILE/9/bcm/

dwc2 controller's GSNPSID register, comparing against the known

0x4F54294A). This is the right general pattern and the SAME signature
IS present and readable in this kernel's own USB code - but uartinit()
runs very early in cmain() (right after machinit()), well BEFORE

block might need before its ID register reads back a reliable, real
value - reading it that early was not verified safe on real hardware in
this session, and getting it wrong risks silently breaking the
already-working real-hardware Mini-UART path for a cosmetic win. Left
as -DRPI3_QEMU (a second, additive compile of the same sources into
build-qemu/, not touching the real-hardware build/ directory at all -
see the Makefile's own comment) rather than risk that regression right
after getting this far. A real fix, if wanted later: confirm (on the
user's own real Pi 3 hardware, or from Broadcom's own documentation)
whether the USB core's ID register is safely readable before any
power-on sequence runs, or find a DIFFERENT always-safe-to-read
QEMU-vs-real signature reachable that early in boot.

MAXFILE, so it happily built a valid-but-too-small filesystem; the
kernel's own balloc() only discovered the shortfall at runtime and
handed back a block number past the compiled-in disksize - a kernel
panic that looks exactly like a hang (the test harness is correctly
waiting forever for a completion string that can never print again).

Fix: nblocks bumped 985 -> 1285 (size 1099 -> 1399) for real headroom,
plus a build-time check in tools/mkfs.c that now fails the BUILD if
fewer than 2*MAXFILE data blocks remain free after packing every file
the image ships with - so a future growth spurt in any shared library
is a clear mkfs error message, not a confusing runtime panic minutes
into a QEMU test run. See forks/arm-pi2's own notes_arch_arm_pi2.txt
Bug 14 for the full measurement (side-by-side block-usage comparison
against the pre-sharing commit) and notes_debugging_techniques.txt for
why this is worth a standing safeguard.

Also lowered validatetest()'s "hi" bound (1100*1024 -> 100*1024, 276
iterations -> 26) - not itself a cause of anything, just no reason to
spend CI minutes on 276 addresses when 26 already samples the
interesting range.

Verified: "make test-arm-pi3" reaches ALL TESTS PASSED in ~49s (was:
a kernel panic partway into every CI run).

Bug 22 (real, fixed 2026-09-11): usertests' own mem() sub-test looked
hung - it was quadratic, same bug shape forks/arm64-pi4 already fixed
----------------------------------------------------------------------------------------------------------------------
Found while trying to share tests/usertests.c across the four Pi ports
(docs/claude_notes/plan_factorization.md) - this fork's own copy skips
mem() and preempt() by default (opt-in via "usertests m"/"usertests p",
which forks/arm-pi3/test-xv6.py never passes), which turned out to
trace via git blame straight to H Paterson's original 2019 upstream
commit (0ed5518c) - not a regression from any factorization work, and
not something the recent printf(1,...) -> printf(...) API-migration
commit (b796fcd) touched beyond the message text. That raised the
question of whether the gating is still needed, or just stale.

Evidence first (see scripts/debug_timing.py, written for exactly this
question - "how long does each stage take", not just pass/fail):
 - Ran "usertests p m" directly. It did NOT hang: left running for the
   repo's own 300s CI budget (docs/claude_notes/notes_debugging_
   techniques.txt's own "measure, don't guess" rule) it progressed past
   mem() at 420s, printing "Tested first 50MB. Breaking early for fast
   testing." (this fork's own mem() already caps the allocation loop at
   0x147A blocks/~50MB, unlike forks/arm-pi2's fully uncapped version -
   also inherited from the 2019 upstream, also not itself the problem).
 - For comparison, forks/arm-pi2 runs mem() unconditionally and
   finishes its own FULL ~960MB run in ~4s (see that fork's own
   notes_arch_arm_pi2.txt Bug 12) - both forks share the identical,
   already-fixed lib_core/libc/ulib/umalloc.c, so the fragmentation bug
   Bug 12 fixed there is not the explanation for a 100x-worse result on
   a SMALLER (50MB vs 960MB) workload here.
 - gdb (QEMU's own gdbstub) was tried first, matching forks/arm-pi2's
   own successful technique for its Bug 12 - unlike there, it was not
   usable here: "info registers" returned identical pc=0x8003c/sp=0/
   lr=0 on all four CPU threads, and "x/8i $pc" could not even read
   memory at that address. Whether that is this board's own AArch64-
   EL-stub boot chain (armstub64.S dropping into AArch32 EL1, unlike
   arm-pi2's much simpler direct 32-bit boot) or a QEMU raspi3b
   gdbstub limitation was not chased further - the timing approach
   above answered the actual question without it.
 - -smp 1 was tried to isolate whether this is SMP-specific: QEMU
   refuses it outright ("Invalid SMP CPUs 1. The min CPUs supported by
   machine 'raspi3b' is 4"), so that comparison is not available on
   this board.

Cause: kernel/vm.c's switchuvm(p, old_sz) unconditionally does a full
"writeback the old process' cached data" flush_dcache_range(0x0,
min(old_sz, p->sz)) - real, necessary work when p is genuinely a
DIFFERENT process/image than what the CPU last ran (every xv6 process
shares the same VA range starting at 0, so an incoming process really
could read a predecessor's stale cached data there without it). But
kernel/proc.c's growproc() - sbrk()'s caller, and so mem()'s own
malloc(10001) loop's real hot path - calls switchuvm(curr_proc, old_sz)
on ITSELF, just to reload its own page table after allocuvm()/
deallocuvm() changed it. There is no "old process" in that call at all;
the flush ran anyway, scaled to the CURRENT (and growing) process size,
on every single sbrk() call. A heap that grows to N bytes via repeated
small sbrk()s pays that flush O(N) times at up to O(N) cost each - the
same O(n^2) shape forks/arm64-pi4 already found and fixed (that port's
own p->cachesync flag gates I-cache sync for newly-written code, a
related but distinct concern from this D-cache writeback-of-a-
predecessor; see that fork's own proc.c). forks/arm-pi2's own
switchuvm() has no such flush at all, which is why it was never exposed
there regardless of workload size.

Fix: kernel/vm.c's switchuvm() gained a third parameter, writeback_old
- the three call sites are scheduler() and exec() (genuine process/
image switches, pass 1, behaviour unchanged) and growproc() (pass 0 -
there is no old process to write back). No change to the "reload this
process' own page table" half of switchuvm() (the memmove of pgdir into
kpgdir, TLB flush, and new-region cache invalidate for growth) - that
part is real, structural work every one of the three call sites still
needs, since allocuvm()/deallocuvm() really did just change which
physical pages p->pgdir points at.

Not a QEMU artifact and not a test-tuned hack: flush_dcache_range()
loops per cache line issuing a real ARM cache-maintenance instruction
each time (see kernel/exception.S's own loop_flush_dcache_range) -
QEMU does not model cache timing, but it still executes that many real
loop iterations, the same instruction count real silicon would. Real
Pi 3 hardware would hit the identical O(n^2) wall on the identical
sustained-sbrk() workload, just later (faster CPU, bigger constant
before it becomes painful) - this removes provably unnecessary work
in one specific call path, it does not weaken the cache-coherency
guarantee anywhere a real switch actually happens.

Result: mem() (still capped at 50MB by this fork's own upstream-
inherited early break) now finishes in ~1s, down from 420s - see
scripts/debug_timing.py's own timestamped output. "make test-arm-pi3"
(default args, mem()/preempt() both still skipped) re-verified green
after the change: ALL TESTS PASSED, no regression in the normal path.

What it does NOT do: fix preempt(). Tried in the same investigation,
also via scripts/debug_timing.py, in complete isolation (confirmed no
other QEMU instance running) and given the same 300s budget: preempt()
alone did not reach "ALL TESTS PASSED" - not a contention artifact
from other diagnostic runs (an earlier attempt was contaminated by a
leftover QEMU process and gave a false hang reading; re-run clean, the
result held). preempt() does not share mem()'s "sbrk() in a growing
loop" shape at all, so this fix does not apply to it, and the failure
was not chased further this session. The original upstream skip
message - "Test is designed for two or less cores" - may well still be
the real, current reason; this fork boots with -smp 4. Left gated
(usertests' own default "usertests" command still skips it, matching
upstream's own original choice) until someone actually roots-causes
it. mem() is a reasonable candidate to un-gate by default now that its
own reason for skipping is fixed; preempt() is not.
