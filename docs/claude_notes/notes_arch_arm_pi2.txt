What this is
------------
forks/rpi2 extends forks/rpi1 to ARMv7/Cortex-A7 (real Raspberry Pi
2/3, BCM2836/2837) - same zhiyihuang/xv6_rpi_port lineage, but a
noticeably more general, more mature Makefile than rpi1's own: a single
parameterized Makefile supports THREE hardware targets via "hw=" (fvp -
ARM's own Fixed Virtual Platform simulator, rpi1, and rpi2, the
default), with PHYSTART/PHYSIZE/KERNBASE/MMIO_PA/MMIO_VA/PERIPHBASE all
passed through as both CC_OPTIONS (-D defines) and LD_OPTIONS (--defsym)
per target - unlike rpi1's own Makefile, which hardcoded most of this.
Ships a real xv6-guide.pdf and a genuine multi-core (WFE/SEV-based)
secondary-CPU boot gate in entry.S - a real, working piece of SMP
bring-up code, unlike the sibling forks/armv7-rpi port's own complete
absence of one (see notes_arch_armv7_rpi.txt's own open "Gap").

Family relationships, for the record: forks/pi_mp (patha454/xv6_pi_mp,
2019, real Raspberry Pi 3 MP hardware) is a *verified* real git fork
partway down THIS port's own history (root README's fork-point table:
`git merge-base` against zhiyihuang/xv6_rpi2_port confirms it), not off
MIT directly and not off rpi1. pi_mp has not been brought up in this
repo's Phase 4 QEMU work yet - no notes_arch_pi_mp.txt exists - so
nothing here has been verified to transfer to it; noted only so a future
rpi2-adjacent bring-up session knows the relationship exists.

Toolchain: arm-linux-gnueabihf-gcc/qemu-system-arm, already installed - no gaps
--------------------------------------------------------------------------------------
Unlike every other ARM fork brought up this phase, "make hw=rpi2
TOOLCHAIN=arm-linux-gnueabihf-" built completely CLEAN on the very first
attempt - zero flag/codegen bugs of any kind. This Makefile's own CFLAGS
already uses real gcc-level "-mcpu=cortex-a7 -mfloat-abi=hard" (not the
"-Wa,"-only mistake that bit rpi1/armv6-rpi/armv7-rpi), and proc.h
apparently doesn't hit the -fcommon issue here (not investigated further
since it wasn't needed - may already use "extern" correctly, or this
codebase's own header organization differs enough to avoid it).

Real hardware safety
---------------------
kernel.ld and the Makefile's own "all"/"$(TARGET)" (kernel7.bin) rule
were NOT touched in any way that changes their behavior. The one real
fix (delay()'s busy-wait, source/timer.c) is universal-correctness-only
(see rpi1's own identical writeup for why). The QEMU-only build path is
entirely NEW, additive Makefile content (a new "kernel7-qemu.bin"/"qemu"
target pair) - critically, THIS TIME NO SEPARATE LINKER SCRIPT WAS
NEEDED AT ALL: kernel.ld already parameterizes its own load address via
"PHYSOFFSET"/"KERNOFFSET" --defsym symbols (with sensible built-in
defaults if undefined), so the QEMU-only target just relinks the exact
same object files with a different set of --defsym values passed on the
command line - a smaller, more surgical addition than rpi1's own
kernel-qemu.ld copy.

Bug 1 (real, fixed): delay()'s exact-equality busy-wait - identical to rpi1's own bug 4
---------------------------------------------------------------------------------------------
source/timer.c's delay() function is BYTE-FOR-BYTE IDENTICAL to
forks/rpi1's own (same "while(t != getsystemtime());" exact-equality
spin-wait) - same root cause (QEMU's emulated timer counter can advance
by more than 1 between two reads and skip the exact target), same fix
(a signed "target reached or passed" comparison), same justification
for why it's safe on real hardware too. See notes_arch_arm_pi1.txt bug 4
and ~/principia/kernel/COMPILE/9/bcm/clock.c's own "claude:"-tagged
comment on this exact class of bug for the same real hardware family.

QEMU load address: confirmed the same 0x10000 finding transfers from the sibling armv7-rpi port
-------------------------------------------------------------------------------------------------------
QEMU's "-M raspi2b" needs a raw "-kernel" image placed at physical
0x10000, not the real-hardware firmware's own 0x8000 - already
established for this exact board in notes_arch_armv7_rpi.txt bug 7
(forks/armv7-rpi's own bring-up); re-confirmed working here via a clean
boot through the full SMC/firmware handoff with the QEMU-only target's
own PHYSOFFSET=0x10000/KERNOFFSET=0x80010000 --defsym overrides.

Real multi-core boot code exists and looks correct (not investigated further)
-----------------------------------------------------------------------------------
source/entry.S's boot_reset has a genuine, textbook-correct ARM SMP
parking sequence: reads MPIDR (mrc p15,0,r0,c0,c0,5), masks the low 2
affinity bits, and any core where that's nonzero does "wfene"
(conditional wait-for-event) then branches to mp_continue - i.e. every
core but CPU0 parks itself waiting for a later SEV, while CPU0 alone
proceeds to build page tables (mmu_phase1). This is real, working code
(unlike forks/armv7-rpi's own complete absence of any core-ID check at
all) and the QEMU trace shows only CPU0 taking the final Undefined
Instruction exception - the other 3 emulated cores' own SMC handoffs all
complete cleanly and there's no sign they're involved in the crash. Not
investigated further this session since CPU0 alone is what's crashing.

Bug/gap 2 (open, NOT fixed): a late crash deep in real kernel code, landing at an address with no symbol at all
---------------------------------------------------------------------------------------------------------------------
With the delay() fix in place, "-d in_asm" shows CPU0 executing well
past uartinit() (including its own now-fixed GPIO-settle delay() calls)
and several other real functions (timer3init, flush_idcache/flush_tlb/
set_pgtbase, getsystemtime again) before jumping to physical address
0x00000300 - which does NOT correspond to ANY symbol in the linked
kernel.elf at all (confirmed via "nm": the closest symbols before/after
this address are getsystemtime at 0x80010284, on a completely different
side of the address space - 0x300 is neither in the low pre-MMU .init
region (0x10000-0x10200) nor the high mapped .text region (0x80010200
onward) - it corresponds to nothing this kernel linked at all). From
there, execution reaches the kernel entry point (0x80010000/0x10000
depending on mapping) and then the high Undefined Instruction vector
(0xffff0004), settling into a steady repeating "Taking exception 1
[Undefined Instruction] on CPU 0" loop - confirmed NOT a full system
reset (only 4 total "Secure Monitor Call" events in the whole trace, one
per CPU, all at the very start - no second round later).

The jump to an address with no matching symbol at all is the most
suspicious part - this looks like a corrupted return address or a
stale/garbage function pointer being called, rather than a
straightforward "wrong constant" bug like every other fix this session.
Diagnosing this properly would need gdb-based single-stepping (checking
the actual LR/call stack at the moment of the bad jump) rather than the
trace-log-based methodology that sufficed for every other bug found so
far - not attempted this session per the user's own explicit choice to
stop here. A reasonable starting hypothesis for a future session: check
whether this happens specifically after uartinit()'s FULL return (not
mid-delay), i.e. whatever calls uartinit() and then makes this bad jump
next - likely somewhere in main.c's own init sequence, given the
function-address clustering seen in the trace (0x8000fdc8, itself also
symbol-less, immediately precedes the jump to 0x300).

=== Session 2 (2026-09-09) ===

Methodology: QEMU's own gdbstub ("-s -S", connect with gdb-multiarch,
"target remote :1234") rather than trace-log reading. Each of QEMU's
emulated cores shows up as its own gdb "thread" (CPU0 = thread 1), which
is what confirmed CPUs 1-3 were innocent (cleanly parked in QEMU's own
synthetic secondary-core spin stub, an address range with no matching
kernel symbol - not a bug, just QEMU's raspi2b machine model's own
boot-time behavior, easily mistaken for a kernel bug from a trace log
alone). A repeatable technique going forward: set breakpoints at a
sequence of function addresses along the expected call path (from
"nm build/kernel-qemu.elf"), "continue" through each in order, and
whichever breakpoint is the LAST one hit before the crash marks the
function actually responsible - much faster than single-stepping, and
avoids the false "it's stuck forever" reading a slow gdbstub singlestep
session gives for a loop that's actually fine and just slow to observe
this way (see Bug/gap 7's own note on this trap). Cross-check any
"stuck" reading against a fast, non-gdb "-d in_asm,int" trace (dedups
by translated block, so a real busy-loop shows as silence rather than
megabytes of repeated lines) before concluding a real hang.

Bug 3 (real, fixed): entry.S's "bl cmain" doesn't perform ARM<->Thumb interworking, but every C function is Thumb
--------------------------------------------------------------------------------------------------------------------------
"readelf -s build/kernel-qemu.elf" showed cmain/uartinit/mmuinit0/etc
all at ODD addresses - the ELF convention for a Thumb interworking
target - confirming this arm-linux-gnueabihf- toolchain defaults to
Thumb-2 C code generation with no explicit "-mthumb"/"-marm" either way
in this fork's own Makefile. source/entry.S is hand-written pure ARM
assembly; its "_pagingstart: bl cmain" is a plain ARM-mode
branch-with-link, which does NOT change CPSR.T (unlike "blx", which
does) - so the CPU stayed in ARM state while fetching cmain()'s own
Thumb-2 instruction bytes and decoded them AS 32-bit ARM instructions.
This is mostly harmless-looking garbage for a surprisingly long
stretch - a gdb breakpoint sweep showed mmuinit0()'s own 256-iteration
loop and several later functions still appearing to "complete" (PC
reaching their addresses), since a breakpoint only checks the PC VALUE,
not whether the CPU decoded its way there via a semantically correct
instruction stream - until a genuinely undecodable 32-bit pattern was
hit inside uartinit(), producing the repeating "Taking exception 1
[Undefined Instruction]" loop this file's own Bug/gap 2 (above) already
found the symptom of, just not the cause.

Fix: added "-marm" to all three hw= blocks' own CFLAGS (fvp, rpi1, and
rpi2 - only rpi2 is QEMU-tested, but all three share the identical
entry.S and the identical bug class) - makes the whole C codebase ARM,
matching entry.S, rather than patching every asm-to-C call site with
"blx" (the user's own explicit preference, given forks/arm-pi1's
toolchain already defaults to/is pinned at ARM). A genuine ISA-
correctness bug, not a QEMU quirk - real hardware would hit the
identical fault - so no runtime/QEMU-only special-casing needed; see
CLAUDE.md's own "Real hardware vs. QEMU" section for why that
distinction matters here.

Bug 4 (real, fixed): GCC auto-vectorized a struct init into NEON instructions, but VFP/NEON coprocessor access was never enabled
----------------------------------------------------------------------------------------------------------------------------------------
With Bug 3 fixed, the crash moved (same "Undefined Instruction"
symptom, later in the boot sequence) to gpuinit()'s own first statement
- "fbinforesp = initframebuf(...)". Disassembly of gpuinit()'s entry
block (objdump -d) showed the REAL culprit wasn't the mailbox call at
all: initframebuf()'s own bulk zero-initialization of the "fbinfo"
struct (fbinfo.width=...; fbinfo.fbp=0; fbinfo.fbs=0; - 8 consecutive
32-bit fields) got compiled by GCC into "vld1.64 {d16-d17}, [sp]" /
"vstr d16/d17, [r4, ...]" - NEON/VFP 128-bit load-store instructions,
GCC's own optimization for a fixed-size bulk memory copy given
"-mcpu=cortex-a7" makes NEON available. This is entirely independent of
"-mfloat-abi=hard/soft" (that flag only selects the calling convention
for float ARGUMENTS - it does not stop the compiler from using
vector/NEON instructions for ordinary memory operations). Nothing in
this kernel's own boot sequence had EVER enabled CPACR (coprocessor
access control, cp10/cp11) or FPEXC (the VFP unit's own enable bit), so
the very first such instruction anywhere in the kernel faulted.

Fix: added the standard ARM VFP/NEON bring-up sequence (CPACR full
access to cp10/cp11, isb, FPEXC.EN) to entry.S's "mp_continue", right
before the MMU is enabled and the code jumps into cmain() - a real,
generic ISA bring-up step this kernel had simply never done, needed
identically on real hardware (which also starts with VFP/NEON access
disabled at reset) - not a QEMU quirk.

Bug 5 (real, fixed): .bss was never zeroed - identical to forks/arm-pi1's own Bug 5 and forks/arm-pi1-bis's equivalent fix
---------------------------------------------------------------------------------------------------------------------------------
With Bugs 3-4 fixed, boot progressed further and produced the exact
same "Blocked re-entrant IO on MemoryRegion: bcm2835-fb at addr: 0x0"
QEMU warning already diagnosed twice before in this repo (see
notes_arch_arm_pi1.txt's own Bug 5) - confirmed via grep that nothing in
this fork (kernel.ld, entry.S, main.c) ever zeroed .bss, only declared
the linker SECTION. Fixed the same way: a "bss_start" linker symbol
(PROVIDE(bss_start = .); right before ".bss :" in kernel.ld) plus a
bsszero() function (source/main.c) called as cmain()'s literal first
statement, before mmuinit0(). Safe for real hardware - this only makes
true what the C standard already promises for zero-initialized globals.

Bug 6 (real, fixed): QEMU's raspi2b "-nographic" console is backed by PL011, not the mini-UART this fork's own uartinit() programs
----------------------------------------------------------------------------------------------------------------------------------------
With Bugs 3-5 fixed, the kernel actually ran deep into cmain() (traced
via "-d in_asm,int" all the way into exec(), i.e. past the ENTIRE
init sequence) - but zero characters ever appeared on the captured
serial console, even given 15 real seconds. This fork's own
source/uart_pl011.c (a PL011 driver, present in the tree but written for
ARM's own FVP simulator's different register base - "fvp.h" addresses,
not BCM283x's) was never called from anywhere outside its own file -
dead code. Exactly the same finding as forks/arm-pi1's own Bug 6/
notes_arch_arm_pi1_bis.txt's Session 2: QEMU's raspi machine models back
"-nographic" with PL011 (UART0), not the mini-UART/AUX peripheral this
port's own uartinit()/uartputc() were written against.

Fix: added a small RPI2-specific PL011 register block (UART0_DR/FR/
IBRD/FBRD/LCRH/CR at MMIO_VA+0x201000, the standard BCM283x PL011
offset) plus pl011putc()/pl011init() to source/uart.c, following the
exact pattern already used for forks/arm-pi1/forks/arm-pi1-bis:
uartputc() calls pl011putc() FIRST, then falls through to the original,
UNMODIFIED mini-UART code; uartinit() calls pl011init() before its own
mini-UART setup. Real hardware keeps working identically - PL011 is a
real, always-present BCM283x peripheral there too, this is a pure
addition, nothing removed or reordered in the mini-UART path.

Verified after Bug 6: "Hello World from xv6" (consoleinit()'s own first
cprintf, main.c) now genuinely appears on the QEMU serial console - the
first-ever visible console output from this port under QEMU.

Bug/gap 7 (open, NOT fixed): a real kernel panic ("popcli") on the first cprintf() call that actually uses cons.lock
---------------------------------------------------------------------------------------------------------------------------
Immediately after "Hello World from xv6" prints, the boot enters a
tight repeating "cpu0: panic: " loop (the message text itself never
prints - see below for why). A gdb breakpoint at panic() itself
(source/console.c:328) caught it cleanly: panic(s="popcli"), called from
source/spinlock.c:101's "if(--curr_cpu->ncli < 0) panic("popcli");",
itself called from release() (spinlock.c:58), from cprintf() itself
(console.c:319 - the "if(locking) release(&cons.lock);" line), from
cmain() at main.c:169 ("The core clock rate is set to %d\n", ...) - a
single-level, non-recursive call chain, no earlier frames. This is
notable because "locking" only becomes true once consoleinit() sets
"cons.locking = 1" near its own end (console.c:529) - so this cprintf()
call is very plausibly the FIRST time cons.lock's acquire()/release()
(and therefore pushcli()/popcli()) pair is genuinely exercised - yet
popcli() finds curr_cpu->ncli already <= 0 BEFORE its own decrement,
despite THIS SAME cprintf() call's own acquire()/pushcli() call having
had to succeed first (no earlier "acquire" panic was seen, and
machinit() - which zeroes the whole cpus[] array - runs early in
cmain(), well before this point). Something between this call's own
pushcli() and popcli() is deflating curr_cpu->ncli by at least one extra
count, OUTSIDE of the visible cprintf()->acquire()/release() pair -
the character-printing loop between them calls gpuputc()/uartputc() per
character, so a reasonable next-session hypothesis is to check whether
either of those (or something they call) has its own, separate
pushcli()/popcli() or acquire()/release() use that isn't correctly
paired. NOT a recursive-panic explanation: the backtrace is a single,
clean level - the "cpu0: panic: " repeating with no message text is
just this cprintf() call itself (INSIDE panic(), also locking-gated
through the exact same broken cons.lock) hitting the identical bug on
its own first character, over and over, in panic()'s own infinite
"for(;;);" - not real reentrant/recursive panic() invocations.

Diagnostic trap worth recording for its own sake: a gdb breakpoint sweep
across cmain()'s later calls (kinit2/userinit/pinit/tvinit/etc) initially
looked "stuck" after gpuinit() - none of those breakpoints hit within a
10-second gdb session. A parallel, non-gdb "-d in_asm,int" trace of the
SAME binary showed real forward progress all the way into exec() within
about 4 real seconds. The gdbstub round-trip overhead, not a real hang,
was responsible for the false "stuck" reading - see this file's own
"Methodology" note above.
