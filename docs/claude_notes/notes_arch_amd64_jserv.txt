What this is
------------
forks/x86_64 is jserv/xv6-x86_64 (per the root README's port table) - a
maintained x86-64 port of the classic xv6-public, structured differently
from forks/i386: out-of-tree object directories (`.kobj/`, `.uobj/`,
`.fs/`, `out/`), a `CROSS_COMPILE`/`QEMU` variable pair (no TOOLPREFIX
auto-detect at all, unlike every other fork examined so far), and an
`X64`-gated Makefile that can build either 32- or 64-bit xv6 from the
same source tree (`X64=1` is the default; this session only exercised the
64-bit path).

Toolchain: no auto-detect at all, but the natural default already works
------------------------------------------------------------------------------
`CROSS_COMPILE ?=` (empty by default) and `QEMU ?= qemu-system-x86_64` in
forks/x86_64/Makefile - unlike TOOLPREFIX in the riscv64/i386 forks, there
is no `ifndef`-guarded shell-probe auto-detect here at all. On this
aarch64 host, `x86_64-linux-gnu-gcc` (the natural cross-compiler target
name) was already installed and `qemu-system-x86_64` too - both were
already covered by the exact same apt packages riscv64/i386 needed
(`qemu-system-misc`/`qemu-system-x86` overlap - `qemu-system-x86`
provides `qemu-system-i386` AND `qemu-system-x86_64` AND
`qemu-system-amd64` from one package, confirmed via `dpkg -L
qemu-system-x86`). No new package was needed.

Same `-Winfinite-recursion` false positive as i386, same fix
--------------------------------------------------------------------
forks/x86_64/user/sh.c is a direct descendant of forks/i386/user/sh.c
(same recursive-descent `runcmd()`) and hits the exact same GCC 12+
`-Winfinite-recursion` false positive documented in
notes_arch_i386.txt - confirmed by plan_build_and_test.md's own guidance
(check siblings, see notes_debugging_techniques.txt item 7). Fixed
identically: `CFLAGS += -Wno-infinite-recursion` in
forks/x86_64/Makefile, with a comment pointing back at forks/i386/
Makefile's own fix rather than re-explaining it.

A real bug: MAXFILE*BSIZE (70656 bytes) is too small for the 64-bit usertests binary (79728 bytes)
------------------------------------------------------------------------------------------------------------
`make` failed inside `mkfs` itself (a HOST tool, not cross-compiled):

  mkfs: tools/mkfs.c:268: iappend: Assertion `fbn < MAXFILE' failed.

Read the assertion, computed the actual numbers (see
notes_debugging_techniques.txt item 2 for the general technique):
`MAXFILE = NDIRECT(10) + NINDIRECT(BSIZE/sizeof(uint) = 512/4 = 128) =
138` blocks, `138 * BSIZE(512) = 70656` bytes - the largest file this
filesystem can hold - and this fork's own compiled `usertests` binary is
79728 bytes, over budget. 64-bit code is inherently bigger than the
32-bit i386 build of the identical source (wider register saves, wider
pointers/immediates throughout, `mcmodel=kernel` addressing) - a real
consequence of X64=1 that BSIZE=512/NDIRECT=10 (unchanged i386-era
constants) never accounted for. The Makefile's own header comment already
half-predicted this: `"FIXME: -O1 and -O2 result in larger user programs,
which can not fit mkfs"`.

**First attempt (wrong, worth keeping as a record): doubled BSIZE
instead.** Doubling `BSIZE` (512 -> 1024) multiplies `MAXFILE`'s
`NINDIRECT` term without touching `struct dinode`'s on-disk layout, and
mirrors what MIT's own later xv6-riscv did for the identical reason
(`forks/riscv64/kernel/fs.h`'s own `BSIZE 1024`). It looked safe against
this fork's IDE driver too: `idestart()` already derives `sector_per_block
= BSIZE/SECTOR_SIZE` generically, with a `panic` guard above
`sector_per_block > 7`. mkfs succeeded, fs.img built - but booting broke:
this change silently takes `sector_per_block` from 1 to 2, and this
fork's `ideintr()` assumes exactly ONE interrupt per `idestart()` request,
doing a single `insl()` of the WHOLE transfer. That assumption was never
actually wrong until now, because BSIZE has always equaled SECTOR_SIZE in
every configuration anyone has ever run this driver in. A real ATA PIO
"READ SECTORS" (not "READ MULTIPLE") command raises one interrupt PER
SECTOR, not one for a whole multi-sector request - confirmed via
gdb-multiarch (see notes_tutorial_gdb_multiarch.txt): `ideintr()` fired
twice per `idestart()` once `sector_per_block` was 2, and the very first
disk read (loading `/init`) got stuck reading incomplete/corrupted data
as a result. This produced a genuine, reproducible heisenbug: it booted
further under gdb (whose breakpoint pauses happened to give the second
sector time to actually become ready before the buggy single `insl()`
read it) than at full untraced speed, where `ptable.proc[0]` stayed
permanently `SLEEPING` even after 40+ real seconds. Rather than teach
`ideintr()` to handle multi-sector PIO transfers correctly (a real fix,
but a bigger and riskier change to this fork's disk driver), this was
reverted.

**Actual fix: raised NDIRECT instead, keeping BSIZE=512.** This keeps
`sector_per_block` at 1 - the only configuration this driver has ever
been exercised in - and solves the exact same shortfall without ever
touching the disk-interrupt code path. One more wrinkle: `NDIRECT` can't
be just any value large enough - `tools/mkfs.c`'s own `main()` asserts
`BSIZE % sizeof(struct dinode) == 0` (inodes must pack evenly into a
block), and since `BSIZE(512) = 2^9`, `sizeof(dinode)` (`24 +
4*(NDIRECT+1)` bytes) must itself be a power of two for that to hold.
`NDIRECT=26` (dinode=128 bytes) very nearly works
(`MAXFILE*BSIZE=78848`) but falls 880 bytes short of the 79728-byte
binary; the next valid value is `NDIRECT=58` (dinode=256 bytes,
`IPB=512/256=2`), giving `MAXFILE*BSIZE=95232` - comfortable margin. Set
in `include/fs.h`.

A real bug: forks/x86_64 double-unmasks interrupt lines on both the legacy PIC and the IOAPIC
---------------------------------------------------------------------------------------------------------
Independent of the BSIZE/NDIRECT story above: the kernel booted (SeaBIOS,
ACPI CPU enumeration, "cpuN: starting xv6") but then produced ZERO
further console output, indefinitely, under both `-smp 1` and `-smp 2` -
this was true even BEFORE the BSIZE experiment above, i.e. two
independent bugs were stacked on top of each other. Full gdb-multiarch
investigation in notes_tutorial_gdb_multiarch.txt (case studies 1-4);
summary of the findings:

- The CPU was legitimately parked in `scheduler()`'s own documented idle
  path (`hlt()`, waiting for the next interrupt to re-scan the process
  table) - not a tight-loop hang.
- The LAPIC timer (`ticks`, read directly via its address from
  `kernel.sym`) was genuinely incrementing at ~100Hz - interrupts in
  general were not globally broken, and `hlt()` was correctly waking up
  every tick.
- `ptable.proc[0]` (pid 1 - the very first process, i.e. what's running
  the embedded `initcode.S` blob then `exec("/init", ...)`) was
  permanently `SLEEPING`, and no second process (the forked shell) ever
  existed (`proc[1]` stayed `UNUSED`) - meaning `init` never even got
  past its *own* first action, `exec("/init", ...)`, which needs a real
  disk read.
- Setting breakpoints on `idestart`/`ideintr`/`trap` showed the disk read
  WAS issued and the IDE completion interrupt WAS delivered and dispatched
  into `ideintr()` - ruling out "no interrupt ever arrives."

Comparing against the WORKING i386 sibling (forks/i386/ide.c) found a real,
concrete divergence: this fork's `kernel/ide.c`, `kernel/console.c`, and
`kernel/uart.c` each call `picenable(IRQ_X)` **in addition to**
`ioapicenable(IRQ_X, ...)`; forks/i386's equivalents call only
`ioapicenable()`. `picinit()` starts by masking every PIC line; in
genuine IOAPIC/MP mode (confirmed active here - `ioapicenable()` itself
early-returns unless `ismp`), the legacy PIC is supposed to stay fully
masked for lines the IOAPIC now owns. The extra `picenable()` calls
unmask those same physical IRQ lines on the PIC too, which - depending on
how a given chipset/QEMU version cross-wires the two controllers - can
mean an interrupt doesn't reliably reach the CPU via the vector the trap
dispatcher actually expects. Fixed by removing the three errant
`picenable()` calls (ide.c, console.c, uart.c), matching forks/i386's own
pattern exactly, each with a `claude:`-tagged comment.
`kernel/timer.c`'s own `picenable(IRQ_TIMER)` was checked and NOT
touched - it lives in the genuinely-uniprocessor-only PIT fallback path
(`if(!ismp) timerinit()` in `main.c`, no competing `ioapicenable()` call
for that device at all in that mode), so it's architecturally different
from the other three and was correctly left alone; confirmed by direct
comparison rather than assumed from the pattern (see
notes_debugging_techniques.txt item 7's own caution against
over-generalizing a pattern without checking each instance).

A real bug: FSSIZE=1000 (inherited from i386) is too small once NDIRECT grew
-----------------------------------------------------------------------------------
With the picenable fix in place and NDIRECT raised to 58 (BSIZE still
512), the kernel booted all the way to `init: starting sh` and a real
shell prompt at full, untraced speed - the interrupt bug above was
genuinely the whole boot-hang story, confirmed once BSIZE stopped
confounding it. Running `usertests`, though, stalled silently partway
through, at `writetest1()`'s own "big files test": that function writes
a single file of exactly `MAXFILE` (now 186, up from 138) 512-byte
blocks. `mkfs`'s own build-time output showed only 118 blocks free
after laying down the initial `/README` + UPROGS files
(`FSSIZE(1000) - 882 already allocated`) - already less than the 186
blocks that one test alone needs, on top of everything else usertests
creates. The `NDIRECT` increase didn't just grow `MAXFILE` (more data a
single file can hold) - it also raised `sizeof(struct dinode)` to 256
bytes (`IPB` dropped from 8 to 2), quadrupling the number of blocks
needed just to store the fixed inode table (101 blocks vs. the original
~25), eating deep into `FSSIZE=1000`'s budget. `forks/riscv64/kernel/
param.h` had already solved the identical kind of shortfall (a bigger
MAXFILE/inode layout than i386's original FSSIZE was ever sized for) by
doubling `FSSIZE` to 2000; doing the same here (`include/param.h`)
immediately fixed it - `usertests` now runs to completion and prints
`ALL TESTS PASSED`, verified via a real, untraced, full-speed boot.

Verification: full boot and full usertests pass, no gdb involved
-----------------------------------------------------------------------
  make -C forks/x86_64 CROSS_COMPILE=x86_64-linux-gnu- QEMU=qemu-system-x86_64
    -> kernel.elf, fs.img, xv6.img all build clean
  qemu-system-x86_64 -nographic -net none -drive ... -smp 1 -m 512
    -> boots through SeaBIOS/ACPI/kernel init, "init: starting sh", "$"
       prompt - at full untraced speed, no gdb attached
  echo usertests -> runs the full suite, prints "ALL TESTS PASSED"

One benign trap pattern worth flagging, same category as the other
`notes_arch_*.txt` files' own such notes: partway through usertests, a
burst of `pid N usertests: trap 14 err 5 on cpu 0 eip 0x25ac addr
0x...--kill proc` lines followed by several `allocuvm out of memory`
lines appears, then the suite continues normally through several more
tests and eventually `ALL TESTS PASSED`. This is deliberate memory-
exhaustion testing (a test forks repeatedly until physical memory runs
out, expecting the kernel to fail allocation and kill the offending
process cleanly rather than crash) - not a regression.

A packaging gotcha: this fork's own CPUS default is this HOST's core count, not a small constant
--------------------------------------------------------------------------------------------------------
Once the bugs above were fixed, wiring up `make test-x86_64` through the
top-level Makefile (using the fork's own `qemu-nox`/default `CPUS`,
rather than the explicit `-smp 1`/`-smp 2` used while debugging by hand)
initially still failed - not a regression, a different, purely
environmental issue: `forks/x86_64/Makefile`'s own `ifndef CPUS` default
is `` `grep -c ^processor /proc/cpuinfo` `` (this HOST's own real core
count), unlike every other fork here (forks/riscv64 hardcodes 3, forks/i386
hardcodes 2). On this 64-core dev machine that means `qemu-nox` boots 64
vCPUs. xv6 itself only ever starts `min(that count, NCPU=8)` of them, so
the extra 56 vCPUs do nothing useful, but QEMU still pays real per-vCPU
TCG overhead for all 64 of them regardless - confirmed this alone was
enough to blow past `test-xv6.py`'s 60s boot-detection window (a real
boot to a shell prompt, reconfirmed separately with `-smp 2`, completed
in under 30s). Not a kernel bug - fixed at the call site instead of in
the fork: the top-level Makefile's own `run-x86_64`/`test-x86_64`
targets now pass `CPUS=2` explicitly (`CPUS` is `ifndef`-guarded, so it
threads through the environment into `test-xv6.py`'s own `make qemu-nox`
subprocess call the same way `TOOLPREFIX`/`CROSS_COMPILE` does elsewhere
in this repo). Worth remembering when bringing up any future fork: check
what a "sensible-looking" `ifndef`-guarded default actually resolves to
on THIS machine before assuming it's a small, portable constant like
every sibling fork uses.

Fully wired up this session
--------------------------------
- `./configure` now has an x86_64 detection block
  (`TOOLPREFIX_X86_64`/`QEMU_X86_64`), passed to forks/x86_64/Makefile
  under the name it actually expects (`CROSS_COMPILE=`, not
  `TOOLPREFIX=` - this repo's own naming stays `TOOLPREFIX_X86_64` for
  consistency with every other arch regardless of what the fork itself
  calls the variable).
- Top-level Makefile: `build-x86_64`/`run-x86_64`/`test-x86_64`/
  `clean-x86_64`/`kill-x86_64`, folded into `build-all`/`test-all`/
  `clean-all`/`kill-all`.
- `forks/x86_64/test-xv6.py`, modeled on forks/i386/test-xv6.py (same
  shape: usertests-only, no crash/log/orphan tiers - this fork's own
  UPROGS list has no grind/sync/logstress/forphan/dorphan either).
- Dockerfile `ARCH=x86_64` case and a matching
  `.github/workflows/docker.yml` matrix entry, verified locally first
  with the exact `--build-arg ARCH=x86_64` (see
  notes_debugging_techniques.txt item 6) before relying on CI to catch
  anything.
