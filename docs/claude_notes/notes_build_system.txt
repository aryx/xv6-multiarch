Build-system findings: incremental builds across the 14 ports
=============================================================

Notes on how these ports' Makefiles actually behave as *builds* - what is
tracked, what is not, and what that cost - as opposed to what any one port
does at runtime (see notes_arch_*.txt for that). Written 2026-09-09 after
"make build-all; make test-all" turned out to recompile most of the tree a
second time.


1. Header dependency tracking: "make depend" is the wrong answer
----------------------------------------------------------------
The symptom was that `make test-all`, run straight after a complete
`make build-all`, recompiled eight of the fourteen ports from scratch.
The direct cause was a `make clean` sitting in those ports' own
test-xv6.py `reset_cmds` - but the *reason* someone had put it there is
the interesting part: those Makefiles had no working header dependency
tracking, so editing a header rebuilt nothing, and a from-scratch build
was the only way to be sure the kernel under test matched the source.
The clean was a workaround for a build bug, not a test requirement.

The tempting fix is a `make depend` target, the way UNIX makefiles did it
before roughly 2000: a separate pass (`makedepend`, or BSD `mkdep`) that
scans every source file for #includes and appends the results to the
Makefile itself. Do NOT add one here. Its failure mode is silence: the
dependencies are only as fresh as the last time somebody remembered to
re-run the pass, and a stale entry produces a kernel built against a
header that no longer exists in that form - which then boots, and misbe-
haves subtly, which is the single most expensive kind of bug in this
repo (see notes_debugging_techniques.txt item 38 on how long a wrong
assumption about what is actually running costs).

Linux itself abandoned `make depend` during 2.5/2.6. What it does now,
and what this repo does now, is the same idea in one step:

  - Pass `-MD` (or `-MMD`) when compiling. GCC then writes, as a side
    effect of the compile that produces `foo.o`, a `foo.d` next to it
    containing a real Make rule:

        build/proc.o: source/proc.c include/types.h include/proc.h ...

  - `-include` those .d files from the Makefile. The leading dash makes
    a missing .d (a first build, nothing to be stale about) a no-op
    rather than an error.

The property that matters: the dependency list is generated by the very
compile whose output it describes, so it cannot be stale. There is no
pass to remember, no target to document, and no way for the tree to
drift. Linux adds a `fixdep` step on top (rewriting each .d into
`.<obj>.o.cmd`, so that a changed *command line* also forces a rebuild,
and so that deleting a header does not break the build) - worth knowing
about, but more machinery than these ports need.

State of the tree after this session - every wired-up port now both
generates and reads its dependencies:

  already correct    riscv64, riscv32, i386, amd64, amd64-jserv, arm64,
                     loongarch, mips, arm64-pi4
  generated but      arm-pi1, arm-pi2, arm-pi3, arm-pi1-bis
  never read         (-MD was in CFLAGS all along; nothing -included the
                     .d files, so it was pure overhead)
  neither            arm (no -MD anywhere; -MD added to both CFLAGS and
                     ASFLAGS in makefile.inc)

Verifying a fix here is not optional and not hard: touch a header, build,
and check that a .o which includes it actually got a new mtime. Counting
compiler lines in the build log is NOT a reliable check - forks/arm and
forks/arm-pi1-bis route every compile through makefile.inc's
`quiet-command` macro, which prints "  CC  build/proc.o" and no compiler
name at all, so a grep for "gcc" reports zero and looks like success.


2. A directory must be an order-only prerequisite
--------------------------------------------------
forks/arm-pi1 and forks/arm-pi2 rebuilt themselves completely on *every*
make, even two `make build-all` runs back to back with no edit in
between. Both had object rules of the form

    $(BUILD)%.o: $(SOURCE)%.c $(BUILD)

listing the output directory as a normal prerequisite so that it gets
created first. But writing a file into a directory updates that
directory's own mtime, so `build/` becomes newer than every object the
moment the first one is written, and stays that way - every later make
sees all objects as out of date. The fix is an order-only prerequisite:

    $(BUILD)%.o: $(SOURCE)%.c | $(BUILD)

"|" means "make sure this exists first, but never compare timestamps
against it". forks/arm-pi3 already had it right, which is what made the
other two identifiable as bugs rather than as a house style.


3. A phony target must not be a prerequisite of a real file
------------------------------------------------------------
Also in forks/arm-pi2, and the second half of why it never stopped
rebuilding. Its filesystem image is built by a recursive make, and the
rule was marked phony so that the recursive make runs every time and
does its own up-to-date checking:

    .PHONY: source/fs.img
    source/fs.img:
            $(MAKE) -C uprogs ... fs.img
            cp uprogs/fs.img source/fs.img

    $(BUILD)entry.o: source/fs.img          # entry.S .incbin's it

GNU Make treats a phony prerequisite as unconditionally newer than any
real file depending on it, so entry.o was re-assembled and the whole
kernel re-linked on every build - and the unconditional `cp` bumped the
image's mtime to match, so even dropping .PHONY would not have helped on
its own. Delegating the up-to-date check to a sub-make is a reasonable
design; the fix is to keep the phony target but stop naming a real file
with it, and to make the copy content-conditional so the timestamp only
moves when the bytes do:

    .PHONY: uprogs-fs-img
    uprogs-fs-img:
            $(MAKE) -C uprogs ... fs.img

    source/fs.img: uprogs-fs-img
            cmp -s uprogs/fs.img $@ || cp uprogs/fs.img $@

General rule: if a real file depends on it, it cannot be phony. If you
want "always run the check, rarely touch the file", separate the two.


4. What test-<arch> legitimately needs to redo, and what it does not
--------------------------------------------------------------------
Worth keeping straight when touching any test-xv6.py, because the two
groups look similar and are not:

  - Ports booted with a writable disk image (riscv64, riscv32, i386,
    amd64, amd64-jserv, arm64 - QEMU gets fs.img as a drive) genuinely
    must regenerate it per run: usertests writes into that filesystem,
    and a second run against a dirtied image can fail for reasons that
    have nothing to do with the change under test. Their `rm -f fs.img`
    + `make fs.img` is correct and costs one mkfs invocation.

  - Ports whose filesystem is embedded in the kernel image (arm, arm-pi1,
    arm-pi1-bis, arm-pi2, arm-pi3, arm64-pi4, loongarch, mips - all
    booted with `-kernel` and nothing else; the image arrives via
    `.incbin`, a ramdisk header, or a memfs build) cannot be dirtied at
    all: guest writes land in RAM and die with the process. These needed
    no reset beyond an ordinary incremental build.

Effect of getting this right: `make test-all` went from recompiling
eight ports from scratch to recompiling nothing, and from a bit over a
minute to 21 seconds, with the six mkfs runs above as the only work it
repeats.
